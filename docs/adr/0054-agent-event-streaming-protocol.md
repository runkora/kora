# 54. Agent Event Streaming Protocol

**Status:** Proposed  
**Date:** 2026-05-08  
**Deciders:** Platform Engineering  
**Technical Story:** Users must see agent output streaming in real time — text, thinking, tool calls — regardless of when they connect. This ADR defines the event format, the streaming path from CLI subprocess to browser, and how context is preserved on reconnect.

---

## Context

### Background

Agent output is generated by CLI frameworks (Claude Code, Codex, OpenCode) running as subprocesses inside agent pods. That output must reach the browser in real time with sub-second latency. Users must also be able to reconnect and see full history — not just what happened while connected.

The inference-gateway already streams tokens to CLI frameworks. That stream cannot be intercepted for the browser: it flows into the CLI, not out of it, and includes internal scaffolding (tool call markup, system prompts, multi-call chaining) that should not be exposed directly.

### Problem Statement

The platform needs a streaming protocol that:
- Sources from CLI stdout (not from the inference-gateway stream)
- Delivers events to the browser in real time
- Is framework-agnostic — the browser does not know or care which CLI is running
- Supports full history replay when a user connects mid-run or reconnects after a disconnect
- Works for both interactive chat sessions and headless observation

### Goals

- Define the Orbit standard event format
- Define the full streaming path from CLI subprocess to browser
- Define how event history is persisted and replayed
- Define the user message input path (browser → CLI stdin)

### Non-Goals

- WebSocket bidirectional protocol (deferred — SSE + POST is sufficient for v1)
- Server-push notifications for run state changes (run state is polled via REST in v1)
- Multi-observer broadcasting (only one active session per run in v1)

---

## Decision Drivers

* The CLI subprocess owns the output stream — we must read stdout, not tap the inference-gateway
* Events must be persisted before being emitted to SSE — no data loss on reconnect
* `orbit-agents` must be stateless with respect to active streams — any instance can serve any session
* SSE is simpler than WebSocket and sufficient for the one-way output stream

---

## Considered Options

### Option A: orbit-agents as stateful SSE proxy (per-connection state in memory)

**Description:** Each `orbit-agents` instance maintains an in-memory SSE connection to the session-manager and proxies it to the browser. Session routing is sticky to the `orbit-agents` instance.

**Pros:**
- Low latency — direct proxy, no intermediate persistence
**Cons:**
- `orbit-agents` instances are sticky — cannot scale horizontally without session affinity at the load balancer level
- `orbit-agents` restart drops all active SSE connections
- History replay requires in-memory buffer — data lost if buffer is full or instance restarts

### Option B: Event log in PostgreSQL + LISTEN/NOTIFY

**Description:** Session-manager writes events to `run_events` (Postgres) as they occur. `orbit-agents` uses Postgres LISTEN/NOTIFY to receive new event notifications. On connect, `orbit-agents` replays the full event log, then tails live notifications. Browser receives a single SSE stream.

**Pros:**
- `orbit-agents` is fully stateless — any instance can serve any session
- Full history always available — replay from event log regardless of when user connects
- Durable — events survive `orbit-agents` and session-manager restarts
- No in-memory buffers — event log is the buffer
**Cons:**
- Adds Postgres write on every event — must be fast enough for token-level streaming
- LISTEN/NOTIFY adds a small latency hop over direct proxy

### Option C: Redis pub/sub for live streaming + Postgres for history

**Description:** Session-manager publishes events to Redis pub/sub channel. `orbit-agents` subscribes for live events. Postgres stores event log for history. On connect: replay from Postgres, then subscribe to Redis.

**Pros:**
- Lower live latency than Postgres LISTEN/NOTIFY
- Separate channels for different concerns

**Cons:**
- Adds Redis as a dependency on the hot streaming path
- Two systems to keep in sync — event written to Postgres but not Redis (or vice versa) creates inconsistency
- Postgres LISTEN/NOTIFY latency is acceptable for token streaming (sub-10ms typical)

---

## Decision

**Chosen Option: B — Event log in PostgreSQL + LISTEN/NOTIFY**

Postgres LISTEN/NOTIFY is already available in the platform stack, provides sufficient latency for streaming text, and eliminates the need for Redis on the hot path. The event log is the single source of truth for both live streaming and history replay.

### Orbit Standard Event Format

All events emitted by the transform layer are typed. The browser renders based on event type regardless of the underlying framework.

| Event Type | Payload Fields | Description |
|---|---|---|
| `text_delta` | `delta: string` | A chunk of assistant text |
| `thinking_delta` | `delta: string` | A chunk of assistant reasoning |
| `tool_use` | `id: string`, `name: string`, `input: object` | Agent invoking a tool |
| `tool_result` | `tool_use_id: string`, `content: string`, `is_error: bool` | Tool invocation result |
| `message_stop` | — | Agent has finished the current response turn |
| `run_state` | `state: string` | Run state change notification (starting, active, completed, failed) |

Events are serialised as newline-delimited JSON in the `run_events` table and as SSE `data:` lines in the browser stream.

### Streaming Path

```
CLI subprocess stdout
  ↓ (read by)
transform layer (per-framework, inside session-manager)
  ↓ (normalises to Orbit event format)
  ↓ INSERT INTO run_events + NOTIFY run:{run_id}
PostgreSQL
  ↓ LISTEN run:{run_id}
orbit-agents (any instance)
  ↓ SSE data: {event JSON}
browser (EventSource)
```

### Connect / Reconnect Flow

1. Browser opens `GET /api/v1/runs/{id}/events` (SSE)
2. `orbit-agents` acquires a Postgres connection
3. Begins LISTEN on channel `run:{run_id}`
4. Replays all existing `run_events` for this run in `sequence_no` order as SSE events
5. Transitions to live tail: each NOTIFY triggers a read of new events since last replayed sequence and emits them
6. On browser disconnect: stops LISTEN, releases Postgres connection

This ensures the browser always sees all events in order from the beginning of the run, regardless of when it connects.

### User Message Input Path

User messages travel a separate path — they are not events in `run_events`.

```
browser → POST /api/v1/runs/{id}/messages {content: "..."}
  ↓ (orbit-agents looks up pod_ordinal for run_id)
  ↓ POST http://{agent}-{n}.{agent}.{namespace}.svc/session/{run_id}/messages
session-manager
  ↓ writes to CLI subprocess stdin
CLI subprocess (processes message, emits new events on stdout)
```

User messages are stored in a separate `run_messages` table (ADR-0053) — not in `run_events`. The agent's response is captured as `text_delta` and `tool_use` / `tool_result` events in `run_events`. This split keeps the event log strictly as agent output (what the UI renders), while `run_messages` captures the input side for resume.

### Event Write Ownership

**Transform layer (session-manager)** writes all CLI output events to `run_events`: `text_delta`, `thinking_delta`, `tool_use`, `tool_result`, `message_stop`. These come from parsing CLI subprocess stdout.

**orbit-agents** writes `run_state` events to `run_events` when a state transition occurs (triggered by the session-manager's internal callback `POST /internal/runs/{id}/state`). `run_state` events are never written by the session-manager directly.

Both writers INSERT into `run_events` and issue `NOTIFY run:{run_id}` in the same transaction. Sequence numbers are monotonically increasing per run — all writers use a Postgres sequence for `sequence_no` to ensure ordering without coordination.

### Backpressure

If the browser's SSE connection is slow, `orbit-agents` applies natural backpressure: it does not read the next NOTIFY until it has written the current batch to the SSE connection. This is acceptable — the event log preserves all events regardless.

---

## Consequences

### Positive

- `orbit-agents` is fully stateless for streaming — horizontal scaling works without sticky sessions
- Full history always available — replayed deterministically from event log
- No data loss on `orbit-agents` or session-manager restart — events in Postgres survive
- Works identically for interactive chat and headless observation

### Negative

- Postgres write per event adds latency — acceptable for text streaming (sub-10ms), needs validation at token throughput
- LISTEN/NOTIFY does not guarantee delivery if the listener disconnects — mitigated by the replay-from-log approach (missed NOTIFYs are caught by sequence_no gap detection on reconnect)

### Neutral

- `run_events` table grows continuously — retention policy required for long-running agents

---

## Implementation

### Sequence Number Gap Detection

On reconnect, `orbit-agents` replays from `sequence_no = 0`. No gap detection is required for the reconnect case. LISTEN/NOTIFY gaps during a live session are handled by reading all events with `sequence_no > last_emitted` on each NOTIFY, not just the single notified event.

### SSE Event Format

```
id: {sequence_no}
event: {event_type}
data: {json payload}

```

The SSE `id` field allows browsers to send `Last-Event-ID` on reconnect. `orbit-agents` honours this by replaying from `sequence_no = Last-Event-ID + 1` rather than from 0, reducing replay volume for long-running sessions.

---

## Validation

### Success Metrics

- First event delivered to browser within 5 seconds of run start
- No events lost on `orbit-agents` restart while a run is active
- Full event log replayed correctly on reconnect for runs up to 1 hour in duration
- Event write latency (INSERT + NOTIFY) ≤ 5ms p95
