# Graders

**Status:** Proposed  
**Date:** 2026-11-19  
**Deciders:** Justin Wilkin  
**Technical Story:** [Graders PRD](../prd/graders.md). Grade every ended run of an agent against fixed questions answered by a decision model, and show the verdicts on the run page and the agent page.

---

## Context

A Grader is a `runkora.io/v1alpha1` resource with fixed questions about one agent's runs. A decision model on the System One API answers them from the run's recorded trace. The PRD defines the resource, the verdict rules and the views. This ADR decides where grading runs, how the state is built, who pays for it, how results are stored and how they are read.

The code grading builds on has these properties:

*   Declared kinds are applied by the operator through `NewDeclaredReconcilers` (`backend/internal/operator/declared_kinds.go`). Each kind has a prepare function that resolves its references, such as `prepareTrigger`. kora-agents serves the `environments` and `agents` appliers through `declaredController` (`backend/cmd/kora-agents/main.go`). Kinds are listed in `backend/internal/platform/declarative/contract.go`.
*   CRD validation is CEL in `XValidation` markers on `backend/internal/platform/declarative/v1alpha1/types.go`. `TestEveryCELRuleHasACase` in `cel_test.go` needs a case for every rule.
*   A run ends in `completed`, `failed`, `budget_exhausted` or `terminated`. The end is recorded inside one transaction with its platform event: `SetRunState` and `publishState`, `MarkRunFailed`, `TerminateRun` and `endRuns` in `backend/internal/agents/postgres.go`. `Transition` writes the terminal `run_state` run event after `SetRunState` commits (`backend/internal/agents/run_service.go`). The event types come from `stateEventType` in `backend/internal/agents/spine_events.go`.
*   The internal event stream admits only kora-triggers. `InternalController.Middleware` calls `mw.RequireSystemCaller(triggersComponent, ...)` (`backend/internal/koraevents/handlers.go:111-135`). The mesh policy admits only `/system/kora-triggers` (`charts/kora/templates/kora-events/authorizationpolicy.yaml:24`).
*   `run_events` holds the durable types in `durableEventTypes` (`backend/internal/agents/pubsub.go`), plus `human_message`, `trigger_message`, `run_state` (`backend/internal/agents/run_service.go`) and `sandbox_environment` (`backend/internal/agents/run_environments.go`). A `tool_result` past 64 KiB is cut by `newToolResult` with `truncated` and `original_bytes` (`backend/internal/agents/sessionmanager/events.go`).
*   `text_block` holds the assistant text that preceded a tool call. `recordToolUse` resets the text after it records the block (`backend/internal/agents/sessionmanager/acp_events.go`). `message_complete` holds only the text after the last tool call (`MessageCompletePayload`).
*   The System One client times out after 15 seconds (`backend/internal/platform/clients/inference/client.go:30`). Its comment says the value matches the gateway's per-attempt decision timeout. `newClient` takes a timeout and is unexported. `SystemOneRequest.Questions` and `Question.Criteria` are maps. Only the `choice` type has a constant. `Answer` has `Choice`, `Probabilities` and `Confidence`. The gateway's per-attempt decision timeout is 15 seconds (`backend/internal/inferencegw/providers/compatible/discovery.go:24`).
*   `Service.SystemOne` in `backend/internal/inferencegw/service.go` checks model policy and budget, writes a usage row and returns the upstream body unchanged. `writeUsage` stamps the run ID from `mw.RunIDFromContext`, which returns one only for AGENT principals (`backend/internal/platform/middleware/run_context.go`). The response carries no usage ID and no cost.
*   Minting a SERVICE token is allowlisted to kora-triggers (`mintServiceTokenCallers`, `backend/internal/identity/handlers_service_token.go:32`). kora-triggers creates a SERVICE principal per trigger with `CreateGrant` (`backend/internal/platform/clients/policy/client.go:112`). Its grants carry no `BudgetAssignment`. It mints the principal's token in `triggerToken` (`backend/internal/triggers/service_ingest.go`). The policy client has no grant scope update.
*   Run reads are authorized in the service. `Authz.checkRun` checks one agent's runs, and `readableRunAgentTypes` scopes lists (`backend/internal/agents/authz.go`). Runs of a delegated agent that others started also need `agents:delegated:read`.
*   `systemPromptWithBrief` appends a brief that embeds the run's workspace directory (`backend/internal/agents/run_service.go`). The rendered prompt differs on every run.

This touches **Who is this agent?** Grading calls the gateway as its own per-tenant SERVICE principal, and kora-agents gains the right to mint that principal's token. It touches **What can it access?** Grades are read under the same rules as the runs they describe. **How does it connect?** is unchanged. The decision model reads the run's recorded events through the inference gateway.

### Goals

*   Grade each run once at its end, for every Grader of its agent.
*   Give the same stored verdict for the same snapshot and the same Grader version.
*   Pay for grading under its own principal, outside the agent's cost and within the tenant ceiling.
*   Keep a run's grades regradable after its events are gone.

### Non-Goals

*   The statistics views, config versions, thread grading, answer labels and offline test sets (see the PRD).
*   Grading a run before it ends.

## Considered Options

### Decision 1: Grader CRD and Validation Split

**Context:** A Grader is declared like a Trigger. Some rules need only the object. Others need other resources or produce derived fields.

*   **Option A (chosen):** CEL checks every rule that reads only the Grader. The operator resolves the Agent and the VirtualModel. The kora-agents applier normalizes the spec, computes the version and writes the rows.
*   **Option B (rejected):** The applier checks every rule. `kubectl apply` would accept a bad Grader. The error would show only in its status.
*   **Option C (rejected):** A validating webhook. It adds a served component to the operator for rules CEL can express.

**Decision:** `GraderSpec` has `agent`, `description`, `model` (`ModelRef`), `threshold`, `minPassRate`, `appliesWhen` and `questions`. `questions`, `options` and `levels` are `listType=map` keyed by `name`. The list type makes names unique. The applier also rejects a repeated question name. `questions` has at most 32 items. `accept` and `skipOn` are `listType=set`. Every list has a `maxItems` to keep the CEL cost estimate inside its budget. CEL rules on the object:

*   `type` is `boolean`, `choice` or `scale`.
*   A `boolean` sets `expect` and no `options`, `levels`, `accept` or `skipOn`.
*   A `choice` sets `options` and `accept`, and no `levels` or `expect`. No option is named `none`. `options` has at most 254 items. With `none` added the count stays within the System One limit of 255.
*   A `scale` sets `levels`, `accept` and `skipOn`, and no `options` or `expect`. `levels` has 2 to 10 items, the System One `score` range.
*   Every `accept` and `skipOn` name is an option or a level. A `choice` may also name `none`.
*   No name is in both `accept` and `skipOn`.
*   `skipOn` does not list every option or level. For a `choice` the count includes `none`.
*   A `choice` `accept` does not list every option and `none`.
*   A `threshold` has `0 <= fail < pass <= 1`.
*   `minPassRate` is a whole percentage from `0%` to `100%`.
*   `agent` is immutable. A Grader's grades belong to one agent.

The operator gains a `graders` kind with `prepareGrader`. It resolves the Agent in the Grader's namespace and the VirtualModel with `refs.model`, as `prepareTrigger` does. It watches Agent and VirtualModel. The operator ClusterRole (`charts/kora/templates/operator/clusterrole.yaml`) gains `graders`. kora-agents registers `declarative.KindGraders` in `declaredController`.

The applier fills default thresholds, adds the `none` option to each `choice`, computes the version (Decision 2), upserts `graders` and inserts `grader_versions` when the version is new. A new version enqueues its regrade (Decision 9).

**Consequences:** A structural error fails at `kubectl apply`. A missing Agent or model shows in the Grader's status, as for a Trigger. Each CEL rule needs a case in `cel_test.go`.

### Decision 2: Version Hash

**Context:** Verdicts are compared only within one Grader version. A field that changes answers or verdicts must change the version. A field that changes neither must not.

*   **Option A (chosen):** SHA-256 over canonical JSON of the normalized `model`, `threshold`, `appliesWhen` and `questions`.
*   **Option B (rejected):** The resource's `metadata.generation`. A description edit would split the series. A recreated Grader would restart at 1.
*   **Option C (rejected):** Hash the whole spec. A `description` or `minPassRate` edit would regrade runs whose answers cannot change.

**Decision:** The hash input is the spec after the applier normalizes it. The Grader's default threshold is filled in. A question threshold equal to the Grader's is dropped. `none` is added to each `choice`. `accept` and `skipOn` are sorted. Questions are sorted by name. A Grader that omits `threshold` and one that sets 0.7 and 0.3 share a version. The request keys questions by id (Decision 6), so their order does not reach the model. `description`, `minPassRate` and `agent` are not hashed. `grader_versions.version` is the lowercase hex digest.

The applier also hashes the same input with every `threshold` removed. Two versions with the same thresholdless hash ask the same questions of the same model (Decision 9).

**Consequences:** Reordering questions keeps the version. Editing `minPassRate` changes the Grader's status at once, over the same window.

### Decision 3: Trigger and Queue

**Context:** A run is graded once, when it ends. The end is written in a run-state transaction in kora-agents. kora-agents owns grading.

*   **Option A (chosen):** kora-agents inserts one `grade_jobs` row per Grader of the run's agent inside the run-state transaction at run end. This is an outbox in the same database.
*   **Option B (rejected):** Subscribe to the kora-events internal stream for `agents.run.*` end events. The stream admits only kora-triggers today (`backend/internal/koraevents/handlers.go:111-135`). The mesh policy admits only `/system/kora-triggers`. kora-agents would read its own events back through another service and keep a cursor.
*   **Option C (rejected):** Start grading in memory after the transaction commits. A restart between the commit and the call loses the grade.

**Decision:** `SetRunState` (for a terminal state), `MarkRunFailed`, `TerminateRun` and `endRuns` insert the jobs in their transaction. The insert selects the agent's Graders and their current versions. It uses `ON CONFLICT (grader_id, version, run_id) DO NOTHING`. A terminate after a run has ended records `agents.run.terminated.v1` after the run's earlier end event. The conflict clause keeps one job. A worker in kora-agents claims due jobs with `FOR UPDATE SKIP LOCKED`, as `ClaimPendingRuns` does. The worker builds the state once the run's terminal `run_state` event is recorded. A job claimed before it is recorded returns to the queue. On its last attempt the worker builds the state from the events present. A failed call backs off and retries. A call that fails on its last attempt writes the grade with status `error`.

**Consequences:** A grade job commits only when its run's end commits. Every kora-agents replica runs the worker. A Grader grades runs that end after it is applied.

### Decision 4: State Construction

**Context:** The decision model reads one state per call. The same run must give the same state. The window is about 247k input tokens. A typical run is about 24k.

*   **Option A (chosen):** Build the state from `run_events` in sequence order, cap `tool_result` bodies by fixed steps against a deterministic size estimate, and store the uncapped state as a snapshot.
*   **Option B (rejected):** Count tokens with the model's tokenizer. The gateway exposes no tokenizer. A tokenizer change would change the state of an old run.
*   **Option C (rejected):** Summarize long tool results with a model. Two calls on the same run would give different states.

**Decision:** The state is a JSON array of `{seq, type, payload}`, one item per event, in `sequence_no` order. It includes `human_message`, `trigger_message`, `tool_use`, `tool_result`, `text_block`, `message_complete`, `run_state`, `run_error`, `turn_stopped` and `guardrail_warning`. It excludes `sandbox_status`, `sandbox_environment` and `api_retry`. Streaming deltas are not recorded and are not included. `human_message` keeps its sender and event summary. `trigger_message` keeps its trigger, delivery and event summary. A `tool_result` cut at 64 KiB keeps `truncated` and `original_bytes`.

The size estimate is the byte length of the serialized state divided by 4. It is compared with `agents.grading.windowTokens`, a kora-agents setting with a default of 247000. When the estimate exceeds the window, kora-agents caps every `tool_result` content at the first step that fits: 4000, 2000, 1000, then 500 characters, then no bodies. A capped result keeps a marker with its original length. Messages, text and tool inputs are never cut. A state that does not fit with no bodies is written with status `too_large` and no model call. `grades.state_cap` records the step used, or null. `grades.state_hash` is the hash of the snapshot.

The snapshot is the uncapped state. The first grade job of a run writes it to `grade_states` with its SHA-256 hash. Later jobs and regrades read the snapshot and apply the cap step from it. `grade_states` carries `run_id` with no foreign key to `runs`.

**Consequences:** Every Grader of a run reads the same state. The cap step depends only on the run's events and the window setting. A change to `agents.grading.windowTokens` changes the cap of later grades only. A snapshot holds every tool result up to 64 KiB. The largest measured run is about 1.58M tokens. Postgres compresses the column out of line. kora-agents has no run event retention today.

### Decision 5: Grading Principal and Budget

**Context:** Grading is paid through its own principal. The principal has no budget of its own. A run that ended on `budget_exhausted` is still graded. Agent cost excludes grading. The gateway admits a System One call under a token with `inference:invoke` and the model's `inference:<family>:<name>:use` scope. It checks the caller's budget with `checkBudget`.

*   **Option A (chosen):** A per-tenant SERVICE principal `grader:<tenant>`, minted by kora-agents.
*   **Option B (rejected):** A gateway path that accepts kora-agents' SYSTEM token on behalf of a tenant, with a grading budget bucket. It adds a new authentication path to the gateway and a new budget type to enforcement.

**Decision:** kora-agents creates the SERVICE principal `grader:<tenant>` when the tenant's first Grader is applied. Its grant holds `inference:invoke` plus the use scope of each Grader model in the tenant. The grant has no `BudgetAssignment`, like the grants of trigger principals. No budget is set on the principal. A Grader may name any Ready `VirtualModel` in the system namespace, as a routed Trigger may name its decision model. The grant holds exactly the models of the tenant's live Graders. A change to that set creates a replacement grant. kora-agents then deletes the old grant. When the tenant has no Grader left, kora-agents deletes the grant.

kora-agents is added to `mintServiceTokenCallers` (`backend/internal/identity/handlers_service_token.go:32`). The worker mints a short-lived token for `grader:<tenant>` through `MintServiceToken`, as `triggerToken` does in kora-triggers.

Grading spend counts against the tenant. The tenant ceiling bounds it. `checkBudget` refuses a call when the tenant ceiling is spent. The grade is then written with status `error` with no retry. `grader:<tenant>` is a SERVICE principal. Its usage rows carry no run ID.

**Consequences:** Adding kora-agents to the mint allowlist is a security change. kora-agents can then act as any SERVICE principal in any tenant. Each token is bounded by its principal's grants. A budget-exhausted run is graded while the tenant ceiling has room. Grading spend competes with the tenant's other spend under that ceiling.

### Decision 6: System One Call

**Context:** A Grader has `appliesWhen` and up to many questions. The gateway and the client both stop a decision after 15 seconds. Large states have unmeasured latency.

*   **Option A (chosen):** One System One call per run per Grader, with `appliesWhen` and every question in one request.
*   **Option B (rejected):** One call per question. Cost and input tokens multiply by the question count for the same state.
*   **Option C (rejected):** Call `appliesWhen` first and the questions only when it applies. Every graded run would take two calls.

**Decision:** The request's `state` is the capped state. `SystemOneRequest.Questions` stays an object keyed by question id. It holds `appliesWhen` and each question. A `boolean` maps to `noul`, a `choice` to `choice` and a `scale` to `score`. A choice's `criteria` stays a map from option name to description. A score's `criteria` is a list of level descriptions, lowest first. System One rejects a map for a score. A choice answer carries `probabilities` keyed by option name. A score answer carries `probabilities` and a `legend` keyed by the 0-based level index. The scale p reads these probabilities.

The gateway's per-attempt decision timeout stays 15 seconds by default for every caller. A caller raises it for one request with the `X-Kora-Decision-Timeout` header, in whole seconds. The gateway caps it at `inferenceGateway.maxDecisionTimeoutSecs`, default 60. Grading sends 60 seconds. The client gains `NewClientWithTimeout`. The grading client timeout exceeds the decision timeout to leave room for a gateway retry. Grading uses 130 seconds on the client and 60 seconds on the decision.

The gateway returns the usage row's ID and estimated cost in the `X-Kora-Usage-Id` and `X-Kora-Cost-USD` response headers. The System One body passes through unchanged. A model with no known price gives no cost, and `grades.cost` is null. The grade records `input_tokens` from `usage`, `model_served` from the response's `model`, `usage_id` and `cost`.

**Consequences:** A timeout or a provider error fails the whole grade. The job retries it. Callers that send no timeout header keep the 15 second decision timeout. Every System One caller gets the two usage headers.

### Decision 7: The agent_config Digest

**Context:** At run start, kora-agents hashes the effective config and stores it on the run as `agent_config`. The rendered prompt embeds the run's workspace directory. Skills do not attach to agents yet.

*   **Option A (chosen):** Hash the inputs of the session request at `startClaimed`.
*   **Option B (rejected):** Hash the rendered `sessionmanager.CreateSessionRequest`. Every run would get its own digest.
*   **Option C (rejected):** Hash the resolved provider route. A provider failover would change the digest with no change to the agent.

**Decision:** `startClaimed` computes SHA-256 over canonical JSON of:

*   the agent's raw `SystemPrompt`;
*   the brief's inputs from `EffectiveAccess`, without the workspace directory, the sandbox mount or the product name;
*   the VirtualModel name;
*   the framework;
*   the MCP tools from `MCPServers`;
*   the connectors;
*   the agent's grant scopes;
*   the environments;
*   the skills, empty until skills attach to agents.

A migration adds nullable `runs.agent_config`. The first attempt sets it with `WHERE agent_config IS NULL`. A run started before the column exists has no digest.

**Consequences:** Two runs with the same inputs share a digest. A change to the brief's template does not change the digest. Config versions are a follow-up.

### Decision 8: Storage

**Context:** kora-agents owns the tables. Access is plain pgx with Goose migrations from `make migrate-create`.

**Decision:** Six tables. `grader_versions`, `grade_jobs`, `grades` and `grade_answers` cascade from `graders`. `grade_states` holds one snapshot per run.

```sql
CREATE TABLE graders (
    id              text PRIMARY KEY,
    tenant_id       text NOT NULL,
    agent_type_id   text NOT NULL REFERENCES agent_types(id) ON DELETE CASCADE,
    name            text NOT NULL,
    description     text NOT NULL DEFAULT '',
    min_pass_rate   numeric,              -- 0 to 1; null when unset
    current_version text NOT NULL,
    created_at      timestamptz NOT NULL,
    updated_at      timestamptz NOT NULL,
    UNIQUE (tenant_id, name)
);

CREATE TABLE grader_versions (
    grader_id         text NOT NULL REFERENCES graders(id) ON DELETE CASCADE,
    version           text NOT NULL,     -- Decision 2
    thresholdless     text NOT NULL,     -- the hash without thresholds
    spec              jsonb NOT NULL,    -- the normalized spec
    created_at        timestamptz NOT NULL,
    PRIMARY KEY (grader_id, version)
);

CREATE TABLE grade_states (
    run_id      text PRIMARY KEY,        -- no foreign key to runs
    tenant_id   text NOT NULL,
    state       bytea NOT NULL,          -- the uncapped state
    state_hash  text NOT NULL,
    size_bytes  integer NOT NULL,
    created_at  timestamptz NOT NULL
);

CREATE TABLE grade_jobs (
    id          text PRIMARY KEY,
    tenant_id   text NOT NULL,
    grader_id   text NOT NULL REFERENCES graders(id) ON DELETE CASCADE,
    version     text NOT NULL,
    run_id      text NOT NULL,
    kind        text NOT NULL,           -- grade, regrade or recompute
    attempts    integer NOT NULL DEFAULT 0,
    run_after   timestamptz NOT NULL,
    last_error  text,
    created_at  timestamptz NOT NULL,
    UNIQUE (grader_id, version, run_id)
);

CREATE TABLE grades (
    id              text PRIMARY KEY,
    tenant_id       text NOT NULL,
    grader_id       text NOT NULL REFERENCES graders(id) ON DELETE CASCADE,
    version         text NOT NULL,
    run_id          text NOT NULL,
    agent_type_id   text NOT NULL,
    agent_config    text,
    run_outcome     text NOT NULL,
    run_started_at  timestamptz NOT NULL,  -- the run's started_at, or created_at when it never started
    graded_at       timestamptz NOT NULL,
    state_hash      text NOT NULL,
    state_cap       integer,             -- characters; 0 is no bodies; null is not capped
    input_tokens    integer,
    model_served    text,
    usage_id        text,
    status          text NOT NULL,       -- graded, not_applicable, applies_uncertain, too_large, error
    applies_raw     jsonb,
    applies_p       numeric,
    verdict         text,                -- pass, fail or uncertain; set when status is graded
    cost_usd        numeric,
    UNIQUE (grader_id, version, run_id)
);
CREATE INDEX idx_grades_window ON grades (grader_id, version, run_started_at DESC) WHERE status = 'graded';

CREATE TABLE grade_answers (
    grade_id  text NOT NULL REFERENCES grades(id) ON DELETE CASCADE,
    question  text NOT NULL,
    raw       jsonb NOT NULL,            -- the answer as returned
    p         numeric,                   -- null when skipped
    verdict   text NOT NULL,             -- pass, fail, uncertain or skipped
    PRIMARY KEY (grade_id, question)
);
```

`applies_raw` holds the `appliesWhen` answer as returned. A recompute needs it. Deleting a Grader deletes its versions, jobs, grades and answers. The applier's delete path then removes the `grade_states` rows of runs with no grade left.

**Consequences:** The window query reads `idx_grades_window`. Postgres tests are `TestPostgres_*` under `make test-postgres`.

### Decision 9: Regrade

**Context:** Thresholds are part of the version. A new version starts with no grades. Without a regrade the Grader would read "Not enough runs" until 15 new runs end.

*   **Option A (chosen):** A new version regrades the Grader's last 30 graded runs from their snapshots. A threshold-only change recomputes from the stored raw answers with no model call.
*   **Option B (rejected):** Regrade every graded run. The cost grows with the agent's history.
*   **Option C (rejected):** Never regrade. A question edit would hide the Grader's status for 15 runs.

**Decision:** The applier selects the previous version's last 30 grades with status `graded`, ordered by `run_started_at`. It inserts one job per run for the new version. The job kind is `recompute` when the new version's thresholdless hash equals the previous version's, and `regrade` otherwise. A `recompute` copies `raw` and `applies_raw` and computes p and the verdicts under the new thresholds. A `regrade` reads the snapshot and calls System One. Grades of the old version stay. Views read the current version.

**Consequences:** A question edit costs at most 30 calls. A threshold edit costs none. Runs that end during a regrade are graded on the new version.

### Decision 10: Read API and Authorization

**Context:** Grades describe runs. Reading a grade must need what reading the run needs. Route scopes on run paths are empty. The service checks access.

**Decision:** kora-agents serves four reads:

| Endpoint | Returns | Authorization |
| --- | --- | --- |
| `GET /api/v1/runs/{id}/grades` | Per Grader of the run's agent, the run's grade on the newest version that graded it, with its version, answers, question text, model, tokens, cost and state cap | The run access check of `GET /api/v1/runs/{id}` |
| `GET /api/v1/agent-types/{id}/graders` | Each Grader's name, description, `minPassRate`, window counts, `too_large` count and status | `checkRun(at, "read")` |
| `GET /api/v1/agent-types/{id}/graders/{name}` | The spec, the window counts, and per question the failed and uncertain runs of the window | `checkRun(at, "read")` |
| `GET /api/v1/runs?grader=&question=&verdict=` | Runs filtered by a current-version answer verdict | The existing list visibility |

A Grader's status is `passing`, `failing`, `not_enough_runs` or `no_minimum`. The window is the current version's last 30 grades with status `graded`. A Grader without `minPassRate` is `no_minimum` at any run count. A Grader with `minPassRate` and under 15 graded runs is `not_enough_runs`. For a delegated agent the two agent-type endpoints also need `agents:delegated:read`. Their counts include runs other people started. The existing `/api/v1/runs/` and `/api/v1/agent-types/` GET prefix entries in `backend/cmd/kora-agents/main.go` cover the new routes with an empty required scope. The handlers register in `backend/internal/agents/server.go`. The BFF proxies them under `frontend/src/app/api/agents/`.

**Consequences:** A person who can read an agent's runs can read its grades. The runs filter adds a join on `grades` and `grade_answers` to the runs list query. The runs list leaves out terminated runs, which carry `deleted_at`. The "All failed runs for this question" link therefore omits terminated runs, while the Grader page lists them.

### Decision 11: UI Scope and Copy

**Context:** The PRD sets the v1 views. The spec's series views are dropped from v1.

**Decision:** v1 ships the run rail's Grades section, the agent's Grades tab, the Grader page and the Runs tab filter by grade. The layouts follow the Storybook stories `Proposed/Graders/Run page` and `Proposed/Graders/Agent page`. The Grades tab list follows the Triggers delivery list pattern for search, quick filters and paging. The run rail exports `PeopleStack`, `Links`, `RunsOn` and `Spend` for the proposed rail. The proposed files are replaced by real components in the UI change.

Every string is a stored fact or a label for one, in the spec's vocabulary: run, pass, fail, uncertain and Grader. Copy carries no advice, interpretation or invented summary. Digests, bars, grids and statistics are not shown. A Grader under 15 graded runs reads "Not enough runs". An unset `minPassRate` reads "No minimum". A run that has not ended reads "Not graded yet", from the run's state.

**Consequences:** The run strip, the config table, config comparison, question failures and stability views need their own decision later.

### Architecture

```
  run ends (SetRunState / TerminateRun / endRuns)
     │  one transaction: runs row + event_outbox + grade_jobs
     ▼
  grade_jobs ── worker (kora-agents, FOR UPDATE SKIP LOCKED)
     │
     ├── grade_states: snapshot of run_events (written once per run)
     ├── cap tool_result bodies until bytes/4 fits agents.grading.windowTokens
     ├── mint token for grader:<tenant> (identity, service-token)
     ▼
  inference gateway POST /v1/systemone
     │  inference:invoke + model use scope, tenant ceiling
     │  X-Kora-Usage-Id, X-Kora-Cost-USD
     ▼
  grades + grade_answers ──► GET /api/v1/runs/{id}/grades
                             GET /api/v1/agent-types/{id}/graders[/{name}]
                             GET /api/v1/runs?grader=&question=&verdict=
```

### Implementation

The change lands as a stack, bottom to top:

1.  This ADR, the PRD and the proposed Storybook mocks.
2.  `runs.agent_config` at `startClaimed` (Decision 7).
3.  The Grader kind, CEL, the operator kind, the applier, `graders`, `grader_versions` and the version hash (Decisions 1, 2).
4.  System One client types, score criteria as a list, the decision timeout header and the usage headers (Decision 6).
5.  The grading principal and the mint allowlist (Decision 5).
6.  The grading package: state builder, caps, size estimate, hash, p and verdicts, and the window (Decision 4).
7.  The pipeline: enqueue at run end, the worker, snapshots, grades and regrade (Decisions 3, 8, 9).
8.  The read API and the runs filter (Decision 10).
9.  The UI (Decision 11).

---

## Consequences

### Positive

*   Every ended run of an agent with a Grader has a stored verdict per Grader version.
*   A grade can be recomputed from its snapshot after the run's events are gone.
*   Grading spend is attributed to one principal per tenant. The tenant ceiling bounds it.

### Negative

*   kora-agents joins the SERVICE token mint allowlist.
*   Snapshots add storage per graded run.
*   A System One caller can hold a gateway attempt for up to `inferenceGateway.maxDecisionTimeoutSecs`.

### Neutral

*   A Grader grades runs that end after it is applied.
*   `agent_config` is a digest. The views do not show it in v1.
