# Orbit MCP — Platform Management MCP Server

**Status:** Proposed
**Date:** 2026-06-30
**Deciders:** Justin Wilkin, Orbit Core Team
**Technical Story:** [Orbit MCP PRD](../prd/orbit-mcp.md)

---

## Context

The [Orbit MCP PRD](../prd/orbit-mcp.md) calls for the first platform-global MCP server: a deployed, in-cluster MCP server that exposes Orbit's own management surface (agents, runs, policy, budgets, models, triggers, environments, identity) as tools, so an agent can operate the control plane. It is the first concrete consumer of the accepted MCP/tool gateway pillar ([gateway](2026-06-29-mcp-tool-gateway.md), [registration](2026-06-29-mcp-server-registration-and-introspection.md), [OAuth](2026-06-29-mcp-oauth-authentication.md)).

This ADR is the *how*. It is one cohesive server — a single ADR, not a sub-decision monster — covering its deployment shape, transport, the identity model, the tool registry and scope-path mapping, how it reaches the backend services, and how it registers behind the gateway.

### Security framing (this feature touches all three of Orbit's questions)

*Who is the agent? What can it access? How does it connect?* — the Orbit MCP touches each, so the framing is warranted:

- **Identity / access:** the server holds **no standing authority**. It forwards the *caller's* platform token to each backend (passthrough), and the backend enforces the caller's real platform scope. Governance is two existing layers — the gateway's `mcp:orbit:<tool>:use` pre-filter and the downstream service's real scope check (`platform:grants:write`, `agents:types:write`, …) — and the server adds none of its own.
- **Known gap, deliberately deferred:** the platform has **no anti-escalation rule** on grant/role/PAT creation today (`CreateGrant` validates only that scopes exist in the vocabulary). Exposing those *write* tools makes a pre-existing escalation primitive agent-callable. Per the PRD this is a **platform-level concern with its own future ADR**, not solved here; it is recorded in Consequences and Future Work.

## Decision Drivers

- **Don't reinvent the MCP protocol.** Adopt a maintained Go MCP SDK for JSON-RPC, the Streamable HTTP transport, schema, and spec-version tracking — not a hand-rolled server.
- **Build it once, for every Orbit MCP.** Orbit will host more MCP servers over time; the SDK + platform integration (passthrough auth, typed-client wiring, OTel, mounting, tool/scope conventions) belongs in a **shared reusable kit**, so each new MCP is just its tools — not a re-implementation.
- **Reuse the platform service template** — binary, config, server, typed clients, OTel — exactly as inference-gateway/policy-gateway do. The Orbit MCP is another service instance.
- **No standing authority** — the server must never be a privileged actor; passthrough keeps every action bounded to the caller's own grants and makes pre-gateway standalone testing safe.
- **Convention compliance** — feature code uses typed platform clients (no raw `http.Client`), `config.LoadService`, injected logging.
- **Clean scope mapping** — one tool per operation, tool names mapping to grantable, verb-terminated, prefix-coverable scopes.

## Considered Options

### Decision 1 — MCP framework (don't hand-roll)

- **Option A: The official Go MCP SDK, `github.com/modelcontextprotocol/go-sdk` (chosen).** Official, maintained in collaboration with Google, v1.7.0+ (v1.0.0 reached; ~2k dependents), tracks the latest spec. It provides a **Streamable HTTP server transport** (`mcp.NewStreamableHTTPHandler(getServer func(*http.Request) *Server, opts)` — a standard `http.Handler`), an SSE handler, **server middleware** (`AddReceivingMiddleware`/`AddSendingMiddleware`), and **typed tools with JSON schema generated from Go structs**. The `getServer(*http.Request)` hook and receiving-middleware are exactly the seams we need for per-request **passthrough** (pull the caller's token) and OTel.
- **Option B: `github.com/mark3labs/mcp-go`.** Mature community SDK, also supports Streamable HTTP + hooks/middleware + session management. A solid fallback; we prefer the official SDK for longevity and spec-tracking. Recorded as the alternative.
- **Option C: Hand-roll the JSON-RPC/MCP protocol.** Reinvents transport, schema, and spec compatibility for no benefit; rejected for a real multi-tool networked server.

### Decision 2 — A reusable platform MCP kit

- **Option A: A shared `internal/platform/mcp` kit wrapping the SDK + platform integration (chosen).** Orbit will run multiple MCP servers; the cross-cutting glue — building a server from a tool set, the Streamable HTTP handler mounted on the platform `api.Server`, **passthrough plumbing** (extract the caller's bearer token per request → expose it to tool handlers via context so they build caller-scoped typed clients), OTel/structured-logging middleware, and the **tool-name → scope-path convention** — lives once in the kit. A new Orbit MCP then depends on the kit, defines its tools, and registers them. The kit lives in `internal/platform/` (any feature/binary may import it; it imports no feature package — tools are passed *in*).
- **Option B: Put the integration directly in `internal/orbitmcp`.** Works for one server; guarantees the next MCP copy-pastes it. Rejected — the goal is to not duplicate this when the next Orbit MCP is built.

**Scope of the kit:** it targets **gateway-fronted platform MCP servers** — Streamable HTTP, caller token passthrough, scope registration. It is **not** for agent-runtime-internal stdio MCPs (e.g. the sandbox-provisioning server an agent spawns inside its own sandbox); those are a different category — local stdio, no gateway, no passthrough — and out of the kit's scope.

### Decision 3 — Deployment shape

- **Option A: New `cmd/orbit-mcp` binary + thin `internal/orbitmcp` feature package on the kit (chosen).** A first-class in-cluster service with its own config and SPIFFE identity; `internal/orbitmcp` holds only this server's *tools*; the kit does the protocol/transport/auth. The SDK's `StreamableHTTPHandler` is mounted on the platform `api.Server` so the pod still gets the platform's outer server, health endpoint, and observability.
- **Option B: A subcommand/mode of an existing binary.** Couples an independently-deployed, gateway-fronted server to an unrelated service's lifecycle. Rejected.

### Decision 4 — Identity model

- **Option A: Token passthrough (chosen).** The kit's receiving-middleware extracts the caller's bearer token from the inbound request and exposes it via context; each tool's typed clients use a `TokenFunc` that reads it, so every backend call carries the caller's identity. The backend enforces the caller's real scope. The server holds no authority. (PRD-decided; this ADR implements it.)
- **Option B: Brokered service identity.** Rejected in the PRD — makes the server a confused deputy with platform-wide authority.

### Decision 5 — Tool registry & scope-path mapping

One tool per operation. Tool wire-names are **dotted domain paths** — `agents.create`, `policy.grants.create`, `budgets.set_role` — which the [registration ADR](2026-06-29-mcp-server-registration-and-introspection.md)'s introspection maps to a **multi-segment** scope path by splitting on `.`: `agents.create` → `mcp:orbit:agents:create:use` (path `[orbit, agents, create]`). Prefix coverage then yields domain rollups for free: `mcp:orbit:agents:use` covers all agent tools, `mcp:orbit:use` the whole server. Each segment stays within the charset `[a-z0-9_-]`; `.` is only the separator. **This needs a one-line clarification to the registration ADR** (a tool may register at a multi-segment scope path) — native to the policy model (`inference:<family>:<model>:use` already has a 2-segment path), recorded as a follow-up.

### Decision 6 — Backend access

The typed clients live in **`internal/platform/clients/{service}/`** — shared, importable by any feature/binary, never importing each other (no dependency cycles), exactly as the BFF and other services use them. The Orbit MCP **reuses** the existing ones (`agents`, `identity`, `policy`) and, where a service has none yet (inference-gateway, triggers, budgets), **adds the client to `internal/platform/clients/`** so the next Orbit MCP reuses it too — **never** a raw `http.Client` and **never** a client defined inside the feature package. The feature's `clients.go` only *assembles* these shared clients with `TokenFunc = mcp.CallerToken(ctx)`. All target in-cluster DNS (`orbit-policy-service.orbit-system`, etc.). The handful of **BFF-composition** operations (scope-filtered model list, user-enriched principal analytics) are replicated by composing the same backend calls inside the relevant tool handler; MVP may return the raw backend response where the composition is a pure UI nicety.

## Architecture

### Packages

```
backend/internal/platform/mcp/        # the reusable kit (imports no feature package)
  server.go        # Build(opts, tools…) → wraps an SDK *mcp.Server
  http.go          # Mount(mux, server): NewStreamableHTTPHandler + getServer hook
  passthrough.go   # receiving-middleware: caller bearer → ctx;  CallerToken(ctx) string
  observe.go       # OTel span + structured log per tool call (SDK middleware)
  scope.go         # dotted tool-name ↔ mcp:<server>:<path>:use convention helpers

backend/internal/orbitmcp/            # THIS server: tools only
  register.go      # registers the tool set onto a kit server
  tools_agents.go  tools_policy.go  tools_budgets.go  tools_*.go
  clients.go       # ASSEMBLES the shared internal/platform/clients/* with
                   # TokenFunc = mcp.CallerToken(ctx) into a Clients struct
                   # (does NOT define clients — those are platform-shared)

backend/cmd/orbit-mcp/
  main.go          # init observability/logger/config; kit.Build + orbitmcp.Register; mount on api.Server; run
  config/base.yaml # backend service URLs, port, service name
```

The binary mirrors the inference-gateway `init*` sequence and loads config via `config.MustLoadService[Config]`. A second Orbit MCP would add only its own `internal/<x>mcp` tools package + `cmd/<x>-mcp` wiring — the kit is unchanged.

### Tool contract (official SDK typed tools)

Tools are the SDK's typed handlers — input/output Go structs with JSON schema generated automatically; no hand-written schema maps:

```go
type CreateAgentIn struct {
    Name  string `json:"name"  jsonschema:"the agent display name"`
    Slug  string `json:"slug"  jsonschema:"unique slug within the tenant"`
    Model string `json:"model,omitempty"`
}

func registerAgentTools(s *mcp.Server, c *Clients) {
    mcp.AddTool(s, &mcp.Tool{Name: "agents.create", Description: "Create an agent type."},
        func(ctx context.Context, _ *mcp.CallToolRequest, in CreateAgentIn) (*mcp.CallToolResult, any, error) {
            // c.Agents is built with TokenFunc = mcpkit.CallerToken(ctx): the call
            // carries the CALLER's token; orbit-agents enforces agents:types:write.
            return c.Agents.CreateAgentType(ctx, in)  // → MCP text result
        })
}
```

The handler never authorises — it executes against a caller-scoped client and reports. The kit's passthrough middleware put the caller's token in `ctx`; `CallerToken(ctx)` feeds the client `TokenFunc`.

### Request lifecycle

```
 agent / human MCP client
   └─(Streamable HTTP, caller's token)─▶ gateway ──▶ orbit-mcp (SDK StreamableHTTPHandler)
        1. kit receiving-middleware: caller bearer + claims → ctx        (no authz here)
        2. SDK dispatch: initialize | tools/list | tools/call
        3. tools/call → typed tool handler(ctx, in)
        4. handler → typed client (TokenFunc = CallerToken(ctx)) → backend service
              (Authorization: caller's token)  ──▶ orbit-policy-service / orbit-agents / …
              backend enforces the REAL platform scope (platform:grants:write, …)
        5. SDK marshals the result; errors become MCP isError
```

The gateway has already filtered `tools/list` and checked `mcp:orbit:<…>:use` before the request arrives; step 4's backend check is the authoritative gate.

### Scope-path mapping (Decision 5)

| Tool wire-name | Registered scope | Rolled up by |
|---|---|---|
| `agents.create` | `mcp:orbit:agents:create:use` | `mcp:orbit:agents:use`, `mcp:orbit:use` |
| `policy.grants.create` | `mcp:orbit:policy:grants:create:use` | `mcp:orbit:policy:grants:use`, `mcp:orbit:policy:use`, … |
| `budgets.set_role` | `mcp:orbit:budgets:set_role:use` | `mcp:orbit:budgets:use`, `mcp:orbit:use` |

Read-only vs read-write is **not** a path level, so a "read-only analyst" grant is a **role** bundling the read scopes, not a single prefix. Using a write tool requires both the `mcp:orbit:…:use` grant *and* the underlying platform scope (`platform:grants:write`, `agents:types:write`, …) — bundled via roles (PRD governance section).

```yaml
# cmd/orbit-mcp/config/base.yaml

  policyURL:    http://orbit-policy-service.orbit-system:8083
  agentsURL:    http://orbit-agents.orbit-system:8080
```

### Registration as a global server

A global `MCPServer` CR in `orbit-system` (per the [registration ADR](2026-06-29-mcp-server-registration-and-introspection.md)) points at the in-mesh endpoint; introspection registers its tools as `mcp:orbit:<…>:use` scopes:

```yaml
apiVersion: orbit.io/v1alpha1
kind: MCPServer
metadata: { name: orbit, namespace: orbit-system }   # global → mcp:orbit:… scopes
spec:
  displayName: "Orbit"
  endpoint: http://orbit-mcp.orbit-system:8095/mcp
  transport: streamable-http
```

## Consequences

### Positive

- The control plane becomes agent-operable through one governed server; reuses the service template, typed clients, and the gateway pillar wholesale.
- **No reinvented protocol.** The official SDK carries JSON-RPC, Streamable HTTP, schema generation, and spec-version tracking — we maintain none of it.
- **The kit is a platform investment.** Every future Orbit MCP gets passthrough auth, OTel, mounting, and the scope convention for free; a new MCP is just its tools.
- Passthrough means the server can never exceed the caller — safe to expose the full surface, and safe to exercise standalone (a direct MCP client + a real platform token) before the gateway lands.
- Domain-rollup scopes (`mcp:orbit:agents:use`) make grants manageable despite ~50 tools.

### Negative

- **Escalation primitive made agent-callable.** Grant/role/PAT/budget *write* tools, combined with the platform's missing anti-escalation rule, let a caller holding `platform:grants:write` escalate. Bounded (passthrough requires that scope to begin with) but real — admins must grant the access-control write scopes deliberately. **Fix is a separate future platform ADR.**
- **Dual-grant.** Using a tool needs both the `mcp:orbit:…:use` and the underlying platform scope; operators must bundle them via roles or hit "passes gateway, denied downstream."
- **Recursion surface.** `runs.start`/`runs.send_message` can re-enter the MCP; MVP relies on the caller's budget grants as the backstop.
- A registration-ADR clarification (multi-segment tool paths) is required before introspection registers Orbit MCP scopes as designed.
- **A new third-party dependency** (`modelcontextprotocol/go-sdk`) enters `go.mod` — official and widely used, but a supply-chain surface to track (pin + review like any dependency).

### Neutral

- ~50 one-per-operation tools is a large registry; grouped per domain file, filtered to the caller's granted subset by the gateway.
- The 2 BFF-composition tools carry a little join logic the dashboard also has.
- The kit is a thin wrapper, not a framework — it owns the platform seams (auth, OTel, mounting, scope naming) and delegates the protocol to the SDK.

## Implementation (phased)

1. **The kit (`internal/platform/mcp`).** Wrap the SDK: `Build` a server from tools, `Mount` its `StreamableHTTPHandler` on the platform `api.Server`, the passthrough receiving-middleware + `CallerToken(ctx)`, OTel/logging middleware, and the dotted-name → scope-path helpers. Cover with unit tests — it's reused.
2. **Server skeleton.** `cmd/orbit-mcp` + `internal/orbitmcp`: config, kit wiring, caller-scoped `Clients`, and one read tool end-to-end.
3. **Read surface.** All observe tools across the domains (+ read-only connections catalog & MCP registry); add missing typed clients.
4. **Write surface.** Create/update/delete/start tools; destructive ops clearly marked in descriptions.
5. **Registration & deploy.** Helm/manifests; the global `MCPServer` CR; verify introspection registers `mcp:orbit:<…>:use` and the gateway governs end-to-end.

`make check` must pass at each step.

## Future Work

- **Anti-escalation rule** (can't grant/mint scopes you don't hold) — its own platform-level ADR; a hard prerequisite to *safely* granting the access-control write tools widely.
- **Run event streaming / live triage** — once the event spine is architected.
- **Recursion guardrail** — a depth/budget limit for run-starting tools.
- **Mutation of infra-driven domains** (connections, tenant config) — pending their own designs.
