# Chat Page

**Status:** Accepted  
**Date:** 2026-11-26  
**Deciders:** Justin Wilkin  
**Technical Story:** [Chat Page PRD](../prd/chat-page.md)

---

## Context

The chat page starts a run with any agent the viewer can run and then shows that run in the run page's own frame. It replaces the Start run modal and the chat demo.

The console starts runs in these places today:

*   `StartRunModal` (`frontend/src/app/(dashboard)/agents/_components/start-run-modal.tsx`) takes an agent and a task, calls `fetchStartRun` and shows `DelegatedRunNotice` for a delegated agent.
*   `agents-page.tsx` opens the modal from the "New Run" button with an agent `NativeSelect`, and from each row's and card's run action with the agent set.
*   `agent-detail-page.tsx` opens the modal from the "Start Run" button and from `AgentRunsTab`'s `onStartRun`.
*   On success each caller runs `router.push(APP_ROUTES.agents.run(slug, runId))`.
*   The Runs tab's "Start work" button links to `APP_ROUTES.chat` (`frontend/src/app/(dashboard)/runs/_components/runs-page.tsx`).

`APP_ROUTES.chat` is `/chat` (`frontend/src/lib/routing/routes.ts`). The page at `frontend/src/app/(dashboard)/chat/page.tsx` is a demo with canned replies, a fixed `MODELS` list and suggestion chips, and it starts no run. `PageGutter` (`frontend/src/app/(dashboard)/_components/page-gutter.tsx`) leaves `/chat` unpadded.

The run page lives in the `(chat)` route group. `frontend/src/app/(chat)/layout.tsx` renders its children only. The run route's own `layout.tsx` provides `PermissionsProvider` and the full-viewport frame. `RunShell` mounts `RunProvider` and `RunPage`. `RunPage` draws `SessionsPane` in the left pane at the `wide` layout and in a drawer below it (`layoutFor` in `_lib/run-layout.ts`). `SessionsPane` reads `from=runs` and a `runs` query, and only that value changes its back link, whose path is fixed.

The run page titles a run with `run.summary` and falls back to `"<Agent> run"` (`toRunView` in `_lib/to-run-view.ts`). `earlierRunsOf` labels other runs with `summary` and falls back to `Run <first 8 characters of the id>`.

The data the page needs exists:

*   `fetchAgentTypes` (`frontend/src/app/(dashboard)/agents/_services/agents-api.ts`) returns each agent with `canRun`, mapped from `can_run`. `setCallerAccess` (`backend/internal/agents/agent_type_service.go`) sets `can_run` from `checkRun`, the run-start check.
*   `GET /api/v1/runs` refuses any `created_by` value other than `me` (`backend/internal/agents/run_page.go`), and the BFF route `frontend/src/app/api/agents/runs/route.ts` passes it through `pickRunsPageParams` (`frontend/src/server/services/runs-server.ts`).
*   Each list row carries `agent_slug` and no message text.
*   `fetchStartRun` posts the task to `POST /api/agents/types/{typeId}/runs`. The BFF route sends it to `POST /api/v1/runs` as `initial_message`, and `StartRun` (`backend/internal/agents/run_service.go`) records it as the run's first `human_message` with the starter as sender.

Hades has `Popover`, `Input`, `NativeSelect` and `InlineSelect`, and no combobox and no motion primitive. `cmdk` is not a frontend dependency. `ModelPicker` (`frontend/src/components/model-picker.tsx`) shows a filter box above 8 models. `BrandLogo` renders the theme's whole logo, and `frontend/src/app/icon.svg` holds the product mark.

### Security and Identity

The change touches none of the three questions. The page starts runs through the same BFF route and `StartRun` call as the modal. `checkRun` passes the agent's creator and otherwise requires `agents:runs:<slug>:write`, or `agents:runs:delegated:write` for a delegated agent. `can_run` only disables an agent in the picker. `StartRun` takes `created_by` from the verified token, and a delegated agent acts as the starter within the delegator's access. "Your runs" reads `GET /api/v1/runs` with its existing visibility, and `created_by=me` compares against the caller's verified subject. The page adds no identity, grant, scope, credential or endpoint.

### Goals

*   Start a run of any agent the viewer can run from `/chat`.
*   Show the started run in the run page's frame without a reload.
*   Keep the viewer's own runs beside the run, also after a reload.
*   Make `/chat` the only start surface in the console.

### Non-Goals

*   Backend or API changes.
*   Repository or model selection.
*   Live updates to "Your runs".
*   Moving `ModelPicker` to the new combobox.

---

## Decision Drivers

*   **One frame:** The new run must look like the run page and reuse its pane, reading column and composer.
*   **No reload:** The browser must not reload between the first message and the run's thread, and the composer must move to its new place without a jump.
*   **Router-safe:** After a start, "New run", the run's links and Back must behave as they do on any run page.
*   **Reload-safe:** A reload or a copied address must open the same run with the same pane.
*   **Hades only:** Product JSX must use Hades, and a missing primitive is added to Hades.

---

## Decision 1: Route and Layout

`/chat` moves to `frontend/src/app/(chat)/chat/page.tsx`. The page reads `agent` from its search parameters and passes it to `ChatPage`.

*   `frontend/src/app/(chat)/layout.tsx` provides `PermissionsProvider` and the full-viewport `Stack`. The run route's `layout.tsx` is deleted.
*   `frontend/src/app/(dashboard)/chat/` is deleted with `page.tsx`, `_components/message-content.tsx` and `chat-page.stories.tsx`.
*   `PageGutter` pads every dashboard page and drops its `/chat` case, and `page-gutter.test.tsx` drops the matching test.
*   The page's components live in `frontend/src/app/(chat)/chat/_components/` as Tier 3 code.

---

## Decision 2: Entry Points

`APP_ROUTES` gains `chatWith(slug)` for `/chat?agent=<slug>`.

*   The Runs tab's "Start work" keeps its link to `APP_ROUTES.chat`.
*   The Agents list's "New Run" button opens `APP_ROUTES.chat`.
*   Each row's and card's run action on the Agents list opens `APP_ROUTES.chatWith(slug)`.
*   The agent page's "Start Run" button and `AgentRunsTab`'s start action open `APP_ROUTES.chatWith(slug)`.
*   `StartRunModal` and `start-run-modal.tsx` are deleted, and `DelegatedRunNotice` stays for `AgentRunsTab`.

### Option 2A (chosen): One page for every start

Every start action opens `/chat`, and `agent` selects the agent.

### Option 2B (rejected): Keep the modal beside the page

The Agents list and the agent page would keep `StartRunModal`. The console would keep two start surfaces with different agent pickers.

---

## Decision 3: Agents and the Selected Agent

`useActiveAgents` (`_hooks/use-active-agents.ts`) calls `fetchAgentTypes` and keeps the agents whose `state` is `active`. `selectAgent` (`_lib/select-agent.ts`) picks the agent once the agents and "Your runs" have loaded.

*   An agent with `canRun` false shows disabled with "No access".
*   An `agent` query selects that agent when the list holds it. An agent with `canRun` false is selected too, and the composer is disabled.
*   Without a matching `agent` query, the page selects the agent of the newest run in "Your runs" when that agent has `canRun`. Otherwise it selects the first agent with `canRun`.
*   With no agent that has `canRun`, the page selects the first agent and disables the composer.
*   With no active agent, the page shows `EmptyState` with "No agents to start" and a link to `APP_ROUTES.agents.list`.

---

## Decision 4: Your Runs

A `useOwnRuns` hook in `frontend/src/app/(chat)/chat/_hooks/use-own-runs.ts` reads `ApiRoute.runs.list()` with `created_by=me&limit=30` once on mount.

*   `HistoryPane` (`_components/history-pane.tsx`) draws a Home link to `APP_ROUTES.home`, a "New run" row and the runs, inside `PaneFrame`. Beside a run, the "New run" row links to `APP_ROUTES.chat`. On the empty chat page it is the active row and has no link.
*   `SessionsPane` exports `PaneFrame`, `SessionRow`, `BackLink` and `RunSessionRows`, and `SessionRow` takes an `icon` for an action row. Both panes draw their top link and the open run's rows with them.
*   The open run reads as running while it is pending, starting or active, and as done once its state is in `ENDED`.
*   The open run shows first and lists its subagents under it from the run's rows.
*   Each other row links to `APP_ROUTES.agents.chatRun(slug, id)` with the row's `agent_slug`. A row without `agent_slug` has no link.
*   Below the `wide` layout, the empty page opens the pane in a left `SidePanel` from a "Your runs" button, and the run page opens it from the run header's Sessions button.

---

## Decision 5: Starting the Run in Place

### Option 5A (chosen): Replace the page with the run's route and hand over the composer

The page calls `fetchStartRun(agent.id, { task })` and then:

1.  Records the box of its composer frame, its current layout and the runs it loaded with `handOver` (`_lib/hand-over.ts`), keyed by the new run's id.
2.  Calls `router.replace` with `APP_ROUTES.agents.chatRun(slug, id)`, the run's path with `from=chat`.
3.  On the run's route, `ChatRunRoute` reads the hand-over once on mount and passes the box and layout to `RunPage` as `enter`. The handed-over runs fill "Your runs" until its own read returns.

The `(chat)` layout stays mounted across the replace. The composer stays in its sending state until the run page replaces it. A failed or thrown start keeps the text in the composer and shows the error under it with `role="alert"`. A start that returns after the viewer left the page records no hand-over and does not navigate.

### Option 5B (rejected): Swap in the run page and change the URL with `replaceState`

The page would mount `RunPage` in place and call `window.history.replaceState` with the run's path. The router would keep the `/chat` tree under the run's address. "New run" would leave the run on screen, and Back to the run would show an empty chat page.

### Option 5C (rejected): Keep the `/chat` URL

The page would show the run under `/chat`. A reload or a copied address would open an empty chat page.

---

## Decision 6: The Run Page Opened From Chat

`RunPage` takes an optional `pane` of type `RunPaneSlot` and an optional `enter`. The slot receives the run, its rows and the drawer flag, and without it `RunPage` draws `SessionsPane`.

*   The run route's `page.tsx` reads `from` from its search parameters and passes `fromChat` to `RunShell` when the value is `chat`.
*   Under `fromChat`, `RunShell` renders `ChatRunRoute` to draw `HistoryPane` in the pane from its own `useOwnRuns` call. A reloaded run has no hand-over and no move. Every link in the pane has a fixed path.
*   `from=runs` keeps its behavior in `SessionsPane`.

---

## Decision 7: Run Title Before a Summary

`toRunView` sets the title to `run.summary`. Without a summary, a run whose record has no `started_by` takes the first non-empty line of its first `human_message`, cut at a word to 60 characters with an ellipsis. When the word cut would keep less than 30 characters (e.g., a URL after a short word), the line is cut at 60 characters mid-token. Every other run falls back to `"<Agent> run"`. The open run's row in `HistoryPane` uses the same title. Other rows keep the `earlierRunsOf` label.

---

## Decision 8: The Composer's Move

`Composer` takes `enterFrom`, the box of the chat page's composer frame. On mount it animates its own frame from that box's left and bottom edges to its place with the Web Animations API. The move takes 280 ms (`COMPOSER_MOVE_MS` in `_lib/run-styles.ts`) with the easing `cubic-bezier(0.2, 0.8, 0.2, 1)`. Hades exports that easing as `SETTLE_EASING` beside `Reveal`. `RunPage` starts in the layout from `enter`, and the frame measures its final place on mount. Under `prefers-reduced-motion: reduce` the frame takes its place with no animation.

---

## Decision 9: Agent Picker on a Hades Combobox

Hades gains `Combobox`, `ComboboxInput`, `ComboboxList`, `ComboboxItem` and `ComboboxEmpty` in `frontend/src/packages/hades/src/components/combobox/`. They are built on `cmdk` and exported from `src/index.ts`. The default filter keeps the list's order and keeps each item whose value or keywords contain the search, ignoring case.

*   The agent picker opens the combobox in a `Popover` from a ghost `Button` in the composer footer, where the run composer has no control.
*   Each `ComboboxItem` has the agent's slug as its value and its name and description as keywords.
*   `ComboboxInput` shows from 8 agents up. Without it, the picker focuses the `ComboboxList` on open to make the arrow keys work.
*   `ComboboxItem` renders an agent with `canRun` false as disabled.
*   `ModelPicker` shows its filter box from 8 models up as well, and can move to the combobox in a later change.
*   Without an input, `Combobox` hides the label cmdk renders for one.

### Option 9A (chosen): A cmdk combobox in Hades

The combobox follows the listbox pattern that `cmdk` implements.

### Option 9B (rejected): Popover with an input and a list of buttons

Each agent would render as a `Button` with `aria-pressed` under an `Input`. The list would have no arrow-key navigation and no listbox semantics.

---

## Decision 10: Heading Reveal

Hades gains `Reveal` in `frontend/src/packages/hades/src/components/reveal/`. It plays once on mount and animates each child in order from 0.4em below and transparent to its place.

*   `stagger`, `duration` and `delay` take milliseconds and set the gap between children, each child's time and the first child's start.
*   Under `prefers-reduced-motion: reduce` it renders its children in their final state.
*   It adds no ARIA attributes. The heading's words stay inside one `Heading`, and screen readers read it once.

The page code in `_components/heading-reveal.tsx` draws the disc and its motion: a 360 ms drop and a 280 ms split, after which the disc is the mark. The words start with the split, take 280 ms each, and the last lands 600 ms after the first starts. The name is the last word, and the page draws the heading once the session has loaded.

### Option 10A (chosen): A one-shot Hades primitive for the words

The word reveal is a Hades primitive, and the disc stays in page code.

### Option 10B (rejected): All motion in page code

The page would animate the words itself. The stagger and the reduced-motion rule would live in one page, and another page that reveals text would copy them.

---

## Decision 11: The Heading Mark

The page draws the product mark from the geometry of `frontend/src/app/icon.svg`: two half-discs in `--color-foreground` and `--color-border-accent`. The mark has `aria-hidden`. No theme field or tenant logo changes it.

### Option 11A (chosen): The product's fixed mark

The mark is drawn in page code and is the same on every tenant.

### Option 11B (rejected): Crop the tenant logo

The heading would crop `BrandLogo` to the default mark's width from the default logo's geometry. A tenant logo with another shape would be cropped at the wrong point.

### Option 11C (rejected): A mark field on the theme

Each tenant theme would supply its own mark. PD8 keeps the product mark on every tenant, and the field would add a theme surface that nothing else reads.

None at this time.

## Consequences

### Positive

*   The console has one start surface, and every start shows the agent's description and who the run acts as.
*   `Combobox` and `Reveal` are available to other pages.

### Negative

*   `DelegatedRunNotice` no longer shows before a delegated run starts.
*   A start from the agent page leaves the agent page.
*   `cmdk` joins the frontend dependencies and the Hades peer dependencies.
*   "Your runs" holds the 30 newest runs, has no paging and does not update live.
*   `RunShell` depends on `ChatRunRoute`, `HistoryPane` and `useOwnRuns` in the chat page's folder.
*   The hand-over lives in module state on the client. A hand-over whose run route never mounts stays in memory until the tab closes.
*   The run route's first render waits for its server response after the start.

### Neutral

*   After the demo's removal, `ChatBubble`, `ChatBubbleActions`, `TypingIndicator` and `InputSurface` have no consumer in the app.
*   A run opened without `from=chat` keeps `SessionsPane`.

---

## Implementation

1.  **Hades:** Add `Combobox` on `cmdk` and `Reveal`, each with stories and tests.
2.  **Run page:** Add the `pane` and `enter` props to `RunPage` and `enterFrom` to `Composer`, export `PaneFrame` and `SessionRow`, and pass `fromChat` from the run route to `RunShell`. Change the title fallback in `toRunView`.
3.  **Chat page:** Move the layout into `(chat)/layout.tsx`, add `(chat)/chat/page.tsx` with `HistoryPane`, `useOwnRuns`, the agent picker, the heading and the hand-over, and add the `Pages/Chat` stories.
4.  **Entry points:** Add `APP_ROUTES.chatWith` and `APP_ROUTES.agents.chatRun`, point the Agents list and the agent page at `/chat`, and delete `StartRunModal`, the demo and the `PageGutter` case.
