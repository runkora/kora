# kora MCP — Platform Management MCP Server

<!-- Filename: 2026-06-30-orbit-mcp.md -->

**Status:** Accepted
**Date:** 2026-06-30
**Deciders:** Justin Wilkin, kora Core Team
**Technical Story:** [kora MCP PRD](../prd/orbit-mcp.md)

---

## Context

The [kora MCP PRD](../prd/orbit-mcp.md) calls for the first platform-global MCP server: a deployed, in-cluster MCP server that exposes kora's own management surface (agents, runs, policy, budgets, models, triggers, environments, identity) as tools, so an agent can operate the control plane. It is the first concrete consumer of the accepted MCP/tool gateway pillar ([gateway](2026-06-29-mcp-tool-gateway.md), [registration](2026-06-29-mcp-server-registration-and-introspection.md), [OAuth](2026-06-29-mcp-oauth-authentication.md)).

This ADR is the *how*. It is one cohesive server — a single ADR, not a sub-decision monster — covering its deployment shape, transport, the identity model, the tool registry and scope-path mapping, how it reaches the backend services, and how it registers behind the gateway.

### Security framing (this feature touches all three of kora's questions)

*Who is the agent? What can it access? How does it connect?* — the kora MCP touches each, so the framing is warranted:

- **Identity / access:** the server holds **no standing authority**. It forwards the *caller's* platform token to each backend (passthrough), and the backend enforces the caller's real platform scope. For a delegated run it also forwards the run's delegation token ([delegated-agent-identity](2026-07-23-delegated-agent-identity.md), Decision 4). Governance is two existing layers — the gateway's `mcp:orbit:<tool>:use` pre-filter and the downstream service's real scope check (`platform:grants:write`, `agents:types:write`, …) — and the server adds none of its own.
- **Known gap, deliberately deferred:** the platform has **no anti-escalation rule** on grant/role/PAT creation today (`CreateGrant` validates only that scopes exist in the vocabulary). Exposing those *write* tools makes a pre-existing escalation primitive agent-callable. Per the PRD this is a **platform-level concern with its own future ADR**, not solved here; it is recorded in Consequences and Future Work.

## Decision Drivers

- **Don't reinvent the MCP protocol.** Adopt a maintained Go MCP SDK for JSON-RPC, the Streamable HTTP transport, schema, and spec-version tracking — not a hand-rolled server.
- **Build it once, for every kora MCP.** kora will host more MCP servers over time; the SDK + platform integration (passthrough auth, typed-client wiring, OTel, mounting, tool/scope conventions) belongs in a **shared reusable kit**, so each new MCP is just its tools — not a re-implementation.
- **Reuse the platform service template** — binary, config, server, typed clients, OTel — exactly as inference-gateway/policy-gateway do. The kora MCP is another service instance.
- **No standing authority** — the server must never be a privileged actor; passthrough keeps every action bounded to the caller's own grants and makes pre-gateway standalone testing safe.
- **Convention compliance** — feature code uses typed platform clients (no raw `http.Client`), `config.LoadService`, injected logging.
- **Clean scope mapping** — one tool per operation, tool names mapping to grantable, verb-terminated, prefix-coverable scopes.

## Considered Options

### Decision 1 — MCP framework (don't hand-roll)

- **Option A: The official Go MCP SDK, `github.com/modelcontextprotocol/go-sdk` (chosen).** Official, maintained in collaboration with Google, v1.7.0+ (v1.0.0 reached; ~2k dependents), tracks the latest spec. It provides a **Streamable HTTP server transport** (`mcp.NewStreamableHTTPHandler(getServer func(*http.Request) *Server, opts)` — a standard `http.Handler`), an SSE handler, **server middleware** (`AddReceivingMiddleware`/`AddSendingMiddleware`), and **typed tools with JSON schema generated from Go structs**. The `getServer(*http.Request)` hook and receiving-middleware are exactly the seams we need for per-request **passthrough** (pull the caller's token) and OTel.
- **Option B: `github.com/mark3labs/mcp-go`.** Mature community SDK, also supports Streamable HTTP + hooks/middleware + session management. A solid fallback; we prefer the official SDK for longevity and spec-tracking. Recorded as the alternative.
- **Option C: Hand-roll the JSON-RPC/MCP protocol.** Reinvents transport, schema, and spec compatibility for no benefit; rejected for a real multi-tool networked server.

### Decision 2 — A reusable platform MCP kit

- **Option A: A shared `internal/platform/mcp` kit wrapping the SDK + platform integration (chosen).** kora will run multiple MCP servers; the cross-cutting glue — building a server from a tool set, the Streamable HTTP handler mounted on the platform `api.Server`, **passthrough plumbing** (extract the caller's bearer token per request → expose it to tool handlers via context so they build caller-scoped typed clients), OTel/structured-logging middleware, and the **tool-name → scope-path convention** — lives once in the kit. A new kora MCP then depends on the kit, defines its tools, and registers them. The kit lives in `internal/platform/` (any feature/binary may import it; it imports no feature package — tools are passed *in*).
- **Option B: Put the integration directly in `internal/koramcp`.** Works for one server; guarantees the next MCP copy-pastes it. Rejected — the goal is to not duplicate this when the next kora MCP is built.

**Scope of the kit:** it targets **gateway-fronted platform MCP servers** — Streamable HTTP, caller token passthrough, scope registration. It is **not** for agent-runtime-internal stdio MCPs (e.g. the sandbox-provisioning server an agent spawns inside its own sandbox); those are a different category — local stdio, no gateway, no passthrough — and out of the kit's scope.

### Decision 3 — Deployment shape

- **Option A: New `cmd/kora-mcp` binary + thin `internal/koramcp` feature package on the kit (chosen).** A first-class in-cluster service with its own config and SPIFFE identity; `internal/koramcp` holds only this server's *tools*; the kit does the protocol/transport/auth. The SDK's `StreamableHTTPHandler` is mounted on the platform `api.Server` so the pod still gets the platform's outer server, health endpoint, and observability.
- **Option B: A subcommand/mode of an existing binary.** Couples an independently-deployed, gateway-fronted server to an unrelated service's lifecycle. Rejected.

**Mount caveat (verified):** the mounted handler inherits the controller's `Middleware()` and the global `defaultMiddleware`. So the kit mounts the SDK handler under a thin Controller whose middleware does **token extraction only — no `ScopeEnforcementMiddleware`** (the gateway pre-filter and the downstream service own authorisation; a Layer-1 sidecar gate may still front the pod), and the kit must ensure `defaultMiddleware` does not buffer/transform the request or response body in a way that breaks streaming JSON-RPC. Both are pinned in the kit's `Mount` implementation.

### Decision 4 — Identity model

- **Option A: Token passthrough (chosen).** The kit's receiving-middleware extracts the caller's bearer token from the inbound request and exposes it via context; each tool's typed clients use a `TokenFunc` that reads it, so every backend call carries the caller's identity. The backend enforces the caller's real scope. The server holds no authority. (PRD-decided; this ADR implements it.)

**Hard dependency — the gateway must convey the caller's token to this server, and it does *not* do so by default.** The caller's full-power `aud=orbit-platform` token is *not* forwarded to upstream MCP servers in general (that would leak a replayable kora credential to third-party servers — the gateway's secure default). The kora MCP is the **acting-as-caller exception**: it must be registered with **`spec.callerIdentity: forward`** on its `MCPServer` CR ([registration ADR](2026-06-29-mcp-server-registration-and-introspection.md)), which is the *only* thing that makes the gateway forward the caller's bearer to it ([gateway ADR](2026-06-29-mcp-tool-gateway.md), Decision 4). This is permitted precisely because the kora MCP is a **global `orbit-system` server** kora applies itself — `forward` is **enforced global-only** (a tenant CR requesting it is rejected at reconcile), so it cannot be used as a token-harvesting vector by a tenant. Without that flag the passthrough model does not hold and the server would collapse to the rejected brokered model — so the flag is a **required cross-ADR dependency**, not an assumption. (In **standalone/dev** mode the token arrives directly from the MCP client with no gateway hop, which is why standalone works without the flag — and why it must not mask the production requirement.)
- **Option B: Brokered service identity.** Rejected in the PRD — makes the server a confused deputy with platform-wide authority.

### Decision 5 — Tool registry & scope-path mapping

One tool per operation. Tool wire-names are **dotted domain paths** — `agents.create`, `policy.grants.create`, `budgets.set_role` — which the [registration ADR](2026-06-29-mcp-server-registration-and-introspection.md)'s introspection maps to a **multi-segment** scope path by splitting on `.`: `agents.create` → `mcp:orbit:agents:create:use` (path `[orbit, agents, create]`). Prefix coverage then yields domain rollups for free: `mcp:orbit:agents:use` covers all agent tools, `mcp:orbit:use` the whole server. Each segment stays within the charset `[a-z0-9_-]`; `.` is only the separator. **This requires the registration ADR's multi-segment-tool-path amendment** — it changes the shared introspection derivation (split tool names on a reserved `.` delimiter; charset applies per-segment; non-dotted names register single-segment as today; the split is universal across all servers). That is a real, listed **dependency**, not a clarification — confirmed and added to the registration ADR (Decision 5, Amendment 2026-06-30).

### Decision 6 — Backend access

The typed clients live in **`internal/platform/clients/{service}/`** — shared, importable by any feature/binary, never importing each other (no dependency cycles), exactly as the BFF and other services use them. The kora MCP **reuses** the existing ones (`agents`, `identity`, `policy`) and, where a service has none yet (inference-gateway, triggers, budgets), **adds the client to `internal/platform/clients/`** so the next kora MCP reuses it too — **never** a raw `http.Client` and **never** a client defined inside the feature package. The feature's `clients.go` only *assembles* these shared clients with `TokenFunc = mcp.CallerToken(ctx)`. All target in-cluster DNS (`orbit-policy-service.orbit-system`, etc.). The handful of **BFF-composition** operations (scope-filtered model list, user-enriched principal analytics) are replicated by composing the same backend calls inside the relevant tool handler; MVP may return the raw backend response where the composition is a pure UI nicety.

## Architecture

### Packages

```
backend/internal/platform/mcp/        # the reusable kit (imports no feature package)
  server.go        # Build(opts, tools…) → wraps an SDK *mcp.Server
  http.go          # Mount(mux, server): NewStreamableHTTPHandler + getServer hook,
                   # under a thin Controller whose Middleware() does token-extraction
                   # ONLY — no ScopeEnforcementMiddleware (gateway + downstream own authz)
  passthrough.go   # receiving-middleware: caller bearer → ctx;  CallerToken(ctx) string
  observe.go       # OTel span + structured log per tool call (SDK middleware)
  scope.go         # dotted tool-name ↔ mcp:<server>:<path>:use convention helpers

backend/internal/koramcp/            # THIS server: tools only
  register.go      # registers the tool set onto a kit server
  tools_agents.go  tools_policy.go  tools_budgets.go  tools_*.go
  clients.go       # ASSEMBLES the shared internal/platform/clients/* with
                   # TokenFunc = mcp.CallerToken(ctx) into a Clients struct
                   # (does NOT define clients — those are platform-shared)

backend/cmd/kora-mcp/
  main.go          # init observability/logger/config; kit.Build + koramcp.Register; mount on api.Server; run
  config/base.yaml # backend service URLs, port, service name
```

The binary mirrors the inference-gateway `init*` sequence and loads config via `config.MustLoadService[Config]`. A second kora MCP would add only its own `internal/<x>mcp` tools package + `cmd/<x>-mcp` wiring — the kit is unchanged.

### Tool contract (official SDK typed tools)

Tools are the SDK's typed handlers — input/output Go structs with JSON schema generated automatically; no hand-written schema maps:

```go
type CreateAgentIn struct {
    Name  string `json:"name"  jsonschema:"the agent display name"`
    Slug  string `json:"slug"  jsonschema:"unique slug within the tenant"`
    Model string `json:"model,omitempty"`
}

func registerAgentTools(s *mcp.Server, c *Clients) {
    mcp.AddTool(s, &mcp.Tool{Name: "agents.create", Description: "Create an agent type."},
        func(ctx context.Context, _ *mcp.CallToolRequest, in CreateAgentIn) (*mcp.CallToolResult, any, error) {
            // c.Agents is built with TokenFunc = mcpkit.CallerToken(ctx): the call
            // carries the CALLER's token; orbit-agents enforces agents:types:write.
            return c.Agents.CreateAgentType(ctx, in)  // → MCP text result
        })
}
```

The handler never authorises — it executes against a caller-scoped client and reports. The kit's passthrough middleware put the caller's token in `ctx`; `CallerToken(ctx)` feeds the client `TokenFunc`.

### Request lifecycle

```
 agent / human MCP client
   └─(Streamable HTTP, caller's token)─▶ gateway ──▶ orbit-mcp (SDK StreamableHTTPHandler)
        1. kit receiving-middleware: caller bearer + claims → ctx        (no authz here)
        2. SDK dispatch: initialize | tools/list | tools/call
        3. tools/call → typed tool handler(ctx, in)
        4. handler → typed client (TokenFunc = CallerToken(ctx)) → backend service
              (Authorization: caller's token)  ──▶ orbit-policy-service / orbit-agents / …
              backend enforces the REAL platform scope (platform:grants:write, …)
        5. SDK marshals the result; errors become MCP isError
```

The gateway has already filtered `tools/list` and checked `mcp:orbit:<…>:use` before the request arrives; step 4's backend check is the authoritative gate.

### Scope-path mapping (Decision 5)

| Tool wire-name | Registered scope | Rolled up by |
|---|---|---|
| `agents.create` | `mcp:orbit:agents:create:use` | `mcp:orbit:agents:use`, `mcp:orbit:use` |
| `policy.grants.create` | `mcp:orbit:policy:grants:create:use` | `mcp:orbit:policy:grants:use`, `mcp:orbit:policy:use`, … |
| `budgets.set_role` | `mcp:orbit:budgets:set_role:use` | `mcp:orbit:budgets:use`, `mcp:orbit:use` |

Read-only vs read-write is **not** a path level, so a "read-only analyst" grant is a **role** bundling the read scopes, not a single prefix. Using a tool requires both the `mcp:orbit:…:use` grant *and* the caller's own platform scope for the operation (`platform:grants:write`, `agents:types:write`, …). The tool scope confers no platform scope. The platform behind the tool checks the caller's permission.

### Registration as a global server

A global `MCPServer` CR in `orbit-system` (per the [registration ADR](2026-06-29-mcp-server-registration-and-introspection.md)) points at the in-mesh endpoint; introspection registers its tools as `mcp:orbit:<…>:use` scopes:

```yaml

  displayName: "Orbit"
  endpoint: http://orbit-mcp.orbit-system:8095/mcp
  transport: streamable-http
```

## Amendment 2026-07-04 — Full management tool surface

The initial cut shipped 27 tools across four domains (agents, runs, policy grants/roles, `models.list`) — enough to prove the passthrough model but well short of the "operate the control plane" surface the Context sets out. This amendment completes the surface to **66 tools**, adding: the full **model/pricing catalog** (virtual models CRUD, provider models, pricing overrides), **budgets** (tenant cap + per-principal status; grant/role budgets already existed), **environment** CRUD, **PAT** management, **policy vocabulary + route** reads, **identity user** reads, and **triggers** (sources, triggers, deliveries). Each new tool is the same thin passthrough. It forwards the caller's token, and the delegation for a delegated run. No orbit tool declares `requires`: the tool scope lets the caller call the tool, and the platform checks the caller's own permission. Lists the platform filters per item (agents, runs, agent usage) return the filtered result. A platform 403 surfaces from the tool as "You do not have access to <resource>.", never as an empty list or the upstream body.

Two deliberate scope decisions:

- **No PAT creation.** Agents may view, re-scope, and revoke Personal Access Tokens but **must not mint new ones** — a PAT is a long-lived standing credential, and letting an agent create one is a durable privilege-escalation vector. The `POST /identity/tokens` endpoint is simply not exposed as a tool; the other PAT verbs are.
- **Analytics/usage logs deferred.** Usage analytics, per-run spend, and the usage log are **not** exposed, because they depend on the platform event spine, which does not yet exist. They join the surface when the spine ships (this is the same deferral the [tool gateway](2026-06-29-mcp-tool-gateway.md) and event-spine work already carry).

A `TestToolsDeclareNoRequires` invariant test lists the full surface and asserts no tool carries `_meta[orbit/requires]` and every tool names a resource for the no-access error. No leaf/prefix scope collisions (the former leaf `agents.environments` was renamed to `agents.environments.list` so the `agents.environments.*` family rolls up cleanly).

## Consequences

### Positive

- The control plane becomes agent-operable through one governed server; reuses the service template, typed clients, and the gateway pillar wholesale.
- **No reinvented protocol.** The official SDK carries JSON-RPC, Streamable HTTP, schema generation, and spec-version tracking — we maintain none of it.
- **The kit is a platform investment.** Every future kora MCP gets passthrough auth, OTel, mounting, and the scope convention for free; a new MCP is just its tools.
- Passthrough means the server can never exceed the caller — safe to expose the full surface, and safe to exercise standalone (a direct MCP client + a real platform token) before the gateway lands.
- Domain-rollup scopes (`mcp:orbit:agents:use`) make grants manageable despite ~50 tools.

### Negative

- **Escalation primitive made agent-callable.** Grant/role/PAT/budget *write* tools, combined with the platform's missing anti-escalation rule, let a caller holding `platform:grants:write` escalate. Bounded (passthrough requires that scope to begin with) but real — admins must grant the access-control write scopes deliberately. **Fix is a separate future platform ADR.**
- **Dual-grant.** Using a tool needs both the `mcp:orbit:…:use` and the underlying platform scope; operators must bundle them via roles or hit "passes gateway, denied downstream."
- **Recursion surface.** `runs.start`/`runs.send_message` can re-enter the MCP; MVP relies on the caller's budget grants as the backstop.
- The registration-ADR **multi-segment-tool-path amendment** (a change to the shared introspection derivation) is required before introspection registers kora MCP scopes as designed — and the **`spec.callerIdentity: forward`** flag (gateway + registration ADRs) is required before the passthrough identity model holds in production. Both are listed cross-ADR dependencies.
- **A new third-party dependency** (`modelcontextprotocol/go-sdk`) enters `go.mod` — official and widely used, but a supply-chain surface to track (pin + review like any dependency).

### Neutral

- ~50 one-per-operation tools is a large registry; grouped per domain file, filtered to the caller's granted subset by the gateway.
- The 2 BFF-composition tools carry a little join logic the dashboard also has.
- The kit is a thin wrapper, not a framework — it owns the platform seams (auth, OTel, mounting, scope naming) and delegates the protocol to the SDK.

## Implementation (phased)

1. **The kit (`internal/platform/mcp`).** Wrap the SDK: `Build` a server from tools, `Mount` its `StreamableHTTPHandler` on the platform `api.Server`, the passthrough receiving-middleware + `CallerToken(ctx)`, OTel/logging middleware, and the dotted-name → scope-path helpers. Cover with unit tests — it's reused.
2. **Server skeleton.** `cmd/kora-mcp` + `internal/koramcp`: config, kit wiring, caller-scoped `Clients`, and one read tool end-to-end.
3. **Read surface.** All observe tools across the domains (+ read-only connections catalog & MCP registry); add missing typed clients.
4. **Write surface.** Create/update/delete/start tools; destructive ops clearly marked in descriptions.
5. **Registration & deploy.** Helm/manifests; the global `MCPServer` CR; verify introspection registers `mcp:orbit:<…>:use` and the gateway governs end-to-end.

`make check` must pass at each step.

## Future Work

- **Anti-escalation rule** (can't grant/mint scopes you don't hold) — its own platform-level ADR; a hard prerequisite to *safely* granting the access-control write tools widely.
- **Run event streaming / live triage** — once the event spine is architected.
- **Recursion guardrail** — a depth/budget limit for run-starting tools.
- **Mutation of infra-driven domains** (connections, tenant config) — pending their own designs.
