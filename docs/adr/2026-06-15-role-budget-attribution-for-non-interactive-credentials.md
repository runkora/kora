# Role-Budget Attribution for Non-Interactive Credentials

**Status:** Accepted
**Date:** 2026-06-15
**Deciders:** Justin Wilkin, Platform Engineering
**Technical Story:** Role/group budgets neither attribute nor enforce against the credentials that actually drive inference. PATs (Claude Code, scripts) and agent platform tokens carry no OIDC `roles` claim, so every `inference_usage` row records empty `principal_roles`. The budgets dashboard shows every principal as "No budget", the personal usage bar shows `0 / <limit>` for a real spender, and — more seriously — role ceilings silently fail to bind to the traffic they are meant to govern. Diagnosed against the deployed dev tenant (`orbit-dev`): 33 principals, **0** with any role category, while the tenant cap ($236 / $2000) and per-principal spend are correct.

---

## Context

### Background

kora's [hierarchical budget model](2026-06-10-hierarchical-budget-enforcement.md) supports four ceiling scopes: **principal** (grant budgets), **role** (pooled or per-member, keyed on OIDC role/group membership), **tenant** (account rollup), and **run** (per-session). Role budgets are the only scope that depends on *per-request role membership* rather than a stable identifier (`principal_id` / `run_id` / `tenant_id`).

The inference gateway derives a caller's roles from the verified platform JWT at request time (`rolesFromContext` → `claims.Kora.Claims["roles"]`). Two facts collide:

1. **Only interactive browser sessions carry roles.** `ExchangeIDToken` / the login flow merges the IdP's `roles` + `groups` claims into `orbit.claims.roles` on the *session* token (`identity/service.go:406`).
2. **PATs and agent tokens carry no roles.** `CreatePAT` mints a JWT with no `claims` map at all (`identity/pat_service.go:55`, `signToken` at `service.go:962`); the agent SVID-derived platform token likewise has none. The gateway middleware only strips the `orb_` prefix — there is no enrichment.

Effectively no inference flows through browser-session tokens; it flows through PATs and agent identities. So `writeUsage` records `principal_roles = '{}'` on every row, and three things break:

| Surface | Mechanism | Result |
|---|---|---|
| Budgets dashboard, per-principal | `GetActiveRoleHolders` → `unnest(principal_roles)` | empty → no role categories → "No budget" for all |
| Personal usage bar | pooled-role spend via `GetPoolSpendSince` → `role = ANY(principal_roles)` | 0 → shows `0 / <limit>` |
| **Enforcement** | `checkBudget` → `budgetScopesFor` → `rolesFromContext` | no role ceilings resolved → role budgets **do not block** PAT/agent inference |

The scopes that work — tenant rollup (`GetTenantSpendSince`, a SUM over all rows), per-principal spend (`GetMonthlySpendByPrincipal`, GROUP BY `principal_id`), and principal/run enforcement (counters keyed on `principal_id` / `run_id`) — all key off stable identifiers and need no roles. That is exactly why operators observe "session exhausted" enforcement and a correct account rollup while individual role attribution is blank.

### Problem Statement

A person's role/group budget must apply to **all of their inference**, including spend generated by long-lived PATs while the person is not in the platform UI — and those tokens must sum together against the shared role/group ceiling. Today role membership is known only at the instant of an interactive login and is discarded immediately afterward.

There is no durable, queryable answer to: *"What roles does this human currently hold?"* — even though [`user_profiles`](2026-04-19-user-profiles-table-for-principal-attribution.md) already upserts a profile row on **every** federated login. That upsert persists `id`, `email`, `display_name` and deliberately drops `roles` (`userProfileFromPrincipal`, `user_profile_repository.go:164`), and the table has no `roles` column.

### Goals

- Role/group budgets attribute and enforce against PAT-driven inference, summed across all of a principal's tokens.
- Reuse the existing every-login upsert as the source of truth for role membership — no SCIM, no IdP webhooks.
- Keep the inference hot path fast and fail-open (a role-resolution failure must never block inference, consistent with the rest of budget enforcement).
- Keep the cross-service coupling minimal and reversible. (As implemented this is a read-only dependency on the shared `user_profiles` table rather than a new identity endpoint — see [Decision: lookup mechanism](#decision) — but it must stay a single, well-named seam that can be swapped for a typed client if the databases are ever split.)

### Non-Goals

- **Agents are out of scope.** Agent (SPIFFE) principals hold no OIDC roles; role budgets do not apply to them. Their role-based budgeting, if ever desired, needs a separate role-assignment model and its own ADR.
- Real-time role revocation. Membership is refreshed at login; sub-second propagation of an IdP role change is not a goal.
- Reworking the budget ceiling model, OPA policy, or per-request counter increments — this ADR changes *how roles reach the request* and *how role-period spend is summed for the read/rehydrate path*, not what the ceilings mean.
- Re-attributing spend from already-**closed** (past) budget periods. The current open period is in scope and necessary (Decision 5); closed periods are immutable history.

---

## Decision Drivers

* **Roles must never be minted into a PAT (or any long-lived bearer credential) JWT.** *(Ratified constraint, 2026-06-15.)* A bearer token that asserts its own role set freezes a revocable fact into a long-lived secret and moves the source of truth from the platform to the token holder. Role membership is resolved against platform state, never carried by the credential. This eliminates Options 2 and 3 outright.
* **Correctness of governance.** A role ceiling that does not bind to PAT/agent traffic is a silent security/cost gap in a control-plane product.
* **Hot-path latency & resilience.** Inference is latency-sensitive; role resolution must be cached and fail-open.
* **Service boundary discipline.** Features/binaries don't import each other's Go packages. Cross-service reads ideally go through typed `internal/platform/clients/{service}` clients — though all services currently share one database, and the gateway already reads/writes `inference_usage` in it, so a read-only query against `user_profiles` is a pragmatic option that crosses no Go-package boundary (see Decision).
* **Freshness vs. simplicity.** "As of last login" is an explicitly accepted tradeoff; the design should not over-engineer for fresher data than that.
* **Blast radius of turning enforcement on.** Principals have been spending unbounded against role budgets; switching enforcement on is a behavior change.

## Considered Options

The central decision (**Decision 1**) is *where and when a principal's roles are attached to PAT-driven inference*. Four decisions hang off it; they are summarised in [Decisions Required](#decisions-required).

### Option 1: Persisted role snapshot + cached lookup at inference time

**Description:** Extend the existing every-login upsert to store the merged `roles` on `user_profiles`. On the inference path, when the credential carries no roles (PAT) and the principal is HUMAN, the gateway resolves the human's stored roles via a typed `clients/identity` call (short-TTL cached), injects them into the request context, and lets the unchanged downstream (`writeUsage`, `budgetScopesFor`, `checkBudget`) consume them.

**Pros:**
- Single source of truth (the login event), refreshed on every re-login — exactly the "hydrate on re-login" model.
- Roles stay current as of the last login even for long-lived PATs; revoking a role at the IdP propagates on the user's next login.
- Live browser-session roles still take precedence; the snapshot only fills the gap when the credential has none.
- Convention-correct cross-service access; identity remains the owner of identity data.
- One injection point makes attribution *and* enforcement correct simultaneously.

**Cons:**
- Adds a per-request role lookup on the hot path (mitigated by a short-TTL cache keyed on `(tenant_id, principal_id)`).
- Needs a cross-service read of role data — either a read-only query against the shared `user_profiles` table (chosen) or a new authed identity endpoint + typed client. Either way identity remains the owner; the read is confined to one seam.
- Staleness window equal to the user's login cadence (acceptable per Goals; bounded by Decision 3).

### Option 2: Snapshot roles into the PAT JWT at mint / refresh

**Description:** When `CreatePAT` runs (it already receives the creator's live `userClaims`), copy `roles` into the PAT's `orbit.claims`. The token then carries roles like a session token; nothing changes on the inference path.

**Pros:**
- Zero hot-path cost and no cross-service lookup — roles travel with the credential.
- Smallest possible code change.

**Cons:**
- **Stale until reissue.** A PAT minted today freezes today's roles for its full TTL (default many days). A role added or revoked later never reaches existing PATs — the opposite of "hydrate on re-login."
- Roles in a long-lived bearer token are a standing governance risk (a revoked role keeps spending and authorising until the PAT expires).
- Does not help agent tokens or any already-issued PAT.

### Option 3: Hybrid — JWT snapshot at mint + periodic re-stamp

**Description:** Option 2's mint-time snapshot, plus a refresh that re-stamps roles when a PAT's backing session is refreshed or on a scheduled re-sync.

**Pros:**
- Keeps roles on the credential (no hot-path lookup) while bounding staleness better than Option 2.

**Cons:**
- Most moving parts; re-stamping a long-lived PAT means re-issuing it, which breaks the "the token value never changes" contract.
- Still stale between refreshes; complexity without clearly beating Option 1's freshness.

---

## Decision

**Chosen: Option 1 — persisted role snapshot + cached lookup at inference time.** Satellite decisions ratified 2026-06-15: storage on `user_profiles` (2a), login-only freshness (3a), **enforce immediately** (4b), and **current-period spend attributed by current membership** (5b). See [Decisions Required](#decisions-required) for the full record.

### Rationale

Option 1 matches the operator's stated mental model (membership captured at login, persisted while away from the UI, all tokens summing against the shared role/group ceiling). Options 2 and 3 are rejected on principle, not merely on freshness: **roles are never minted into a PAT JWT** — the platform, not the credential, is the authority on a principal's roles, and baking a revocable fact into a long-lived bearer token is unacceptable for a governance product. The existing `user_profiles` upsert already fires on every login, so the storage and refresh path is essentially free.

**Lookup mechanism (implemented):** the gateway resolves roles by a **read-only query against the shared `user_profiles` table** through its existing Postgres pool, not via a new authenticated identity endpoint + typed client. Both were viable (the identity-proxy sidecar auto-injects the gateway's platform token, so an authed call is feasible). The direct read was chosen because all services share one database today, the gateway already reads/writes `inference_usage` there, the access crosses no Go-package boundary (so it does not violate the feature-independence lint), and it avoids standing up an endpoint + route-scope + grant for the gateway's system principal. The cost is a read-only coupling to a table identity owns; it is confined to one place — `GetPrincipalRoles` / `GetActiveRoleHolders` / `GetPoolSpendSince` in the gateway's usage repository — and can be swapped for a typed identity client if the databases are ever split. This is a deliberate reversal of the earlier "must not read identity's tables" goal, accepted for that confinement and the absence of a per-service DB.

## Decisions Required

Ratified 2026-06-15 (decider: Justin Wilkin). Chosen option marked ✅.

**Decision 1 — Role resolution mechanism.**
- ✅ **1a** Persisted snapshot + cached inference-time lookup (Option 1).
- 1b PAT-JWT snapshot at mint (Option 2) — **rejected on principle**: never mint roles into a PAT JWT.
- 1c Hybrid (Option 3) — rejected for the same reason.

**Decision 2 — Where the snapshot lives.**
- ✅ **2a** Add `roles TEXT[] NOT NULL DEFAULT '{}'` to `user_profiles`; extend `userProfileFromPrincipal` + `Upsert`. Reuses the existing every-login write.
- 2b New dedicated `principal_role_snapshots` table.

**Decision 3 — Freshness / staleness policy.**
- ✅ **3a** Login-only refresh, no max-staleness bound; live JWT roles always take precedence over the snapshot. Staleness = login cadence.
- 3b Login-only refresh **plus** a configurable max-staleness guard.
- 3c Add periodic IdP/directory re-sync (SCIM/webhooks) — deferred; its own ADR.

**Decision 4 — Enforcement rollout (behavior change).** Turning this on makes role ceilings bind to PAT/agent inference for the first time; principals currently spending unbounded against a role budget begin to be blocked.
- 4a Two-phase: ship attribution + display first, gate enforcement behind a flag, flip after an observation window.
- ✅ **4b** Enforce immediately on rollout. Attribution and enforcement land together. ⚠️ Combined with backfill (5b), a principal whose backfilled current-period spend already exceeds a role ceiling is blocked the moment this deploys — see [Consequences](#negative).

**Decision 5 — Current-period spend already logged with empty `principal_roles`.** A role budget is a current-period accumulator over whoever **currently** holds the role. The spend already logged this period is real and the membership is current, so it must count — this is necessary for the ceiling to be correct, not an optional backfill.
- 5a Forward-only (ignore already-logged period spend) — **rejected**; it would under-count every live ceiling until the period resets.
- ✅ **5b** Attribute the current period's spend by **current membership**, computed at read/rehydrate time by joining `inference_usage` → `user_profiles.roles` on `principal_id` (role-period spend = SUM of the period's usage for principals who currently hold the role). No historical row is rewritten — there is nothing to "stamp"; the period total is simply computed from current state, which self-heals for new or changed budgets. The only bound is the login-cadence one from Decision 3: a principal who has never logged in since the migration has an empty snapshot and contributes no role spend until they do.

**Decision 6 (resolved default) — Cache TTL on the gateway lookup.** **60–120 s** in-process TTL keyed on `(tenant_id, principal_id)`, with negative caching for "no profile / no roles". Revisit only if faster role-change propagation than the TTL is needed.

## Consequences

### Positive

- Role/group budgets attribute and enforce against the real inference paths; the dashboard, the personal bar, and OPA all agree.
- All of a principal's PATs sum against one shared role/group ceiling, even while the person is offline from the UI.
- Identity remains the single owner of role data; the gateway stays a consumer.
- The integration point (inject resolved roles into context once per request) leaves every downstream consumer unchanged.

### Negative

- New hot-path dependency on the identity service for PAT traffic (bounded by cache + fail-open).
- **Enforce-immediately (4b) is a sharp, correct behavior change.** On deploy, the current period's already-logged spend counts against role ceilings (computed from current membership) *and* enforcement is live, so a principal already over a role ceiling for the period is blocked at once — no observation window. This is the intended steady state, but it should be announced, and operators should preview current-period role utilisation against ceilings before deploying (run the membership-join query read-only to see who is already over).
- Role membership accuracy is bounded by login cadence (Decision 3); a user who never returns to the UI keeps stale roles, and backfill cannot attribute spend for a principal who has never logged in since the migration.

### Neutral

- `inference_usage.principal_roles` is no longer read or written by any code path; role membership is single-sourced in `user_profiles`. The column becomes vestigial and is slated for removal in a follow-up migration. (Net: less duplicated state, not more.)
- Browser-session inference behaves identically to PAT inference for role budgets — both attribute via the `user_profiles` snapshot join — so there is no longer a live-roles-vs-snapshot precedence question on the spend path. The live JWT roles still drive *which* ceilings the request is checked against in the moment.

## Implementation

Ratified decisions: 1a / 2a / 3a / 4b / 5b. Status below reflects what is **implemented** in this change.

1. ✅ **Migration** (`cmd/identity/migrations/20260615161801_add_roles_to_user_profiles.sql`): `roles TEXT[] NOT NULL DEFAULT '{}'` + GIN index on `roles`.
2. ✅ **Identity write path** (`internal/identity/user_profile_repository.go`, `models.go`): `userProfileFromPrincipal` parses the merged `Claims["roles"]` into the `Roles` slice; `Upsert` writes it with `SET roles = EXCLUDED.roles`, so every re-login refreshes the snapshot. `GetByID`/`List` select it too.
3. ✅ **Gateway role resolution** (`internal/inferencegw/role_cache.go`, `repository.go`): `RoleDirectory`-style read implemented as `InferenceUsageRepository.GetPrincipalRoles(tenant, principalID)` — a read-only `SELECT roles FROM user_profiles`. A small TTL cache (`roleCacheTTL`, 90 s) shields the hot path; lookups fail open (empty roles on error). **No new identity endpoint or typed client** (see Decision → Lookup mechanism).
4. ✅ **Resolution at the chokepoint** (`internal/inferencegw/service.go`): `budgetScopesFor` — the single function `checkBudget`, `incrementSpend`, and `GetPersonalBudget` all call — uses live JWT roles when present and falls back to the cached snapshot when the credential carries none. So attribution *and* enforcement (4b) become correct together, with no context-threading and no flag.
5. ✅ **Stop stamping** (`writeUsage`): no role data is written onto `inference_usage`. The `principal_roles` column loses its only consumers (step 6) and is deprecated — left in place here, dropped in a follow-up migration. `Create` still writes the (now-always-empty) column until that migration lands.
6. ✅ **Read/rehydrate path (5b)** (`internal/inferencegw/repository.go`): both role-spend queries recompute against **current** `user_profiles` membership instead of the per-row column, preserving their signatures so the budget counter and mocks are untouched:
   - `GetActiveRoleHolders` → current holders (`cardinality(roles) > 0`) that have period spend (`EXISTS` against `inference_usage`). Drives the budgets list via the unchanged `ListBudgetPrincipals`.
   - `GetPoolSpendSince` → `SUM(estimated_cost_usd)` over rows whose `principal_id IN (SELECT id FROM user_profiles WHERE $role = ANY(roles))`. Rehydrates the role-pool counter from current membership.
   The already-logged current-period spend counts immediately, with no row rewrite. The per-request Redis pool counter still increments live; on counter miss it rehydrates from current membership, so the two reconcile.
7. ✅ **Tests**: snapshot-fallback and live-roles-win unit tests; full `make check` green; the three SQL queries validated against the live schema (membership join attributes a real spender's $ to a seeded role).

### Migration Path

The schema migration and identity write path can ship first (snapshots begin populating on logins immediately, harmlessly). The gateway lookup, the membership-join read path, and enforcement then land together. Recommended deploy sequence: (a) migration + identity write path; (b) encourage/await a login sweep so snapshots populate; (c) preview projected role utilisation against ceilings with a read-only run of the membership-join query, to see who is already over for the period; (d) deploy the gateway integration + read-path change. The budgets dashboard's existing "attributed from inference activity" banner should be updated to reflect that attribution now covers PAT traffic.

## Validation

### Success Metrics

- On the deployed tenant, principals holding a budgeted role show a non-zero effective limit and correct attributed current-period spend as soon as their role snapshot is populated (i.e. after their next login).
- The personal usage bar reflects real spend against the role ceiling (no more `0 / <limit>` for an active spender).
- A synthetic role budget set below a principal's current-period spend blocks their PAT inference immediately (enforcement is not gated).

### Monitoring

- Gateway metric/log for role-resolution outcomes: cache hit/miss, lookup latency, fail-open count.
- `budget.hard_block` logs now include role-scope breaches for PAT traffic.
