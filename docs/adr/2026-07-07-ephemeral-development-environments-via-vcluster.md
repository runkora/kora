# Ephemeral Development Environments via vcluster

**Status:** Proposed
**Date:** 2026-07-07
**Deciders:** Engineering Team
**Technical Story:** Developers building the Orbit platform need on-demand, isolated, full-stack environments. Today the options are the local k3d cluster ([local-development-environment](2026-03-10-local-development-environment.md)) — per-machine, resource-heavy, and divergent from real deployments — or a shared staging cluster, which is contended and cannot be broken safely. This ADR defines button-press ephemeral environments, running as vclusters on the same infrastructure that runs Orbit itself, provisioned from the Orbit UI. It **replaces Tier 2 (`make dev-cluster`, k3d) as the full-stack development path**; Tier 1 (`make dev-up`) remains the fast local inner loop.

---

## Context

Orbit is a multi-service control plane (13 binaries) whose interesting behaviour lives in the seams between services and infrastructure: the operator's Helm release sequencing, SPIRE attestation, Istio sidecar and `ext_proc` wiring, OPA bundle distribution, and tenant namespace reconciliation. A meaningful share of platform work — operator changes, chart changes, CRD schema changes, sidecar injection changes — cannot be validated in Tier 1 (`make dev-up`) at all, and validating it in Tier 2 (`make dev-cluster`) means rebuilding a k3d cluster on a laptop that is also running an IDE, Docker, and an agent or two.

The shared staging cluster is the other escape valve, and it has the usual problems: one engineer's broken operator build blocks everyone; testing a destructive migration means coordinating a freeze; two branches cannot deploy concurrently.

What developers actually need is a **disposable, isolated Orbit installation** — including the cluster-scoped machinery (CRDs, operator, mesh) — that exists for the lifetime of a branch and costs nothing when idle.

This ADR is not an addition to the two-tier local strategy — it **replaces Tier 2**. The k3d cluster earns its keep today only because nothing better exists: it duplicates deployment configuration that must be kept in lockstep with the real charts (a maintenance burden [local-development-environment](2026-03-10-local-development-environment.md) itself lists as a negative consequence), it needs workarounds a real cluster does not (CoreDNS endpoint injection for Docker Compose services, `k3d image import` for unreachable registries), it consumes a large share of a laptop's resources, and it still diverges from real deployments. Once a higher-fidelity environment can be provisioned in minutes from the UI, maintaining a second, lower-fidelity full-stack mechanism is pure cost. Tier 1 (`make dev-up` — Postgres, Redis, Dex via Docker Compose, services under `air`) is untouched: the fast, offline Go inner loop is a different job and stays local.

There is a second, deliberate motivation: **dogfooding**. Orbit's product thesis is that provisioning governed workloads should be a button press backed by identity, policy, and audit. Provisioning Orbit's own development environments through the Orbit UI exercises exactly that thesis — the button is scope-gated by the policy gateway, the action is attributed to a human principal, and the lifecycle is reconciled by the same operator that runs production installs.

### Background

Relevant existing machinery:

- The **operator** ([orbit-kubernetes-operator](2026-03-31-orbit-kubernetes-operator.md)) already reconciles cluster-scoped CRDs (`OrbitPlatform`, `OrbitTenant`) into namespaces, Helm releases, and config projection. It owns the full release sequence `spire-crds → spire → istio-base → istiod → gateway → orbit-platform → orbit`.
- The **UI → BFF → backend** provisioning pattern ([agents-bff-integration-and-run-chat-wiring](2026-06-04-agents-bff-integration-and-run-chat-wiring.md)) is established: the browser never calls backend services directly; BFF routes validate the session cookie and forward the platform JWT.
- `orbit-agents` is today the **only service that talks to the Kubernetes API**, with deliberately broad RBAC across `orbit-tenant-*` namespaces ([agent-execution-infrastructure](2026-05-11-agent-execution-infrastructure.md)).
- All actions are scope-gated by the policy gateway ([policy-gateway-and-authorisation-model](2026-04-14-policy-gateway-and-authorisation-model.md), [platform-scope-enforcement-middleware](2026-06-04-platform-scope-enforcement-middleware.md)).

Naming note: `orbit-agents` already has an `EnvironmentConfig` concept (eager sandbox provisioning for agent sessions — `backend/internal/agents/environments.go`). That is a different thing. This ADR consistently uses **dev environment** / `OrbitDevEnvironment` to avoid collision.

### Problem Statement

We need to define:

1. The isolation model for ephemeral environments — how one developer's full Orbit installation (including CRDs, operator, and mesh) coexists with others on shared infrastructure
2. Where the environments run
3. How an environment is provisioned from a button in the Orbit UI — which service exposes the API, and what reconciles the environment into existence
4. The lifecycle model: TTL, sleep/wake, teardown, and cost controls
5. How the developer accesses a provisioned environment (kubeconfig, ingress) without handling long-lived credentials
6. How environment workloads obtain SPIFFE identities, given that SPIRE's agent performs node-level attestation and a vcluster has no nodes of its own

### Goals

- **Button-press provisioning**: an authenticated developer clicks *New dev environment* in the Orbit UI and gets a ready environment in minutes, with progress visible in the UI
- **Full-stack fidelity**: each environment is a real Orbit installation deployed through the same operator and charts as production installs — not a mock or a subset
- **Cluster-admin inside, least-privilege outside**: developers can install CRDs, replace the operator, and break the mesh *inside their environment* without any grant on the host cluster
- **Same infrastructure as Orbit itself**: environments run on the cluster that runs the Orbit control plane — no separate dev-cluster fleet to build, patch, and pay for
- **Replace the k3d full-stack tier**: retire `make dev-cluster` (Tier 2) and its supporting machinery once parity is demonstrated — one full-stack environment mechanism to maintain, not two
- **Governed like everything else**: provisioning is scope-gated, attributed to a human identity, and audited; environments have TTLs and quotas by default

### Non-Goals

- Replacing Tier 1 (`make dev-up`) for daily Go development — the fast, offline inner loop stays local. (Replacing Tier 2, by contrast, is an explicit goal)
- Preserving an offline *full-stack* development path — after Tier 2 retirement, full-stack work requires connectivity to the host cluster, deliberately
- Ephemeral environments for Orbit *customers* or their agents (agent sandboxes are covered by [sandbox-provisioning-and-shell-proxy](2026-05-11-sandbox-provisioning-and-shell-proxy.md))
- Preview environments wired to PRs / CI automation — a natural follow-up, but the trigger in scope here is the UI button
- Production-hardening validation (Cilium eBPF enforcement, real cloud IAM) — that remains a CI/staging concern, consistent with [local-development-environment](2026-03-10-local-development-environment.md)

---

## Decision Drivers

* **Cluster-scoped resources are the crux**: Orbit development routinely mutates CRDs, the operator, `ClusterSPIFFEID`s, and mesh config — resources that cannot be namespaced away on a shared cluster
* **Provisioning speed**: an environment that takes 20 minutes to appear will not be used; the target is minutes, not tens of minutes
* **Cost**: environments must share host-cluster nodes, scale to zero when idle, and die on a TTL — a per-developer cloud cluster fleet is not acceptable
* **Consistency with the operator model**: Orbit already expresses "desired platform state" as CRDs reconciled by the operator; environment provisioning should follow the same declarative pattern, not introduce a parallel imperative path
* **Two full-stack mechanisms is one too many**: Tier 2 duplicates chart/values maintenance (`values.local.yaml` overlays, CoreDNS injection scripts, image-import workarounds) that must track every platform change; whatever replaces it must carry the full Tier 2 validation load so that duplication can actually be deleted
* **Dogfooding**: the provisioning flow should exercise Orbit's own identity, policy, and audit machinery
* **Security of the host cluster**: developer cluster-admin must be confined; the blast radius of a broken environment must be one namespace on the host

## Considered Options

### A. Isolation model

#### Option A1: Namespace-per-environment on the shared cluster

**Description:** Each environment is a set of namespaces on the host cluster; Orbit services deploy into them directly.

**Pros:**
- Cheapest and simplest — no extra control-plane pods
- Instant "provisioning" (namespace creation is immediate)

**Cons:**
- **Fails the core requirement**: CRDs, the operator, `ClusterSPIFFEID`s, admission webhooks, and Istio config are cluster-scoped — two environments testing different CRD schema versions collide immediately
- Developer workflows need broad host-cluster RBAC, which leaks across environments
- One environment's misbehaving operator reconciles everyone's resources

#### Option A2: Real cluster per environment (cloud cluster or k3d-on-VM fleet)

**Description:** Provision a dedicated Kubernetes cluster (e.g. EKS, or k3s on a pooled VM) per environment.

**Pros:**
- Maximum isolation and fidelity, including node-level components (Cilium, kernel eBPF)
- Developer is genuinely cluster-admin

**Cons:**
- Slow: cloud cluster creation is 15–20+ minutes; a pre-warmed pool mitigates this at significant standing cost
- Expensive: per-cluster control-plane fees and poor bin-packing of mostly-idle environments
- A second infrastructure estate to build, patch, monitor, and pay for — explicitly *not* "the same infra as Orbit itself"

#### Option A3: vcluster per environment *(chosen)*

**Description:** Each environment is a [vcluster](https://www.vcluster.com/) — a certified virtual Kubernetes cluster whose control plane (k3s API server + controller-manager + datastore) runs as a pod inside a single namespace of the host cluster, with a syncer that maps virtual pods onto host nodes.

**Pros:**
- **Cluster-scoped isolation without a cluster**: each vcluster has its own API server, so CRDs, operators, webhooks, and RBAC are private to the environment — the exact gap A1 cannot close
- Fast: a vcluster is running in well under a minute; the Orbit install on top dominates time-to-ready
- Cheap: one namespace, a small control-plane pod, shared host nodes; an idle environment can be slept — workloads scaled to zero with state preserved (implemented in our reconciler; see lifecycle and the licensing con below)
- Developer gets `cluster-admin` *inside* the vcluster with zero grants on the host API server
- Host-side blast radius is one namespace, cappable with `ResourceQuota`/`LimitRange`
- Runs on the existing host cluster — satisfies "same infra as Orbit itself" literally

**Cons:**
- Not full fidelity at the node layer: workloads share host nodes and the host kernel — Cilium/eBPF behaviour is out of scope (already the accepted posture for local dev per [local-development-environment](2026-03-10-local-development-environment.md))
- Node-level infrastructure cannot run *inside* a vcluster: anything that attests or observes workloads via the host kubelet — the SPIRE agent DaemonSet in particular — must be provided by the host instead (see option group C)
- Running Istio inside a vcluster is workable but has sharp edges (injection webhook interplay with the syncer) — see Consequences
- vcluster's native sleep mode and auto-wakeup are **Enterprise-licensed** (and auto-wake on ingress additionally requires the vCluster Platform agent) — the OSS core adopted here does not include them. Sleep is therefore implemented in our own reconciler (see lifecycle, decision 8), and wake is an explicit UI/API action rather than transparent on connection
- A new third-party dependency with its own upgrade cadence

### B. Provisioning trigger and control flow

#### Option B1: GitOps pull request per environment

**Description:** The button opens a PR against the deployment repo adding environment manifests; Flux/ArgoCD syncs it.

**Pros:**
- Every environment is in Git; audit for free
- No new API surface

**Cons:**
- Minutes of PR + sync latency before provisioning even starts; teardown equally indirect
- "Press a button, wait for a robot to merge a PR" is a poor product experience, and this flow *is* product surface (dogfooding)
- Ephemeral, hours-lived state churns the deployment repo with noise

#### Option B2: Imperative provisioning from a backend service

**Description:** A backend handler runs `helm install vcluster ...` and the Orbit install steps directly, the way `orbit-agents` imperatively creates StatefulSets today.

**Pros:**
- Direct; no CRD or operator changes
- Precedent exists in `orbit-agents`

**Cons:**
- No reconciliation: a half-failed install needs bespoke retry/repair logic that the operator already has
- Long-running multi-release install sequence held inside an HTTP request lifecycle
- Duplicates the operator's Helm SDK machinery in a second service
- Grants a request-serving API service broad host-cluster RBAC (namespaces, Helm releases, cluster-scoped reads)

#### Option B3: `OrbitDevEnvironment` CRD reconciled by the operator *(chosen)*

**Description:** The button results in a small API creating an `OrbitDevEnvironment` custom resource on the host cluster. The existing operator grows a third reconciler that turns the CR into a namespace + vcluster + Orbit installation, and reflects progress into `status`, which the UI polls.

**Pros:**
- Identical shape to `OrbitPlatform`/`OrbitTenant`: declarative spec, level-triggered reconcile, self-healing on partial failure, status conditions for the UI
- The operator already owns Helm release sequencing and namespace lifecycle — this reuses it rather than duplicating it
- TTL enforcement is a natural reconcile concern (requeue until `expiresAt`, then delete)
- The API service's host-cluster RBAC shrinks to CRUD on one CRD; everything privileged stays in the operator

**Cons:**
- Operator scope grows; a dev-tooling concern now ships in the production operator binary (mitigated: the reconciler is inert unless `OrbitDevEnvironment` CRs exist, and the CRD is only installed on clusters that opt in)
- Status-over-CR is a slightly slower feedback channel than a synchronous API (acceptable: provisioning takes minutes anyway)

### C. Workload identity for environment workloads

SPIRE is the forcing constraint on how "complete" an in-vcluster Orbit install can be, so the identity topology is decided here rather than left to implementation.

#### Option C1: SPIRE runs inside each vcluster

**Description:** The in-vcluster `OrbitPlatform` installs SPIRE exactly as a real deployment does — per-environment SPIRE server, agent DaemonSet, and trust domain.

**Pros:**
- Maximum conceptual fidelity: every environment is a byte-identical Orbit install, including its identity plane
- Per-environment trust domains give the cleanest isolation story

**Cons:**
- **Does not work.** The SPIRE agent performs node-level workload attestation against the host kubelet, and a vcluster has no nodes — its pods are synced onto host nodes with translated names/namespaces (e.g. `identity-x-orbit-system-x-{env-id}`). An in-vcluster agent's kubelet view can never match the registrations created by the in-vcluster SPIRE controller manager, which sees virtual names
- The Workload API socket is a host node path (hostPath/CSI); an in-vcluster SPIRE cannot own one without colliding with the host agent and every other environment
- Node attestation (`k8s_psat`) needs `TokenReview` against the API server that actually runs the agent pods — the host, not the virtual one

#### Option C2: Nested SPIRE — per-environment server chained to the host

**Description:** Each environment runs its own SPIRE *server* (a plain pod — this part works), chained to the host Orbit SPIRE via the `UpstreamAuthority` plugin, giving per-environment trust domains rooted in the host CA.

**Pros:**
- Per-environment trust domains and a per-environment server, so SPIRE-server-adjacent control-plane logic could be exercised in-environment
- Standard, supported SPIRE topology (nested/downstream servers)

**Cons:**
- Solves the wrong half: the *agents* still cannot attest through the syncer's name translation (C1's core failure), so the host operator would have to run a dedicated agent DaemonSet per environment on host nodes, outside the vcluster, with per-environment socket paths — N agent DaemonSets per node
- Substantial reconciler complexity for a fidelity gain no current development task needs

#### Option C3: Host-provided identity — the main Orbit installation's SPIRE attests environment workloads *(chosen)*

**Description:** Environments run no SPIRE at all (`spire.enabled=false` on the in-vcluster `OrbitPlatform`). Because environment pods physically run on host nodes, the **host** SPIRE agents attest them natively, like any other host pod — no proxy layer is required. The reconciler creates a host-side `ClusterSPIFFEID` for the environment namespace minting path-scoped IDs (`spiffe://{trust-domain}/devenv/{env-id}/…`), the host SPIFFE CSI driver mounts the host Workload API socket into environment pods (the CSI volume spec syncs through to the host kubelet), and the reconciler projects the host trust bundle into the vcluster so in-environment services can validate SVIDs.

**Pros:**
- Works with SPIRE's actual attestation model instead of against it
- Environment services receive **real SVIDs** — identity-consumption flows (`POST /identity/exchange`, `identity-proxy` injection, SVID-based mTLS) are exercised with genuine attestation, which Tier 1 local dev cannot offer at all
- One SPIRE deployment to operate; no per-environment agent or socket management

**Cons:**
- Isolation is by **path prefix within the shared host trust domain**, not per-environment trust domains — host authorization policy must never match `devenv/…` prefixed IDs (host policies match exact `system/…` and `tenant/…` paths today, and environment namespaces are NetworkPolicy-fenced from the host control plane regardless)
- Changes to SPIRE deployment itself (charts, agent config, attestor plugins) cannot be validated in a dev environment — that work stays on Tier 2 / staging
- Prerequisite: the SPIFFE CSI driver, currently disabled in our SPIRE chart values ([local-development-environment](2026-03-10-local-development-environment.md)), must be enabled on host installs that support dev environments
- The exact `ClusterSPIFFEID` selector strategy (namespace-scoped vs. syncer-propagated labels) depends on how faithfully the syncer propagates pod labels — pinned down in the Phase 1 spike
- **The `devenv/…` path prefix is not parseable by current platform code.** `principalFromSpiffeID` (`backend/internal/identity/principal_extractor.go`) recognises only `system/…` and `tenant/…` paths, and chart-shipped authorization policies match exact paths — so the in-environment identity service, XFCC handling, and mesh authz would reject host-minted `devenv/{env-id}/…` SVIDs as written. Prefix handling is resolved in the Phase 1 spike; the preferred direction is teaching platform code to strip an optional `devenv/{env-id}` prefix (one code change, shipped everywhere) rather than parameterising paths through per-environment chart values, which would recreate the Tier 2 values-divergence this ADR exists to delete

## Decision

**Chosen Options:** A3 (vcluster per environment) + B3 (`OrbitDevEnvironment` CRD reconciled by the operator) + C3 (host-provided workload identity).

### Architecture

```
Developer clicks "New dev environment" in the Orbit UI
  → BFF route (frontend/src/app/api/dev-environments/**)
      session cookie → platform JWT → typed client
  → identity API: POST /v1/dev-environments        (scope: devenvironments:write)
      validates quota (max active envs per principal), generates env ID
  → creates OrbitDevEnvironment CR on the host cluster
  → operator devenvironment reconciler:
      1. host namespace  orbit-devenv-{env-id}   (ResourceQuota, LimitRange,
         NetworkPolicy, TTL + owner labels)
      2. vcluster Helm release into that namespace
      3. host-side identity wiring: ClusterSPIFFEID for the env namespace
         (spiffe://{trust-domain}/devenv/{env-id}/…) + host trust bundle
         projected into the vcluster
      4. inside the vcluster: orbit-operator chart → OrbitPlatform CR
         (spire.enabled=false — identity comes from the host, see C3) →
         release sequence, plus Postgres, Redis, Dex, and a seeded
         OrbitTenant (mirrors the deploy/local reference install)
      5. Ingress  {env-id}.dev.{domain}  → the env's gateway
         (k3d/local; **superseded for real infrastructure** — see
         "Amendment (2026-07-10): Path-Based App Ingress for Real
         Infrastructure" below)
      6. surfaces status.phase: Pending → Provisioning → Ready
         (also Sleeping | Expired | Failed) and status.ingressHost,
         status.expiresAt
  → UI polls GET /v1/dev-environments/{id} and renders progress
```

### Key decisions within the design

1. **Environments run on the host cluster that runs Orbit's control plane**, in namespaces named `orbit-devenv-{env-id}`, labelled `orbit.io/role: devenv` and `orbit.io/owner: {principal}`. No separate fleet. Capacity is managed with a dedicated node pool (taint/toleration) where the host cluster has one, so dev-environment load cannot starve the control plane; on single-pool clusters, `ResourceQuota` per environment namespace is the backstop. The ≤5-minute time-to-ready target additionally **requires environment images pre-pulled onto the dev-environment nodes** (DaemonSet pre-puller or node-image baking) — a cold pull of the full stack (Istio, Postgres, Redis, Dex, the Orbit binaries) does not fit the budget.

2. **Each environment is a self-contained Orbit install — identity excepted.** The reconciler installs the `orbit-operator` chart *inside* the vcluster and applies an `OrbitPlatform` CR plus a seeded dev `OrbitTenant`, so the environment exercises the real install path end-to-end — the operator being reconciled inside the vcluster is the very artifact under development. Postgres, Redis, and Dex run inside the vcluster with fixture data; **environments never share the host control plane's database or Redis**. Isolation beats convenience here: a dev environment testing a migration must not be able to touch real control-plane state.

3. **Workload identity is provided by the host Orbit installation's SPIRE** (option C3). SPIRE cannot run inside a vcluster — its agent attests via the host kubelet, where synced pods appear under translated names. Instead, the in-vcluster install runs with `spire.enabled=false`; host SPIRE agents attest environment pods natively (they are host pods), minting path-scoped IDs under `spiffe://{trust-domain}/devenv/{env-id}/…` via a reconciler-managed `ClusterSPIFFEID`, with the Workload API socket delivered by the host SPIFFE CSI driver and the trust bundle projected into the vcluster. Environment services therefore consume **real SVIDs** from real attestation. One compatibility gap gates this: current platform code and chart authz policies parse exact `system/…`/`tenant/…` paths and would reject the `devenv/…` prefix — prefix handling (preferred: platform code strips an optional `devenv/{env-id}` segment) is a Phase 1 spike exit criterion, not an implementation detail.

4. **The environment installs a chosen ref.** `spec.ref` selects the chart/image version to install (default: latest `main` build). Developers iterate by pushing a branch image (built locally or by CI) and either bumping `spec.ref` or using their kubeconfig to `helm upgrade` inside the vcluster directly — inside the vcluster they are cluster-admin, and nothing they do there is visible to the host.

5. **The API surface is a new feature package `internal/devenvironments` in the main control-plane API (`cmd/identity`)**, following the standard feature structure (repository/service/handlers). It owns the environment registry rows (owner, quota accounting, audit trail) and creates/deletes `OrbitDevEnvironment` CRs. This deliberately relaxes, narrowly, the "only `orbit-agents` talks to the Kubernetes API" posture: the identity service gains a k8s client whose RBAC is **CRUD on `OrbitDevEnvironment` CRs only** — it cannot create namespaces, pods, or Helm releases. `orbit-agents` was considered as the host (it has the k8s client precedent) but rejected: dev environments have nothing to do with agent execution, and parking them there couples two unrelated lifecycles to one service's already-broad RBAC.

6. **Access is brokered, not handed out — and the operator does the signing.** The UI's *Connect* action calls `POST /v1/dev-environments/{id}/kubeconfig`, which returns a **short-lived kubeconfig** (client certificate against the vcluster's CA, default 8h) scoped to that vcluster. The identity service never touches the vcluster CA key (which would breach its single-CRD RBAC posture, decision 5): it generates the client keypair, places the CSR on the `OrbitDevEnvironment` CR, and the reconciler — which already holds namespace-scoped privileges — signs it against the vcluster CA and publishes the certificate and CA bundle in `status`. Only public material transits the CR; the private key never leaves the identity service, which assembles and returns the kubeconfig. Developers never receive host-cluster credentials of any kind. The environment's Orbit UI/API is reachable at `https://{env-id}.dev.{domain}` (k3d/local; **on real infrastructure this is a single shared host + path prefix instead — see the Amendment below**), authenticated against the environment's own Dex — consistent with the agent-credential principle that raw long-lived credentials are never exposed ([jit-credential-brokering-egress-gateway](2026-06-06-jit-credential-brokering-egress-gateway.md)). This kubeconfig flow itself, and the SNI-routed kubectl API access it depends on (port `16443`, `devenvironment_ingress.go`), are unaffected by that amendment — the app-ingress hostname and the API-passthrough SNI value are independent mechanisms that happen to share the same `status.ingressHost` field today (see the Amendment for the resulting split).

7. **These environments replace Tier 2, on a parity gate — not on day one.** `make dev-cluster` remains available (and is the test bed for developing the dev-environment reconciler itself — this feature cannot be developed inside itself until it exists) through initial rollout. Tier 2 is deprecated only when the Phase 1 fidelity matrix plus real usage demonstrate that dev environments cover the Tier 2 workload: the `POST /identity/exchange` flow against real SVIDs, operator and chart iteration, sidecar and `ext_proc` wiring. Work dev environments deliberately do not cover is re-homed explicitly rather than silently orphaned: SPIRE deployment work and Cilium validation go to CI/staging (where Cilium already lives).

8. **Lifecycle defaults**: TTL 24h, extendable from the UI up to a hard cap (7 days); **sleep** after 2h idle; per-principal cap of 2 active environments (policy-configurable). Sleep is implemented **by the devenvironment reconciler, not by vcluster** — vcluster's native sleep mode is Enterprise-licensed and its ingress-triggered auto-wake requires the vCluster Platform agent, neither of which we adopt. The reconciler's crude equivalent: scale the vcluster control-plane StatefulSet and its synced workloads to zero, retaining PVCs (the vcluster datastore and all state survive). Idleness is derived from platform-visible signals (last kubeconfig mint, last ingress/UI activity). Wake is **explicit** — a UI action or a `POST /v1/dev-environments/{id}/kubeconfig` call flips the CR's desired state and the reconciler scales back up; there is no transparent wake-on-connection, and a `kubectl` against a sleeping environment fails until woken. On expiry the reconciler deletes the namespace — everything, including the vcluster's datastore, goes with it. Deletion is the recovery path for a wedged environment: delete and re-provision, never repair in place.

### The three questions

- **Who is this agent?** The provisioning action is performed by an authenticated human principal; the CR carries the owner identity, every state transition is audited against it, and quota/TTL policy binds to it. Workloads *inside* the environment carry real, host-SPIRE-issued SVIDs path-scoped under `spiffe://{trust-domain}/devenv/{env-id}/…` — every environment workload is attested and attributable, and no host or tenant authorization policy matches the `devenv/…` prefix.
- **What can it access?** The button is gated by `devenvironments:*` scopes through the policy gateway. On the host, the environment can access exactly one namespace under quota, fenced by NetworkPolicy from the host control plane; the developer's cluster-admin exists only inside the virtual API server. The identity service's new k8s RBAC is confined to one CRD.
- **How does it connect?** Access credentials (kubeconfig, session) are short-lived and brokered through the platform; developers never hold host-cluster or long-lived credentials.

## Consequences

### Positive

- Platform work that today requires the shared staging cluster — operator changes, CRD migrations, chart refactors, mesh wiring — gets an isolated, disposable target per branch
- Staging stops being a contention point and a single point of breakage for the team
- Environments deploy through the production install path (operator + charts), so the install path itself is exercised dozens of times a week — install regressions surface in dev environments before any customer sees them
- The feature dogfoods Orbit's identity/policy/audit stack on a real internal workflow
- Idle cost approaches zero via reconciler-managed sleep + TTL; blast radius is one quota-capped host namespace
- The local strategy collapses from two tiers to one: the entire Tier 2 maintenance surface (`values.local.yaml` overlays, CoreDNS endpoint injection, `k3d image import` workarounds, laptop resource pressure) is deleted after retirement, and full-stack fidelity *improves* — dev environments run real SVID attestation, which Tier 2's k3d SPIRE approximated

### Negative

- **SPIRE deployment work is not exercisable in a dev environment.** With identity host-provided (C3), changes to SPIRE charts, agent configuration, or attestor plugins require a real (non-virtual) cluster — Tier 2 while it still exists, CI/staging after its retirement. The flip side is genuinely positive — identity *consumption* flows run against real attestation — but the SPIRE deployment layer itself is a fidelity hole by design.
- **Full-stack development stops working offline.** Once Tier 2 is retired, a developer without connectivity to the host cluster has Tier 1 only. This is accepted deliberately: the team does not have an offline-development requirement, and keeping Tier 2 alive for a hypothetical one forfeits the consolidation benefit.
- **The host cluster becomes critical developer infrastructure.** After Tier 2 retirement, a host-cluster outage blocks all full-stack validation for the whole team — it needs an availability owner and the same operational care as CI.
- **Istio fidelity inside a vcluster needs spike validation.** Injection webhooks interact with the syncer in ways that must be proven before implementation; if full in-vcluster Istio proves fragile, the fallback is the documented Tier-2 posture (NetworkPolicy substitute, degraded-mode flags) — acceptable for most platform work, but changes to the mesh layer itself would still need staging. Cilium/eBPF remains out of scope entirely, as it already is locally.
- **Host installs that support dev environments must enable the SPIFFE CSI driver** (currently disabled in the SPIRE chart values) so the host Workload API socket can be mounted into environment pods.
- **Sleep/wake is ours to build and operate.** vcluster's native sleep mode is Enterprise-licensed, so the reconciler carries the idle-detection and scale-down/up logic itself, and wake is an explicit UI/API action — a developer running `kubectl` against a sleeping environment gets a connection error until they wake it. More operator code, and a rougher edge than transparent wake-on-connection
- The operator binary takes on a third reconciler and a dev-tooling concern; its test surface grows
- vcluster becomes a load-bearing third-party dependency (version-pinned in the operator's chart references, upgraded deliberately like the Istio/SPIRE pins)
- The host cluster must be capacity-planned for N concurrent environments; a burst of provisioning can pressure shared nodes if no dedicated node pool exists
- The identity service gains a (single-CRD) Kubernetes client — a small but real widening of its dependency surface

### Neutral

- A new scope family (`devenvironments:read|write|admin`) enters the policy vocabulary and dashboard
- `deploy/local/` gains a sibling role: the fixture set it defines becomes the seed content for every dev environment, so it must be kept installable at all times
- The UI grows a *Dev Environments* page (list, provision, connect, extend, destroy) following existing frontend patterns (Terra components, BFF policy projection)

## Phase 1 Spike — Executed 2026-07-08

### Preparatory findings (pre-spike research, retained for context)

Before writing any spike scripts, the assumptions behind Option A3/C3 and the Phase 1 plan were checked against the current state of `main` and current vcluster documentation. Several materially changed the spike's risk profile and required configuration. This section is retained as-written prior to execution; see "Spike Execution — Results" below for what actually happened when these assumptions were tested.

### Corrections to this ADR's existing claims

- **The SPIFFE CSI driver is already enabled, not disabled.** This ADR states in several places (Option C3 cons, Consequences/Negative, and the local-setup Prerequisites) that "the SPIFFE CSI driver... is currently disabled in our SPIRE chart values" and lists enabling it as a Phase 1 prerequisite. That is stale relative to `main`: `backend/internal/operator/platform_controller.go:373-376` sets `"spiffe-csi-driver": map[string]any{"enabled": true}` and `git log -S"spiffe-csi-driver"` shows this has been `true` since it was introduced (commit `d999ca6`, #18) and never changed. `charts/orbit/templates/{frontend,identity}/deployment.yaml` already mount the CSI volume into in-mesh workloads, and `reconcileGateway` (`platform_controller.go:447-498`) does the same for the gateway. **No flag needs flipping on the host side before the spike.** Verify empirically with `kubectl get daemonset -n spire-system` (expect a `spiffe-csi-driver` DaemonSet) and `kubectl get csidriver csi.spiffe.io` after `make cluster-operator`, rather than assuming a change is needed.

### Current vcluster reality (checked against vcluster.com/docs and loft-sh/vcluster, current stable v0.35.1, July 2026 — this ADR's References section and Option A3 description predate these specifics)

- **The k3s distro is gone.** `controlPlane.distro.k3s` was deprecated in v0.25 and removed entirely in v0.33. Current stable only supports the k8s distro (real kube-apiserver + controller-manager, embedded etcd or sqlite datastore). The spike — and any future implementation — runs the k8s distro inside vcluster even though the *host* is k3d/k3s; this is heavier than the ADR's "fast: a vcluster is running in well under a minute" pro implicitly assumed, though likely still true in absolute terms. Doc: [K3s distro (deprecated)](https://www.vcluster.com/docs/vcluster/0.31.0/configure/vcluster-yaml/control-plane/components/distro/k3s).
- **Sidecar-mode Istio inside a vcluster is off vcluster's own supported path.** vcluster's official [Istio Integration](https://www.vcluster.com/docs/vcluster/integrations/istio) supports **only Istio in Ambient mode running on the host**, syncing `DestinationRule`/`Gateway`/`VirtualService` objects out — it explicitly does not cover running istiod and a sidecar-injection webhook *inside* a vcluster, which is exactly what Option C3's architecture requires (`spire.enabled=false` inside the vcluster still leaves `istio.enabled=true` inside the vcluster, per decision 3). This should still work mechanically — pod admission happens against the vcluster's own virtual API server before the syncer mirrors the (already-mutated) pod to the host, so an in-vcluster `MutatingWebhookConfiguration` should fire first — and third-party posts describe doing this pre-dating vcluster's official Ambient-only integration. But it is now the **single highest-uncertainty item in the whole spike**, more so than this ADR's Option A3 cons ("has sharp edges") anticipated. If it fails, the ADR's own documented fallback already covers it (Consequences/Negative: "the fallback is the documented Tier-2 posture... Cilium/eBPF remains out of scope entirely").
- **`sync.toHost.serviceAccounts` and `sync.toHost.networkPolicies` default to `false`.** Per [Sync to host](https://www.vcluster.com/docs/vcluster/configure/vcluster-yaml/sync/to-host/), OSS vcluster syncs Pods/Secrets/ConfigMaps/Services/Endpoints/PVCs virtual→host by default, but ServiceAccounts and NetworkPolicies are opt-in. Both **must** be explicitly set `true` in `vcluster.yaml` for this ADR's C3 identity model and NetworkPolicy host-fencing claim to work at all:
  - SPIRE's `k8s_psat` node attestor (`spire-agent.workloadAttestors.k8s`, configured in `platform_controller.go` per the SPIRE values block) does a `TokenReview` against the **host** API server using the pod's ServiceAccount token. If the ServiceAccount referenced by a synced pod doesn't exist as a real host object, attestation likely breaks.
  - This ADR's isolation claim ("fenced by NetworkPolicy from the host control plane", decisions 8/"three questions") depends on host-side NetworkPolicy objects actually existing, which requires this same opt-in.
  - This is a required line in `vcluster.yaml`, not a nice-to-have — flag prominently in the spike script and carry it into any Phase 2 reconciler-generated values.
- **CSI ephemeral inline volumes (as opposed to PVC-based CSI) are underspecified in vcluster's docs.** `sync.fromHost.csiDrivers` defaults to `auto` (enables when the virtual scheduler is on) and syncs `CSIDriver` objects host→virtual read-only — documented in the context of PVC-based storage-aware scheduling. The SPIFFE CSI driver (`driver: csi.spiffe.io`) is used as an **ephemeral inline volume** on pod specs, not a PVC. Since pod specs are created against the virtual API server and the resulting pod object is what gets synced/rewritten onto the host node, the inline CSI volume block should pass through as opaque pod-spec data and be honored by the **host** kubelet/CSI driver regardless of whether the `CSIDriver` object itself is synced into the vcluster (that object mainly matters for scheduling/validation). This is architecturally plausible but **not a documented guarantee** — it's exactly what `spike-probe.sh` assertion 3 (below) needs to prove empirically, not assume.
- **The k8s distro is not enabled by default, contradicting the ADR's original assumption that "only the k8s distro remains" implied it was the automatic choice.** Checked directly against the chart (`helm show values loft-sh/vcluster --version 0.35.1`): `controlPlane.distro.k8s.enabled` defaults to `false`. With no distro enabled at all, the vcluster pod never becomes ready. `controlPlane.distro.k8s.enabled: true` must be set explicitly in `vcluster.yaml`.
- **The kubeconfig secret name is `vc-{release}`, not `vc-config-{release}`.** The chart creates *two* similarly-named secrets: `vc-config-{release}` (the rendered `vcluster.yaml` values, under key `config.yaml`) and `vc-{release}` (the actual kubeconfig, under key `config`, plus separate `client-certificate`/`client-key`/`token` keys). A substring match against secret names finds both; only the second is usable as a kubeconfig. The chart's own values-file comment ("vCluster will create it with `vc-NAME`") is correct, but easy to conflate with the config secret at a glance.
- **The generated kubeconfig points at `https://localhost:8443` and does nothing to make that reachable.** This only works out of the box via `vcluster connect`, which transparently runs `kubectl port-forward` in the background. Driving vcluster via Helm directly (no `vcluster` CLI installed, per the original plan) means the port-forward has to be started and tracked by hand — `spike-vcluster-up.sh` does this itself now.

#### Finding: Istio native sidecars break `buildSpireInjectionTemplate()` (real, not vcluster-specific)

Deploying a pod with `inject.istio.io/templates: "sidecar,spire"` initially failed outright: `spec.containers[1].image: Required value` / `spec.initContainers[1].name: Duplicate value: "istio-proxy"`. Root cause: Istio 1.29.1 auto-selects **native sidecars** (`istio-proxy` as a K8s-native `initContainers` entry with `restartPolicy: Always`) based on the API server's reported Kubernetes minor version. The vcluster's k8s distro reports a much newer version (`v1.36.0`) than the host (`v1.29.4+k3s1`), so istiod picks native-sidecar mode for the vcluster. `buildSpireInjectionTemplate()` and `buildIdentityProxyInjectionTemplate()` (`backend/internal/operator/istio_templates.go`) both hardcode a legacy `spec.containers: - name: istio-proxy` patch, which does not merge into a native-sidecar `initContainers` entry of the same name — Istio's template-merge logic treats it as an unrelated new container instead, producing an invalid pod.

**Workaround used in the spike**: `pilot.env.ENABLE_NATIVE_SIDECARS: "false"` on the istiod install, forcing legacy sidecar placement. This is not vcluster-specific scaffolding to throw away — it is evidence of a **latent gap in `istio_templates.go`** that would reproduce on any real (non-virtual) cluster once/if its Kubernetes version crosses whatever threshold makes Istio default to native sidecars.

**Fixed, independent of this ADR**: `reconcileIstiod` (`backend/internal/operator/platform_controller.go`) now pins `pilot.env.ENABLE_NATIVE_SIDECARS: "false"` on the host's own istiod install too. Chosen over teaching the injection templates to patch `initContainers` conditionally: Istio's own "Compatibility" auto-detection heuristic is itself the fragility here (the spike's host cluster and vcluster reported different Kubernetes versions and landed on different sidecar placement without any config change), so branching our template logic on that same heuristic would only relocate the fragility, not remove it. Orbit already solves the ordering problem native sidecars address — every chart-shipped deployment sets `proxy.istio.io/config: '{"holdApplicationUntilProxyStarts": true}'` (`charts/orbit/templates/{agents,frontend,identity,inference-gateway,opa-gateway,egress-gateway,policy-service,policy-gateway}/deployment.yaml`) — so nothing is forfeited by pinning legacy mode everywhere.

#### Finding: pod-to-pod mesh mTLS fails with `503`/connection-refused — resolved

`probe-client` → `probe-server` over the mesh (via the `probe-server` Service ClusterIP, PeerAuthentication `STRICT`) consistently returned `HTTP 503` with Envoy's own log showing `upstream reset: ... delayed connect error: Connection refused` — reproduced identically across two independent clean spike runs (full teardown/rebuild between them), so this was not a one-off flake or an artifact of interactive debugging.

**Root-caused on a follow-up session (2026-07-08) using a brand-new, separate `orbit-netrepro` k3d cluster** (same topology as the host: `rancher/k3s:v1.29.4-k3s1`, 1 server + 2 agents, default Flannel CNI, default kube-router network-policy controller) to both rule out state churn from the original debugging session and isolate variables one at a time:

- **Raw pod-to-pod TCP with no Istio at all works** — a host-native pod reached a vcluster-synced pod's IP directly, same-node and cross-node. This ruled out Flannel, kube-router, and the vcluster syncer's pod networking entirely.
- **Full Istio mesh mTLS with Istio's own default (Citadel) certs, STRICT PeerAuthentication, cross-node, via Service ClusterIP, works.**
- A non-mesh client curling a STRICT-mTLS pod's app port directly returns "connection reset" — reproduced as a **control**, entirely inside a single vcluster with no host/vcluster boundary involved. This is normal Istio STRICT-mode behaviour (iptables redirects inbound traffic to Envoy's listener, which refuses plaintext) and is almost certainly what the original spike's "unrelated host-native pod gets connection refused" observation actually was — a red herring, not evidence of a CNI gap.
- **Only the SPIRE-cert-provider case fails**, reproducing the original 503 exactly. With `curl -v` against the client's own sidecar, Envoy reports the real error directly: `TLS_error:...CERTIFICATE_VERIFY_FAILED:verify cert failed: SAN match`.
- **Root cause**: every chart-shipped service already carries a `DestinationRule` pinning `trafficPolicy.tls.subjectAltNames` to its own custom SPIFFE ID (see `charts/orbit/templates/identity/destination-rule.yaml`) — because without one, Istio's automatic-mTLS SAN validation falls back to the standard `spiffe://{trustDomain}/ns/{ns}/sa/{sa}` convention and will never match a custom-shaped ID. `spike-identity-wire.sh` wired the `ClusterSPIFFEID` so SPIRE **issues** a `devenv/{env-id}/...`-shaped cert, but nothing wired the matching `DestinationRule` so Envoy would **accept** it. That omission was the entire bug — not CNI, not kube-router, not the vcluster syncer.
- **Fix verified twice**: first against the isolated `orbit-netrepro` repro, then again end-to-end against this ADR's own `spike-probe.sh` re-run on the real host (`k3d-orbit-local`, see "Spike Execution — Results" below) — applying a `DestinationRule` with `subjectAltNames: ["spiffe://{trustDomain}/devenv/{env-id}/{synced-pod-name}"]` took assertion 5 from 503 straight to 200. `spike-identity-wire.sh`'s ClusterSPIFFEID stays as-is; `spike-probe.sh` now also applies the matching `DestinationRule` before asserting mTLS.
- **Phase 2 implication**: the devenvironment reconciler must template a `DestinationRule` (mirroring the `charts/orbit/templates/*/destination-rule.yaml` pattern) for every in-vcluster service that needs mesh mTLS, with `subjectAltNames` set to its `spiffe://{trustDomain}/devenv/{env-id}/...` identity. No CNI change, no vcluster networking option, and no k3d flag were needed.

The CoreDNS `kubernetes` plugin readiness symptom noted alongside the original mTLS failure **did not reproduce** in the minimal `orbit-netrepro` environment (CoreDNS was `Ready` throughout, Service DNS resolved correctly) or in the clean host re-run below — it is very likely unrelated to the mTLS root cause (e.g. transient to that spike run's resource pressure from installing the full Orbit platform alongside), not a shared cause. It is not being tracked as a blocking finding.

#### Finding: `sync.toHost.networkPolicies` works, but with substantial and variable latency

A `NetworkPolicy` created inside the vcluster reliably syncs to a real host-side object in `orbit-devenv-spike` — confirmed on two independent runs — but sync latency was highly variable, observed anywhere from ~15s to ~70s. Once synced, enforcement was correct: a probe pod could not reach a host control-plane service (`orbit-identity.orbit-system`) by ClusterIP, confirmed on both runs. `spike-probe.sh` polls for up to 90s rather than assuming a fixed short delay. This latency is itself worth flagging for the eventual reconciler design (decision 8's sleep/wake and any security-sensitive NetworkPolicy change should not assume near-real-time host enforcement).

#### What this means for the parity gate

The identity model (option C3 — the actual subject of this ADR's riskiest decision) is **validated**: host SPIRE attests vcluster-synced pods natively, issues real `devenv/`-prefixed SVIDs, and the CSI-mounted Workload API socket works exactly as designed. That is the headline result and de-risks the architectural choice.

**Update, same day, follow-up session**: the mesh-mTLS gap (spike question 5) is root-caused and fixed (missing `DestinationRule`, not a CNI/vcluster networking issue — see above), and the `istio_templates.go` native-sidecar gap is fixed in code (`backend/internal/operator/platform_controller.go`, `reconcileIstiod` now pins `pilot.env.ENABLE_NATIVE_SIDECARS: "false"`). Both fixes were verified end-to-end by re-running `spike-vcluster-up.sh` → `spike-identity-wire.sh` → `spike-istio-up.sh` → `spike-probe.sh` against the real host (`k3d-orbit-local`), not just the isolated repro cluster — see "Spike Re-run — Results" below. **The Phase 1 gate is now met.**

## Phase 2 Progress — First Slice (2026-07-08)

The Ring 1 prerequisites and a first vertical slice of the CRD + reconciler are implemented and verified end-to-end against the real host (`k3d-orbit-local`) — not just unit tests. This slice deliberately stops at a Ready vcluster; it does **not** yet install the in-vcluster Orbit platform (decision 2's `orbit-operator` chart + `OrbitPlatform` CR), which the ADR itself flags as self-referential ("this feature cannot be developed inside itself until it exists") and remains the next increment.

**Ring 1 (`backend/internal/operator/`):**
- `helm_interface.go` — `HelmInterface` extracted from the concrete `*HelmClient`, plus `HelmClientFactory` so a reconciler can be handed a per-namespace Helm client without constructing one inline (the exact gap called out in the Implementation section).
- `clock.go` — `Clock` interface + `realClock`; TTL/idle/sleep-wake logic reads time through it, so tests advance a fake clock instead of waiting.

**CRD + reconciler:**
- `devenvironment_types.go` — `OrbitDevEnvironment` CRD Go types (hand-written `DeepCopy`, matching the existing `OrbitPlatform`/`OrbitTenant`/`Connection` convention) plus the matching CRD manifest (`charts/orbit-operator/templates/crd-orbitdevenvironment.yaml`) and RBAC (`clusterrole.yaml`: the CRD, `resourcequotas`/`limitranges`, `persistentvolumeclaims`).
- `devenvironment_controller.go` — `DevEnvironmentReconciler` implements: namespace creation with `ResourceQuota`/`LimitRange`/owner+role labels; vcluster Helm install/upgrade/uninstall via the injected `HelmClientFactory`; TTL requeue and expiry (capped at a 7-day hard cap regardless of how large `spec.ttl` is extended); a finalizer so TTL-expiry deletion and direct `kubectl delete` converge on one cleanup path; and idle-timeout sleep / explicit wake, scaling every Deployment/StatefulSet in the namespace to zero and restoring their exact prior replica counts via an annotation. **Deliberately no additional devenv-specific NetworkPolicy**: `orbit-system`'s existing `default-deny-all` already fences the host control plane from anything in a `orbit-devenv-*` namespace (confirmed as a side effect of the Phase 1 spike's own assertion 6), and `sync.toHost.networkPolicies` already lets in-environment developers author their own — adding a redundant namespace-wide policy here would only reintroduce the kube-router `to: []` fragility noted above for no isolation gain.
- `devenvironment_csr.go` — decision 6's kubeconfig CSR fulfilment: `signKubeconfigCSR` validates and signs a PEM CSR against a supplied CA (pure `crypto/x509`, no cluster access), and `reconcileKubeconfigCSR` reads the vcluster's own `client-ca.crt`/`client-ca.key` from its `{release}-certs` Secret — confirmed empirically against a live vcluster's apiserver args (`--client-ca-file=/data/pki/client-ca.crt`) rather than assumed from vcluster's undocumented secret schema.
- A real design bug caught by testing, not just written correctly on paper: the first version of the sleep/wake state machine derived "should sleep" from `!spec.Awake || idle`, which meant an idle-triggered sleep (which does not touch `spec.Awake`) looked identical on the next reconcile to "still idle" and could never distinguish itself from "an external actor explicitly woke it" — since both leave `spec.Awake` at whatever it already was. Fixed by having idle-triggered sleep flip `spec.Awake` to `false` itself, so `spec.Awake` is the single source of truth for desired power state and wake is unambiguously "an external actor set it back to `true`."

**Verified against the real cluster** (`deploy/local/devenvironment.yaml`, a short-TTL/short-idle-timeout variant for test-time iteration): CR apply → `orbit-devenv-local-test` namespace with quota/limits/labels → vcluster Helm release → `status.phase: Ready` with `ingressHost`/`expiresAt` populated; idle timeout (patched to 30s for the live check) auto-slept the environment, flipped `spec.awake` to `false`, and scaled the vcluster `StatefulSet` to 0 replicas; patching `spec.awake` back to `true` woke it and restored 1 replica; deleting the CR uninstalled the Helm release and deleted the namespace with nothing orphaned (`helm list` empty, namespace gone); killing the operator pod mid-provision and letting it restart converged to `Ready` without manual repair. The host platform (`orbit-system`, `orbit-operator`) was left untouched throughout. Unit tests (`devenvironment_controller_test.go`, `devenvironment_csr_test.go`) cover the same paths against a fake client/Helm/clock, plus the CSR-signing edge cases (malformed CSR, tampered signature, no private-key material ever produced) per the Implementation section's Ring 1 test plan.

## Phase 2 Progress — Second Slice: In-Vcluster Orbit Platform Install (2026-07-08)

This slice closes the biggest gap the first slice left open: `reconcileReady` no longer stops at a bare `Ready` vcluster — it now installs the `orbit-operator` chart *inside* the vcluster and applies an `OrbitPlatform` CR (`spire.enabled: false`, per decision 3/C3) plus a seeded `OrbitTenant`, exactly as decision 2 describes. Verified end-to-end against the real host (`k3d-orbit-local`), not just unit tests.

**New code (`backend/internal/operator/`):**
- `devenvironment_platform.go` — `VClusterRestConfig` extracts the vcluster's own kubeconfig from its `vc-{release}` Secret and rewrites the `server` field from the chart's default `https://localhost:8443` (which only works via `vcluster connect`'s background port-forward) to `https://{release}.{namespace}` — confirmed **empirically against a live vcluster** that its own server certificate carries `{release}` and `{release}.{namespace}` as SANs specifically for this in-cluster access pattern, and that the two-label short form resolves correctly from any namespace via the default `svc.cluster.local` DNS search suffix. `reconcileInVClusterPlatform` then builds a `client.Client` + `HelmInterface` against that rest.Config, installs `orbit-operator` (now baked into the operator image — see Dockerfile change below), and applies `OrbitPlatform`/`OrbitTenant`. `hostTrustDomain` reads the trust domain from the **host's own** `OrbitPlatform` CR (cluster-scoped, one per cluster) rather than hardcoding or parameterizing it — every in-vcluster Istio must agree with whatever trust domain the host SPIRE actually issues `devenv/`-prefixed SVIDs under (option C3).

Deliberately hand-built Deployments/Services rather than a Helm chart or Tier 1/2's LDAP-backed Dex+glauth config: ephemeral (`emptyDir`) storage and a single Dex static-password user (`dev@orbit.local.clearroute.io` / `password`, matching Tier 1/2's own test credentials) are enough to exercise the real install path. **Two real bugs found only by testing against the live cluster, not caught by unit tests or code review:**

1. **`ORBIT_DEVENV_IMAGE_REGISTRY` never reached the pod.** The fix was first written as a `cmd/operator/config/development.yaml` entry, following that file's own doc comment ("used by the operator pod in local cluster deployments"). It never took effect — `orbit-operator`'s Deployment sets no `APP_ENV`, so `config.Environment()` (`backend/internal/platform/config/config.go`) falls back to `defaultEnvironment = "production"`, and `production.yaml` doesn't exist, so **only `base.yaml` is ever loaded in the actual k3d deployment.** `development.yaml` is dead code for every field, not just this one — every other operator-specific dev override in this codebase (`ORBIT_LEADER_ELECTION`, `ORBIT_OPA_IMAGE`, `ORBIT_OPA_LOG_LEVEL`) already goes through an explicit env-var override in `config.go`'s `Current` func, sourced from a chart value templated into the Deployment's `env:` block (`charts/orbit-operator/templates/deployment.yaml`) — never through an APP_ENV-keyed YAML file. Fixed by following that exact pattern: `values.yaml`'s new `devEnv.imageRegistry`, templated as `ORBIT_DEVENV_IMAGE_REGISTRY`, read by `config.go`, set in `deploy/local/operator-values.yaml`. The stray `development.yaml` entry was removed; `local.yaml`'s entry was kept (that file is for the separate, genuinely APP_ENV-driven "run the operator binary directly on a host machine" workflow).
2. **The namespace `LimitRange`'s default container memory limit (512Mi) rejected istiod outright.** istiod's own chart defaults to a 2Gi memory *request* with no explicit limit; Kubernetes requires `limit >= request` on every container, and admission fails the pod immediately if the `LimitRange`-supplied default limit is smaller than an explicit request — not a scheduling failure, a synchronous `403` at pod-create time (surfaced first as `vcluster`'s syncer logging `SyncError: ... must be less than or equal to memory limit of 512Mi`, discovered by chasing why `istiod`'s Pod never appeared even as `Pending` on the host — it was never even accepted by the *vcluster's own* API server). Fixed by raising `devEnvDefaultContainerMemoryLimit`/`CPULimit` (512Mi/500m → 3Gi/2 cores) and the namespace `ResourceQuota` ceiling accordingly (16Gi/8 cores → 24Gi/12 cores), and — to avoid every unspecified-resource fixture container now claiming that much larger default — giving the Postgres/Redis/Dex fixtures their own modest explicit `Resources` instead of falling through to the `LimitRange` default at all.

**Verified against the real cluster** (`deploy/local/devenvironment.yaml`): CR apply → vcluster `Ready` → in-vcluster `orbit-operator` pod `Running` → `OrbitTenant "devenv"` reaches `Ready` with its OIDC issuer pointed at the fixture Dex → in-vcluster `OrbitPlatform "orbit"` reconciling with SPIRE correctly skipped entirely (no `spire`/`spire-crds` install attempts in the logs) and `istio-base`/`istiod` both reaching `Running` inside the vcluster — the exact release-sequence proof the ADR's Priority-1 next step called for. Also observed, unprompted: the idle-timeout auto-slept the environment mid-session (confirming decision 8's sleep logic fires correctly even while a nested install is in flight), and waking it back up correctly restored the vcluster control-plane `StatefulSet` — the **already-running synced workload pods (istiod, the fixtures) were never disrupted by the control-plane's own restart**, since they are independent host-native Pod objects once scheduled, not host-side Deployments the reconciler's `scaleWorkloads` would find and touch. This is a fidelity point worth flagging for Phase 2's remaining local acceptance checklist, not a bug: **decision 8's sleep, as implemented, only actually scales the vcluster control-plane `StatefulSet` itself** (there being no host-native Deployments for in-vcluster workloads to scale) — the compute cost of a "slept" environment that has installed real workloads is smaller than a naively-read decision 8 implies, but should be measured, not assumed, before the success metric ("Idle-environment cost: sleeping environment consumes storage only") is called met.

The `orbit-operator` chart itself needed one Dockerfile change to make this slice possible at all: it was never baked into the operator image (`Dockerfile.operator` only copied `charts/orbit-platform/` and `charts/orbit/`) because no code path had ever needed to install it from anywhere other than a human running `helm install` by hand. ## Phase 2 Progress — Third Slice: Host Identity Wiring, CA-Root Isolation, and a New JWT Blocker (2026-07-08)

Picked up in a fresh session with the host (`k3d-orbit-local`) already up. Four real, verified fixes landed (three on the identity/mesh path, one an unrelated pre-existing operator crash-loop), and a fourth, deeper blocker was found and precisely characterized but not yet resolved.

**Fix 1 — `orbit-platform` chart installed `ClusterSPIFFEID` resources unconditionally, breaking every in-vcluster install outright.** `reconcileOrbitPlatform` (`platform_controller.go`) always installs the `orbit-platform` chart regardless of `p.Spec.SPIRE.Enabled`, and `charts/orbit-platform/templates/clusterSpiffeIDs.yaml` templated its six `ClusterSPIFFEID` resources with no gate at all. Inside a devenvironment's vcluster, `spire.enabled: false` (decision 3/C3) means `spire-crds` is correctly skipped — but the `orbit-platform` Helm install still tried to create `ClusterSPIFFEID` objects, and failed outright with `no matches for kind "ClusterSPIFFEID" in version "spire.spiffe.io/v1alpha1": ensure CRDs are installed first`. This looped forever; `orbit-platform`, `gateway`, and `orbit` never installed. **Fixed**: added a `spire.enabled` value (default `true`, matching the CR's own default) to `charts/orbit-platform/values.yaml`, gated the whole of `clusterSpiffeIDs.yaml` behind `{{- if .Values.spire.enabled }}`, and wired `"spire": {"enabled": p.Spec.SPIRE.Enabled}` into `reconcileOrbitPlatform`'s values overlay. Verified with `helm template`: renders 6 `ClusterSPIFFEID` resources with the default (host installs unaffected) and 0 with `spire.enabled=false`. Verified live: `deploy/local/devenvironment.yaml` re-provisioned cleanly, in-vcluster `orbit-platform` install succeeded, `gateway` release began installing (previously never reached).

**Fix 2 — host `ClusterSPIFFEID` for devenv workloads (decision 3/C3, first half of the old Next Steps item 3).** Once `orbit-platform` could install, the release sequence progressed to `gateway` — which hung indefinitely on its readiness probe. Root cause: every pod a vcluster syncs onto the host lands in one flattened host namespace (`orbit-devenv-{id}`), and none of the host's existing `ClusterSPIFFEID`s (scoped to `istio-system`/`orbit-system` by literal name) match it — so the gateway's `PILOT_CERT_PROVIDER=spire` pilot-agent waited forever on a SPIRE registration entry that could never arrive, exactly the ordering hazard the ADR already documents for the host's own gateway-after-orbit-platform sequencing, now recurring one layer down. **Fixed**: new `backend/internal/operator/devenvironment_identity.go` — `ensureHostIdentity`/`deleteHostIdentity`, an unstructured (no new Go SDK dependency) host-side `ClusterSPIFFEID` per environment, named `devenv-{env-id}`, `namespaceSelector: matchLabels: {orbit.io/devenv: {env-id}}` (reusing the label `ensureNamespace` already sets — no new selector convention needed), template `spiffe://{trustDomain}/devenv/{env-id}/{{ .PodMeta.Name }}` exactly as the Phase 1 spike proved. Wired into `reconcileReady` right after `ensureNamespace` (before `ensureVCluster`, so it exists before any workload could request an SVID) and into `handleDeletion` for cleanup. **Verified live**: re-provisioned `local-test`; the gateway pod's istio-proxy log now shows `Existing workload SDS socket found... Workload is using file mounted certificates` — the host SPIRE agent successfully attested the synced pod and issued a `devenv/local-test/...`-scoped SVID through the CSI socket. This is the C3 identity model working for a second, independent workload type beyond the Phase 1 spike's hand-built probe pods.

**Blocker found and root-caused: gateway's XDS connection to the in-vcluster `istiod` failed certificate validation — caused by the HOST's istiod clobbering the devenv's own CA-root ConfigMap.** With its own workload SVID in hand, the gateway's pilot-agent still couldn't reach `Ready` — Envoy's control-plane (XDS) connection to `istiod.istio-system.svc:15012` failed repeatedly with `x509: certificate signed by unknown authority`.

Diagnosis, empirical and load-bearing (not guessed): confirmed the host's own real `gateway` pod uses the identical `PILOT_CERT_PROVIDER=spire` setting with **zero** occurrences of this error in 8 hours of logs — ruling out a generic incompatibility — then confirmed (via `pilot-agent request GET clusters/listeners/certs` on both pods) that the host gateway is **genuinely XDS-synced** (real cluster/listener data, not just readiness-probe-green), so the mechanism does work — somewhere. Fetching the actual live TLS handshake with `openssl s_client` against `istiod:15012` from inside the devenv gateway pod, then checking whether the ConfigMap-mounted `/var/run/secrets/istio/root-cert.pem` (`istio-ca-root-cert`) could verify that live leaf cert (`openssl verify`) — it could not. Comparing SHA-256 fingerprints of the devenv's and the host's `istio-ca-root-cert` ConfigMaps: **byte-for-byte identical.** Root cause: **Istio's istiod runs a namespace controller that copies its own self-signed CA-root ConfigMap into every namespace it discovers, cluster-wide, by default** — with no scoping, the HOST's istiod was propagating its own root into the devenv's flattened host namespace (`orbit-devenv-{id}`), where the in-vcluster istiod is independently trying to publish its *own*, different, self-signed root under the exact same object name. The host's write wins, so the devenv's gateway ends up trusting the wrong istiod's root entirely.

**Fixed**: `reconcileIstiod` (`platform_controller.go`) now sets `meshConfig.discoverySelectors` — excluding `orbit.io/role: devenv` namespaces — whenever `p.Spec.SPIRE.Enabled` is true (i.e. only on host-type installs; an in-vcluster istiod has no devenv-namespace concept and needs no exclusion). This scopes the host's istiod's entire namespace-watching (not just the CA-root propagation) away from devenv namespaces, which is also a strict isolation improvement independent of this bug — the host's mesh control plane has no business discovering devenv-internal namespaces at all. Applied live via a manual `helm upgrade istiod ...` (a values-only change; `HelmClient.InstallOrUpgrade`'s version-skip logic — see this ADR's Spike Re-run notes — means the operator itself won't reapply this until the next real chart-version bump) plus a `kubectl rollout restart` to force istiod to reload; verified the host `istio-ca-root-cert` ConfigMap's `discoverySelectors` took effect and the host's own mesh stayed healthy throughout.

**Second-order bug this exposed, also fixed**: excluding the host from devenv namespaces means *nothing* publishes a plain-named `istio-ca-root-cert` ConfigMap there — the in-vcluster istiod's own copy syncs down under a **translated** name (`istio-ca-root-cert-x-istio-system-x-vcluster`, vcluster's normal non-core-resource sync convention), but every pod istiod's own sidecar-injection webhook mutates carries a volume reference *hardcoded to the plain literal name* — a reference baked in at admission time inside the vcluster's own API server, which the vcluster syncer does not rewrite when it syncs the already-mutated pod out to the host. Before the fix above, this went completely unnoticed: the host's clobbering write "accidentally" satisfied the mount (with the *wrong* content). After the fix, the mount fails outright (`FailedMount`, ConfigMap not found) — arguably a better failure mode (loud, not silently wrong), but still blocking. **Fixed**: new `mirrorIstioCARootCert` in `devenvironment_identity.go` — best-effort, non-fatal, wired into `reconcileReady` right after the in-vcluster platform install — copies the translated-name ConfigMap's data into a plain-named sibling in the same host namespace, keeping them in sync on every reconcile.

- **`status.LastActivityAt` was never updated by any activity signal** — only by the wake path itself (`reconcilePowerState`, the one `s.LastActivityAt = &t` assignment). This session picked up the fourth slice's "resolve the mystery, or pivot" fork and did the former, by reading Istio 1.29.1's actual authentication source rather than continuing to probe live cluster state:

- **`KubeJWTAuthenticator` (`security/pkg/server/ca/authenticate/kubeauth/kube_jwt.go`) does not select a validation cluster from `ISTIO_META_CLUSTER_ID` (Envoy Node metadata) at all.** It reads a distinct gRPC metadata header literally named `"clusterid"` (`ExtractClusterID`, via `metadata.FromIncomingContext`) — a wire-level header, not the XDS request body field the fourth slice's `overwriteClusterInfo`/injection-webhook investigation was chasing. Grepping the entire `istio/istio` source tree for this header's only two call sites (`security/pkg/server/ca/node_auth.go` — the CA server — and `pilot/pkg/bootstrap/server.go:407`, which wires the identical authenticator chain into the XDS server) found **no code anywhere in istio-agent/pilot-agent that ever sets it** on an outbound XDS bootstrap connection. `getKubeClient`'s own logic treats an unset (`""`) cluster ID as "assume single cluster" and always returns the **primary** client. - **This was verified empirically before being confirmed by source, at escalating and ultimately unjustified cost.** The remote cluster's RBAC was widened twice this session (first to a `pods/nodes/services/namespaces/endpoints/endpointslices` metadata-only grant, then — approved explicitly after that proved insufficient — to a full read-only mirror of istiod's own `ClusterRole`, including cluster-wide `Secrets`) chasing istiod's own "remote cluster host failed to sync" log line, on the hypothesis that an unsynced remote cluster was why JWT validation fell back to primary. The remote cluster DID reach "sync complete" under the full grant — and the JWT authentication failure was **completely unchanged**, still validating against `"Kubernetes"` (primary), confirming "synced" and "selected for JWT auth" are unrelated Istio concepts. **Both RBAC widenings have been fully reverted** (`ensureTokenReviewClusterRole` is back to `tokenreviews:create` only, its original minimal scope) — the wider grant bought zero functional progress while genuinely increasing blast radius (every devenvironment's in-vcluster istiod could otherwise read every Secret on the host cluster, well beyond this ADR's "one namespace" isolation model).

**3. **Design decisions made without further discussion, recorded here for review:**
- **Ownership is strict, no admin bypass on single-resource actions.** `GetEnvironment`/`ExtendEnvironment`/`DestroyEnvironment`/`Kubeconfig` all return `ErrNotFound` for a non-owner caller, full stop — there is no admin override. `devenvironments:admin` only gates a separate `GET /v1/dev-environments/all` listing endpoint (`ListAllEnvironments`). An admin needing to inspect or destroy someone else's environment today has to do it via `kubectl`/the operator, not this API. Revisit if that turns out to be a real workflow gap.
- **The registry row and the CR are not created atomically** (no distributed transaction across Postgres and the Kubernetes API) — `CreateEnvironment` rolls the registry row back (soft-delete) if CR creation fails, so a failed create never leaves an invisible quota consumer behind, but a crash between the two writes is a theoretical (if narrow) leak window. Consistent with this codebase's general posture elsewhere (e.g. the eighth slice's `orbit-frontend-secrets` "create-once-leave-alone" idiom) of tolerating eventual-consistency gaps this size rather than adding saga/compensation machinery for a low-traffic internal admin action.
- **List operations self-heal the registry against the CR's existence.** If a `GET` finds a registry row whose CR is gone (TTL expiry deleted it, or an out-of-band `kubectl delete`), the row is marked deleted on the read path rather than surfaced as a phantom environment — the CR, not Postgres, is the source of truth for "does this environment still exist."
- **Env IDs are a random 16-hex-character string** (truncated UUID, not a human-chosen slug), sized to leave headroom under the 63-character Kubernetes namespace-name limit once prefixed with `orbit-devenv-`.

## Phase 3 Progress — Second Slice: vcluster API Server External Reachability Resolved and Verified Live (2026-07-10)

Resolved the ADR's last open architectural question (the first slice's "known gap," above): how a developer's `kubectl`, running outside the host cluster, reaches a specific environment's vcluster API server. The design landed on exactly what the first slice's writeup anticipated — SNI-based TLS passthrough on the same shared Istio ingress gateway that fronts the app traffic, on a distinct port — but three real, live-only-reproducible bugs had to be found and fixed before it actually worked end-to-end. All code lives in a new file, `backend/internal/operator/devenvironment_ingress.go`, wired into `reconcileReady` as `ensureDevEnvAPIAccess`.

**Shape of the fix:**
- **One shared Gateway** (`devenv-api-gateway`, `istio-system`), created once and environment-agnostic: a single `TLS`/`PASSTHROUGH` listener on port 16443 (not 6443 — see Bug 0), matching the same Istio ingress gateway workload (`app: gateway`) the host's own app Gateway selects. `reconcileGateway` (`platform_controller.go`) grows a matching Service port, gated on `p.Spec.SPIRE.Enabled` so an in-vcluster gateway release (which has no vcluster of its own to route to) never grows it.
- **One VirtualService per environment**, SNI-matching `status.ingressHost` and routing to that environment's `vcluster.{namespace}.svc.cluster.local:443`.
- **One ServiceEntry per environment**, registering that same host as `resolution: DNS`, `location: MESH_EXTERNAL`.
- **`controlPlane.proxy.extraSANs`** added to the vcluster Helm values (`ensureVCluster`), carrying `status.ingressHost` so the vcluster's own proxy certificate is valid for that name.
- **`assembleKubeconfig`** (`internal/devenvironments/service.go`) now sets `server:` to a new, separately-configured `apiServer.externalAddress` (host:port of the shared gateway's passthrough listener — `localhost:16443` locally) and `tls-server-name:` to `status.ingressHost`. These are deliberately decoupled: `tls-server-name` only needs to exist inside a TLS ClientHello/certificate SAN, never in DNS, so `status.ingressHost` (`{env}.dev.orbit.local`) staying unresolvable is fine — a design property confirmed, not merely hoped for, by the live verification below.

**Bug 0 — port 6443 collides with k3d's own automatic k3s-apiserver-through-loadbalancer proxying.** The natural first choice of port for a "Kubernetes API passthrough" is 6443, but `docker ps` showed k3d had already claimed container port 6443 on its `serverlb` for the HOST cluster's own apiserver, independent of anything in `k3d-config.yaml`. **Fixed** by moving to 16443 throughout (operator constant, `assembleKubeconfig` config default, `infrastructure/bootstrap/k3d-config.yaml`'s new port mapping). The mapping itself was added to the running cluster non-destructively via `k3d cluster edit orbit-local --port-add 16443:16443@loadbalancer` (recreates only the `serverlb` container, confirmed live: the existing `local-test` environment and its nodes were unaffected).

**Bug 1 — the per-environment VirtualService, originally placed in the environment's own namespace for automatic cleanup-on-delete, was invisible to the host istiod that actually programs the shared gateway.** `reconcileGateway`'s `discoverySelectors` (added for an unrelated reason — keeping the host istiod from clobbering each environment's own CA-root ConfigMap, see the Phase 2 sixth-slice notes) exclude `orbit.io/role=devenv` namespaces from istiod's discovery *entirely*, not just for ConfigMaps. Confirmed live: the VirtualService existed, the Gateway existed, but `pilot-agent request GET config_dump` on the gateway pod showed no `0.0.0.0_16443` listener at all. **Fixed** by moving the VirtualService (and the ServiceEntry, Bug 2) into `devEnvAPIGatewayNamespace` (`istio-system`) instead, named per-environment (`devenv-api-{env-id}`) since they no longer share the environment's own namespace to disambiguate. This forfeits automatic cleanup via namespace deletion, so `deleteDevEnvAPIRoute` removes both explicitly from `handleDeletion`, the same pattern `deleteHostIdentity` already uses for the (also namespace-external) host ClusterSPIFFEIDs.

**Bug 2 — the same `discoverySelectors` exclusion also hides the devenv namespace's actual Kubernetes Services, not just its Istio config, so istiod never turns the vcluster Service into an Envoy cluster at all.** Once Bug 1's listener appeared, connections were accepted (SNI matched) and then immediately reset — `pilot-agent request GET config_dump`'s cluster dump had no entry for `outbound|443||vcluster.orbit-devenv-local-test.svc.cluster.local` whatsoever; the gateway's `tcp_proxy` filter was referencing a cluster istiod had never configured. **Fixed** with a `ServiceEntry` per environment (`ensureDevEnvAPIServiceEntry`): a `ServiceEntry` is a standalone Istio config object, not derived from Kubernetes Service discovery, so it exists regardless of the namespace exclusion, and `resolution: DNS` means Envoy re-resolves the host via cluster DNS (CoreDNS, unaffected by `discoverySelectors`) at connection time instead of depending on istiod-pushed endpoints.

**Bug 3 — `location: MESH_INTERNAL` on that ServiceEntry made Envoy attempt Istio auto mTLS on top of the already-TLS-passthrough bytes, which the sidecar-less vcluster apiserver cannot participate in.** With Bugs 1–2 fixed, connections were *still* being reset. The cluster's `transport_socket_matches` showed an `istio`-tlsMode branch attempting an inner mTLS handshake — `MESH_INTERNAL` tells Istio "this host is part of my mesh," triggering its usual per-destination mTLS auto-detection regardless of whether the actual backend has a sidecar. **Fixed** by setting `location: MESH_EXTERNAL` instead, which disables that auto-upgrade; confirmed live via the cluster's `transport_socket`/`transport_socket_matches` going from populated to `null` (plain passthrough) after the change.

**Bug 4 — a kubeconfig's `tls-server-name` does double duty: it is both the SNI value a client sends AND the hostname a standard TLS client verifies the server's presented certificate against.** With Bugs 0–3 fixed, a raw `curl --resolve … -k` (skipping verification) confirmed routing worked end-to-end — a real Kubernetes API response (`403: system:anonymous cannot get path "/"`) came back from exactly the right environment's apiserver. But a real `kubectl` (which does not skip verification) failed with `x509: certificate is valid for kubernetes.default…, vcluster…, not local-test.dev.orbit.local`: the vcluster proxy's own certificate never carried the ingress host as a SAN. **Fixed** by adding `controlPlane.proxy.extraSANs: [{ingressHost}]` to `ensureVCluster`'s Helm values — vcluster's `proxy` component (not `distro.k8s.apiServer`) owns the certificate actually presented on the Service port used here.

**A fifth, non-code gotcha worth recording for whoever touches this next: `extraSANs` cannot be applied to an already-provisioned vcluster via `helm upgrade`.** vcluster persists its PKI (etcd/proxy certs) on the pod's PVC across restarts; changing the desired SAN set via upgrade left the persisted certificate mismatched with what vcluster now wanted to validate, and it crash-looped (`failed to write or validate certificate "etcd-server"`) rather than regenerating. Consistent with decision 8's own stated recovery philosophy ("delete and re-provision, never repair in place"), the fix was deleting and recreating the environment, not attempting an in-place repair — this only matters for environments that existed before this slice's code; freshly-provisioned environments generate PKI with the correct SANs from the start.

**Full live verification, end to end, against a freshly re-provisioned `local-test` environment:**

## Phase 2 Progress — Ninth Slice: A Real Provisioning Attempt Surfaces Three Blocking Bugs and Unmasks a Fourth (2026-07-10)

This slice's premise was simple — provision a devenvironment through the real Orbit UI on `k3d-orbit-local` and watch it converge, the way an actual user would use the feature the eighth/Phase-4 slices declared done. **Bug 1 — no orbit-system service in any devenvironment has ever actually gotten an Istio sidecar injected.** `ensureInVClusterSecrets` (`devenvironment_fixtures.go`) creates the in-vcluster `orbit-system` namespace to seed `orbit-secrets` — and does so with no labels at all. ## Phase 2 Progress — Tenth Slice: Bug 4 Root-Caused and Fixed — a SPIFFE-ID Selector Collision, Not a Silent Cert Fallback (2026-07-10)

Bug 4 was never a fallback to Istio's default self-managed cert — SPIRE was attesting the workload correctly the entire time. The ninth slice's read of the evidence (`ns/{ns}/sa/{sa}`-shaped SAN, described there as "Istio's own default automatic-mTLS identity convention") was a reasonable but wrong inference from the SAN shape alone, because that exact shape is *also* what one of Orbit's own `ClusterSPIFFEID`s mints — just the wrong one.

**Root cause: every devenvironment workload matches two `ClusterSPIFFEID`s at once, and SPIRE's SDS handler resolves the ambiguity by entry-creation order, not by which one is "correct."** `charts/orbit-platform/templates/clusterSpiffeIDs.yaml`'s `istio-sidecar` `ClusterSPIFFEID` is scoped *by exclusion* — every pod labeled `spiffe.io/spire-managed-identity: "true"` gets `spiffe://{trustDomain}/ns/{ns}/sa/{sa}` unless its namespace is the host's own `orbit-system` or labeled `orbit.io/role: tenant`. It was written before devenvironments existed and was never taught about them: a devenvironment's flattened host namespace carries `orbit.io/role: devenv` (`devenvironment_controller.go`'s `ensureNamespace`), which isn't in either exclusion, so every chart-shipped devenv service — carrying the identical `spiffe.io/spire-managed-identity: "true"` label — slips through and matches this host-wide `ClusterSPIFFEID` *in addition to* its own correct, devenv-scoped one (`devenv-{env}-system`, from `devenvironment_identity.go`). Confirmed directly in `spire-controller-manager`'s own logs from the ninth slice's `verify-quota-fix` environment — the *same pod UID* got two entries:

```
spiffeID: spiffe://orbit.test/ns/orbit-devenv-verify-quota-fix/sa/orbit-policy-service-x-orbit-system-x-vcluster   (leaked host ID, logged first)
spiffeID: spiffe://orbit.test/devenv/verify-quota-fix/system/policy-service                                        (correct devenv ID, logged one line later)
```

Per SPIRE's own SDS handler (`pkg/agent/endpoints/sdsv3/handler.go`), the ambiguous `"default"` resource name Envoy/istio-agent requests resolves to `upd.Identities[0]` — whichever entry SPIRE's in-memory workload update happened to register first for that attested workload, with no notion of which `ClusterSPIFFEID` is "the intended one." In the ninth slice's run, the leaked `ns/sa` entry landed first and won; that's the SAN that shipped. This also explains the "workload is not authorized for the requested identities [\"default\"]" log line the ninth slice flagged: that's SPIRE correctly rejecting the SDS request during the brief startup window before `spire-controller-manager` has created *either* entry yet (`upd.Identities` empty) — a benign, self-resolving race, not a permanent failure; it stops the moment the first entry lands, silently, in whichever order that happens to be.

**Fixed**: added `devenv` alongside `tenant` to `istio-sidecar`'s `orbit.io/role NotIn` exclusion list — one line, matching the exact pattern already used for tenant namespaces (which needed the same exclusion for the same reason: tenant workloads have their own tenant-scoped `ClusterSPIFFEID`s). Verified via `helm template` (renders with `devenv` in the exclusion) and live: re-provisioned a fresh environment, confirmed via `spire-server entry show -selector k8s:pod-uid:{uid}` exactly **one** entry for `orbit-policy-service`'s pod (`spiffe://orbit.test/devenv/verify-bug4/system/policy-service`), confirmed Envoy's own `/certs` endpoint serves that SAN on every request (not just by luck of ordering), and confirmed `orbit-agents`' own startup log shows route-scope registration succeeding against `orbit-policy-service` with no `CERTIFICATE_VERIFY_FAILED`/SAN-mismatch anywhere in either side's `istio-proxy` logs — the exact failure mode the ninth slice hit is gone.

**A second bug found while trying to verify the first fix, not devenv-identity-specific but load-bearing for every local chart edit in this operator: `HelmClient.InstallOrUpgrade`'s "skip if already at target version" optimization (`helm.go`) checked the wrong version.** The check compared the *loaded chart's own* `Chart.Metadata.Version` (from `Chart.yaml`, always non-empty, and unchanged by editing a template) against the deployed release's chart version — not the `chartVersion` *request parameter*, which is genuinely empty for every local chart (`orbit-platform`, `orbit`, `orbit-operator` — all installed with `repoURL=""`, `chartVersion=""`) and only ever non-empty for pinned remote charts (SPIRE, Istio). The existing comment already documented the intended behavior ("local charts... we always upgrade so local edits are picked up immediately") — the code just checked the wrong variable, so it never did that: rebuilding the operator image with edited local chart templates (exactly what fixing the `ClusterSPIFFEID` above required) silently kept serving the **old** chart content forever, because the freshly-loaded chart's `Metadata.Version` trivially always equals itself. Caught here because the first attempt to verify the `ClusterSPIFFEID` fix live — rebuild operator, restart, re-provision — showed the *stale* selector still on the live object despite the correct content being confirmed present on disk inside the running pod (`md5sum` matched the fixed source file exactly). **Fixed**: the skip condition now checks the `chartVersion` parameter instead of `chrt.Metadata.Version`, matching the comment's stated intent exactly. Verified live: `orbit-platform`'s host release went from stuck at revision 1 (from cluster bootstrap, five-plus hours earlier) to upgrading on every reconcile once the fix was deployed, and the corrected `ClusterSPIFFEID` selector reached the live object (`namespacesIgnored: 2`, confirmed via `kubectl get clusterspiffeid istio-sidecar -o yaml`). No regression to the skip's actual purpose (avoiding SPIRE/Istio pre/post-upgrade hooks firing every reconcile on *remote* pinned charts) — that path is untouched, since remote charts always pass a non-empty `chartVersion`.

Updated priority order for whoever picks this up next:

1. **Not devenv-specific, but blocking a fully-green environment**: build and push `orbit-tool-gateway`/`orbit-tool-gateway-publisher` images for this cluster, and fix the `Makefile`'s `REDEPLOY_PLATFORM_SERVICES` gap (same gap affects the host's own installation).
2. **Not investigated, low priority**: `orbit-opa-gateway`'s intermittent `/health` 500s (reproduces on the host too).
3. **Worth a follow-up look, not urgent**: now that local-chart edits always trigger a real `helm upgrade` on every `OrbitPlatform` reconcile (every CR change, plus the 5-minute periodic recheck), the `orbit-platform`/`orbit`/`orbit-operator` releases will accumulate Helm release-history revisions steadily over a long-running cluster's lifetime. Helm's own history is unbounded by default; low priority because it costs only Secret storage, not workload disruption (confirmed live: repeated upgrades of identical content did not restart any pods), but worth capping with `--history-max` at some point.

## Amendment (2026-07-10): Path-Based App Ingress for Real Infrastructure

**Decision changed:** on real (non-k3d) infrastructure, a dev environment's browser-facing Orbit UI/API is reachable at a single shared hostname with the environment ID as a path prefix — `https://orbit.dev.clearroute.io/{env-id}` — instead of the per-environment subdomain scheme in Architecture step 5 and decision 6 above (`{env-id}.dev.{domain}`). This supersedes those two references for real infrastructure; the k3d/local default they describe is unchanged pending a follow-up decision on whether it converges to the same scheme (open question, below).

**Why:** a single, fixed hostname needs one DNS record and one TLS certificate provisioned once, rather than a wildcard DNS record and wildcard certificate that must be authorized/provisioned for `*.dev.clearroute.io` before the first environment can exist. The per-subdomain scheme is not wrong, just a heavier one-time provisioning ask on real infrastructure than on a throwaway k3d cluster.

**This is a routing-mechanism change, not just a hostname change.** The existing subdomain scheme works today (`devenvironment_ingress.go`, for the *kubectl API* route only — see below) as SNI-matched **TLS passthrough**: the shared gateway never decrypts, it reads the `ClientHello`'s SNI and forwards raw bytes. A path prefix is invisible at the TLS layer — it only exists in the HTTP request line — so path-based routing requires the *opposite*: the shared gateway must **terminate TLS** for app traffic and route on `uri: prefix: /{env-id}` via a per-environment Istio `VirtualService`, the same idiom `devenvironment_ingress.go` already uses for SNI matching, just at L7 instead of L4.

**Scope: app UI/API only, not the kubectl API-access route.** Decision 6's kubeconfig flow routes `kubectl` to each environment's vcluster API server via a *separate* shared TLS-passthrough listener on port `16443`, matched purely on SNI (`ensureDevEnvAPIRoute`). That mechanism has no path concept at all — a raw Kubernetes API client speaks TLS directly to `server:` in the kubeconfig, with no HTTP path routing involved — and is unaffected by this amendment. `status.ingressHost` currently backs both the app hostname (decision 1) and the kubectl SNI value (decision 6) with one field; implementing this amendment splits that into two independent identifiers: an opaque `{env-id}` used as an HTTP path segment for the app route, and (unchanged) `{env-id}.dev.{domain}` used purely as an SNI/certificate-SAN value for the kubectl route — the latter never needs to be a resolvable DNS name (already true today, per the Phase 3 "Second Slice" verification above) or a browser-facing URL at all.

**Known blocker, not yet solved — flagging so the next slice starts from reproduction, not rediscovery:** `frontend/next.config.ts` sets no `basePath`, and Next.js's `basePath` is a **build-time** setting baked into the compiled asset manifest — there is no supported way to override it per running container via an env var. Per decision 4, every dev environment installs the *same built image* (`spec.ref` selects one shared chart/image version), so a different `/{env-id}` prefix cannot be baked into each environment's identical bits. Concretely: without a per-env basePath, the in-vcluster frontend emits asset requests (`/_next/static/chunks/...`) with no env-id prefix at all — routing `orbit.dev.clearroute.io/{env-id}/*` to environment A's frontend gets the initial HTML to load, but its hydration/asset requests go out unprefixed, indistinguishable at the gateway from environment B's identical unprefixed asset requests. There is no path segment left to route those on. Fixing this needs one of:
- A gateway-level rewrite that strips the prefix on the way in and re-injects it via an `X-Forwarded-Prefix`-style header, paired with Next.js middleware that reads that header and rewrites asset/link URLs at request time (a known workaround pattern; not an officially supported Next.js feature).
- Resolving the per-env prefix another way at the edge for asset requests specifically (e.g. a routing cookie set on the first hit) instead of relying on the URL path alone for every subsequent request.

Either is real engineering work — not a config toggle — and should land before this amendment's routing change is considered usable end-to-end.

**Also needed, smaller in scope:**
- **Cookie `Path` scoping.** All environments now share one hostname; the BFF's iron-session cookie must be scoped to `Path=/{env-id}` explicitly, or a browser with two dev environments open would send environment A's session cookie to environment B's origin (same host, no path scoping = cookie visible platform-wide on that host by default).
- **Per-environment Dex OIDC redirect URI**, scoped under the shared host's path prefix (`https://orbit.dev.clearroute.io/{env-id}/...callback`) — provisioned per environment same as today, just a different redirect URI shape; each environment's own Dex client config already varies per environment, so this is a value change, not a new mechanism.

**Open question, not resolved by this amendment:** whether k3d/local dev environments should converge to this same path-based scheme for consistency (one routing mechanism to build/maintain instead of two), or keep the existing per-subdomain scheme since k3d has no wildcard-DNS/cert provisioning cost to avoid in the first place. Left for whoever picks up implementation. *(Resolved: converged — see the implementation slice below.)*

## Amendment Implementation — Path-Based App Ingress Built, k3d Converged, Blocker Resolved via Routing Cookie (2026-07-10)

The amendment above is now implemented. Three decisions the amendment left open were made here; each is recorded with its reasoning.

**Decision 1 — k3d converges to the path-based scheme (the amendment's open question).** There is exactly one app-ingress mechanism, on every infrastructure. Beyond "one mechanism to maintain," the deciding argument is testability: k3d is the only place this feature's changes get verified before staging, and a k3d that kept a hypothetical subdomain scheme would leave the real (path-based) scheme unexercisable locally. Nothing was actually removed to do this — the subdomain scheme for *app* traffic had never been built (the pre-amendment `devenvironment_ingress.go` carries only the kubectl API route); this slice is the app ingress existing at all. Locally the shared host is `devenv.orbit.local.clearroute.io` (under the same public `*.orbit.local.clearroute.io → 127.0.0.1` wildcard the host's own UI uses) via the existing k3d `8880→80` port mapping — no k3d config change needed.

**Decision 2 — the "known blocker" is resolved with the amendment's second option (a gateway routing cookie), because the first option cannot work.** The amendment's `X-Forwarded-Prefix` + Next.js-middleware sketch fails on inspection: Next.js middleware rewrites *incoming requests*; the unprefixed URLs that break the scheme are emitted in *outgoing* server-rendered HTML/RSC payloads (`/_next/static/...` asset references, `<Link>` hrefs), which middleware never touches — so unprefixed asset requests would still reach the gateway carrying no environment ID anywhere. The routing cookie needs zero frontend changes and preserves decision 4's identical-bits property completely. Mechanics (all in `devenvironment_app_ingress.go`):

- A shared L7 Gateway `devenv-app-gateway` (istio-system, same `app: gateway` workload as everything else) serves the shared hostname — plain HTTP :80 locally; with the new `devEnv.appTLSCredentialName` operator chart value set (real infrastructure), HTTPS :443 terminating with that istio-system Secret plus an HTTP→HTTPS redirect. The operator's new `ORBIT_DEVENV_APP_EXTERNAL_URL` / `devEnv.appExternalURL` supplies the base URL (`https://orbit.dev.clearroute.io`); its hostname is the listener's host match.
- `/{env-id}` and `/{env-id}/*` route to that environment's own in-vcluster ingress gateway — reachable host-side as the vcluster-synced Service `gateway-x-istio-system-x-vcluster.orbit-devenv-{env-id}.svc.cluster.local:80`, registered via a per-environment `ServiceEntry` (`MESH_EXTERNAL`, `resolution: DNS` — same two reasons, discoverySelectors and no-host-mTLS, as the kubectl route's ServiceEntry). The prefix is stripped (`rewrite.uri: /`) so the environment serves unprefixed, `X-Forwarded-Prefix` records what was stripped, and the response sets `orbit-devenv-route={env-id}; Path=/; HttpOnly; SameSite=Lax`.
- Every unprefixed request (assets, client-side navigation, BFF fetches, the OIDC callback) routes by that cookie.
- **All routes live in ONE aggregated VirtualService (`devenv-app-routes`), not one per environment** — deliberately unlike the kubectl route's per-environment VirtualServices. Istio's merge order across multiple VirtualServices on the same host is undefined, so a per-environment split could evaluate environment B's cookie-fallback before environment A's path prefix, letting a stale cookie hijack an explicit `/{env-id}` entry. The aggregated object pins the precedence: every environment's path routes first, every cookie fallback after (`TestReconcile_AppRoutesAggregateAcrossEnvironments` pins this). Rebuilt from the full CR list each reconcile; the deletion path rebuilds it excluding the dying environment (and drops the object entirely with the last environment).
- In-vcluster, the only change is a values override on the OrbitPlatform CR the reconciler applies (`frontendHost: {shared-app-hostname}` into both `PlatformValues` and `OrbitValues`): the host gateway forwards the original Host header, so each environment's own gateway/VirtualServices/EnvoyFilter must match the shared hostname instead of the image-baked `deploy/local` one. Same value for every environment — per-environment identity stays a host-gateway concern, never the environment's bits.

**Accepted limitations of the cookie scheme, explicitly:** after client-side navigation the browser URL is unprefixed, so deep links must re-enter through `/{env-id}`; and one browser profile talks to one environment at a time — visiting another environment's prefix repoints the routing cookie. A second environment needs a second browser profile.

**Decision 3 — the amendment's "cookie Path scoping" item is resolved by dissolution, not implementation.** Path-scoping the BFF session cookie to `Path=/{env-id}` assumed browser-visible URLs stay prefixed; under cookie routing they don't, so a path-scoped session cookie would never be sent. Instead, session-cookie collision between environments (same host, same hard-coded `orbit_session` name) is subsumed by the one-environment-per-browser-profile limitation above — the routing cookie already prevents talking to two environments from one profile, so the colliding session cookie costs exactly one re-login when switching. No frontend change.

**The identifier split is implemented as the amendment specified.** New `status.appURL` (`{appExternalURL}/{env-id}`) is the browser-facing entry point, surfaced through `internal/devenvironments` (`Environment.AppURL`) and rendered as the *Dev Environments* page's App column (a link only once `Ready` — the same no-dead-link concern the in-vcluster-readiness gate exists for). `status.ingressHost` is now documented as exactly one thing: the kubectl route's SNI/certificate-SAN value, unresolvable in DNS, never shown as a URL.

## Correction (2026-07-13): App-Ingress 404s — `devenv-app-gateway` Never Actually Served Traffic

Priority-order item 1 above (live-verify the routing end-to-end) surfaced the bug: every `/{env-id}` request 404'd.

**Root cause:** the previous slice's `devenv-app-gateway` (istio-system) and the platform's own `orbit-gateway` (`orbit-system`, `charts/orbit-platform/templates/gateway.yaml`) are two separate Istio `Gateway` resources that both select the same ingress-gateway workload (`app: gateway`) and both declare a server block for the exact same host (`AppExternalURL`'s hostname — identical to `orbit-gateway`'s `frontendHost`, by design, see "SAME shared gateway host" above) on the same port. Two `Gateway` resources are not additive for a workload+host+port triple already claimed by another: Istio binds one and silently drops the other's server block. `devenv-app-routes` (the aggregated VirtualService) named `devenv-app-gateway` in `spec.gateways`, but that Gateway's own server block was the one left unbound — so the VirtualService's routes never attached to a live listener, and every `/{env-id}` request fell through to whatever `orbit-gateway`'s own (unrelated) routing produced: a 404.

**Fix:** stop creating a devenv-owned Gateway at all. `devenv-app-routes` now names `orbit-system/orbit-gateway` in `spec.gateways` — the platform's own Gateway, which already terminates TLS/serves plain HTTP for this exact host for the platform frontend's own traffic. Multiple `VirtualService`s attached to one `Gateway`+host merge (Istio's normal, supported multi-tenant-ingress idiom — unlike competing `Gateway` resources on the same host+port, which do not); Istio also hoists exact/prefix `http.match` entries ahead of broader ones regardless of which `VirtualService` they came from, so `devenv-app-routes`' `/{env-id}` exact/prefix matches take precedence over the frontend's own catch-all route without any explicit ordering between the two objects. `ensureDevEnvAppAccess` now deletes any leftover `devenv-app-gateway` on reconcile (self-healing already-deployed clusters) instead of creating one. The now-dead `AppTLSCredentialName` plumbing (reconciler field, `ORBIT_DEVENV_APP_TLS_CREDENTIAL`/`devEnv.appTLSCredentialName` config) is removed — TLS for this host was always `orbit-gateway`'s own concern (`gateway.tls.credentialName` in the orbit-platform chart), never a devenv-specific setting.

**Lesson for future ingress additions:** a new `Gateway` resource is only safe when it owns a host+port triple no other `Gateway` already claims for the same workload selector (as the kubectl API route's `devenv-api-gateway` does — a distinct TLS-passthrough port, `16443`, nothing else uses). Sharing a host that another Gateway already serves means attaching a `VirtualService` to *that* Gateway, never declaring a competing one.

## Correction (2026-07-13): App-Ingress Infinite Redirect Loop — In-Vcluster Gateway Inherited the Host's `httpsRedirect`

Fixing the 404 above (by routing through `orbit-gateway`) exposed a second, previously-masked bug: requests to `/{env-id}` now reached the environment's own backend at all, and immediately looped — `301 https://{appHost}/` → `301 https://{appHost}/` forever, confirmed with `curl -L --max-redirs`.

**Root cause:** `devenvironment_app_ingress.go`'s own design says the host gateway forwards app traffic to each environment over **plain HTTP** — TLS terminates once, at the shared host gateway, never per environment. But `applyInVClusterOrbitPlatform` (`devenvironment_platform.go`) installs the *identical* `orbit-platform` chart inside every environment's vcluster that the host itself runs, and never overrode `gateway.tls`. The baked `deploy/local/platform-values.yaml` — copied verbatim into the operator image and loaded for every `OrbitPlatform` reconcile, host or in-vcluster alike (`platform_controller.go`'s `loadValuesFile`) — sets `gateway.tls.enabled: true`, correct for the **host's** own real external-facing `orbit-gateway`. Applied unmodified inside a vcluster, it makes that environment's own gateway serve port 80 with `tls.httpsRedirect: true` (`charts/orbit-platform/templates/gateway.yaml`), 301-redirecting every plain-HTTP request to the HTTPS version of the same external URL — which the host gateway then immediately re-requests over plain HTTP again, on and on. This was invisible until now because the 404 fix above was the first time a request ever reached this listener at all.

**Fix:** `applyInVClusterOrbitPlatform` now sets `PlatformValues["gateway"] = {"tls": {"enabled": false}}`, overriding the baked file (Helm-values merge order in `reconcileOrbitPlatform` puts `p.Spec.PlatformValues` last, i.e. highest priority) so every in-vcluster gateway install stays plain-HTTP-only, matching what the app-ingress design already assumed.

**Verified live**, end-to-end, after rebuilding and redeploying the operator image: a fresh environment's `/{env-id}` now returns a real `307` to `/login?next=%2F` (the app's own auth redirect) with the routing cookie set, and following it returns a real `200` login page — no 404, no loop. Re-ran the full delete-and-recreate cycle once after the fix to confirm it wasn't a one-off.

**Lesson for future in-vcluster chart installs:** any baked `deploy/local/*-values.yaml` default tuned for the *host's own* install is not automatically safe to reuse verbatim for an *in-vcluster* install of the same chart — anything host-topology-specific (TLS termination, external hostnames, ingress class) needs an explicit override in `applyInVClusterOrbitPlatform`, the same way `frontendHost` already gets one, rather than inheriting the host's file by default.

## Correction (2026-07-13): Browser Login Was Still Impossible — Dex Issuer Externalized

The two corrections above got a real user to a real login page — which then rejected every credential, including the fixture's own `dev@orbit.local.clearroute.io` / `password`. This is priority-order item 1's remaining half ("externalize the per-environment Dex issuer"), tracked but not yet done as of the Dex-redirect-URI paragraph above.

**Root cause, confirmed:** the frontend's `/login` redirects the browser straight to the tenant's OIDC issuer (`signinRedirect()` — no Orbit-hosted password form exists). Every dev environment's seeded `OrbitTenant` pointed that issuer at Dex's in-vcluster DNS name (`http://orbit-dex.orbit-devenv-fixtures:5556/dex`) — unreachable from a laptop browser, exactly as flagged above. The browser redirect either fails outright or (depending on what a stale cookie/cache serves) never reaches the real Dex, so no credential — fixture or otherwise — was ever actually being checked.

**Fix:** Dex is now routed through the same shared app-ingress host every other environment path already uses, instead of getting a second unreachable hostname. `devenvironment_app_ingress.go` adds a per-environment `/{env-id}/dex` + `/{env-id}/dex/*` route pair to the aggregated `devenv-app-routes` VirtualService — ordered *before* that environment's general `/{env-id}` app-prefix route, so it isn't shadowed by the broader match — rewriting only the `/{env-id}` segment away (`/{env-id}/dex/auth` → `/dex/auth`) rather than stripping to `/`, since Dex's own configured base path is `/dex`. The destination is the fixture Dex's vcluster-synced Service, added to the same per-environment `ServiceEntry` the app backend already uses. `appDexIssuerURL` (`{appExternalURL}/{env-id}/dex`) is now threaded into both the fixture Dex's own `issuer:` config (`devenvironment_fixtures.go`) and the seeded `OrbitTenant`'s OIDC issuer (`devenvironment_platform.go`) — they must be byte-identical or OIDC discovery's issuer check fails. Both the browser and the in-vcluster identity service's own discovery/JWKS fetch now resolve the same external hostname; `AppExternalURL`'s host is already patched into the **host** cluster's CoreDNS (`scripts/cluster/dev-cluster-up.sh`), and the ordinary DNS-forward chain (vcluster CoreDNS → node `resolv.conf` → host CoreDNS) makes it resolvable from inside a vcluster's own pods too, without a second CoreDNS patch.

**Verification status:** `TestReconcile_ProvisionsNamespaceQuotaAndVCluster` and `TestReconcile_AppRoutesAggregateAcrossEnvironments` extended for the two new routes and the second `ServiceEntry` host; `TestEnsureFixtures_DeploysPostgresRedisDex` extended to assert the configmap's `issuer:` line is the external URL, not the in-vcluster one. **Not yet live-verified on k3d** — that requires an operator-image rebuild, a fresh (or re-provisioned) environment, and actually completing a browser login end-to-end; whoever picks this up next should do that before considering the gap closed.

## Correction (2026-07-13): Bootstrap User Had Zero Scopes — Dex Now Backed by glauth, Not passwordDB

Even once a credential is accepted (the correction above), a freshly-provisioned environment's sidebar was missing every scope-gated nav item: Triggers, Policy, and most of Model Gateway (including the model catalog). This is a distinct gap from the login-rejection bug above — the user could log in, but resolved to zero effective scopes.

**Root cause, confirmed:** every scope a principal resolves comes from the OIDC `roles`/`groups` claim (merged in `service.go`, matched against `DefaultRoleScopes` in `policyservice/bundle/compiler.go`). **Fix:** added a fourth fixture, a minimal glauth (LDAP) Deployment/Service/ConfigMap in `orbit-devenv-fixtures`, seeded with a single `dev@orbit.local.clearroute.io` user in the `platform-admin` group — the same shape as Tier 1/2's directory, pared down to the one account a devenvironment needs. Dex's config switched from `enablePasswordDB`/`staticPasswords` to the same `type: ldap` connector (identical search filters/matchers) Tier 1/2 already uses, pointed at the new in-vcluster glauth Service. No frontend or scope-vocabulary change was needed — `DefaultRoleScopes` already covers `triggers:read`, `platform:grants:read`, `platform:roles:read`, and (via `platform-admin`) `platform:catalog:write`; they just had nothing to attach to.

**Verification status:** `TestEnsureFixtures_DeploysPostgresRedisDexGlauth` (renamed from `TestEnsureFixtures_DeploysPostgresRedisDex`) extended to assert glauth's configmap seeds the dev user and `platform-admin` group, and that Dex's config uses the LDAP connector rather than `enablePasswordDB`. `make check` green. **Not yet live-verified on k3d** — that requires a fresh (or re-provisioned) environment and a real login confirming the sidebar now shows Triggers/Policy/Model Gateway; whoever picks this up next should do that before considering the gap closed.

## Amendment (2026-07-13): Cookie-Based App-Ingress Fallback Can Hijack Main-App Traffic — Fallback to Be Replaced with App-Level Prefix Awareness

Investigating a report that the browser URL bar drops `/{env-id}` after entering a dev environment (the accepted limitation recorded above, line 924) surfaced a second, more serious problem in the same mechanism: the routing cookie can misroute a user's **plain visit to the main Orbit app** into their last-visited dev environment.

**Root cause, confirmed.** `devEnvAppCookieRoute` (`devenvironment_app_ingress.go`) matches purely on the `Cookie` request header (`orbit-devenv-route={env-id}`) — it has no `uri` match at all, so it applies to every path (`/`, `/dashboard`, `/login`, everything), not just asset/navigation requests inside a dev environment. The cookie itself is set with `Path=/` and no `Max-Age`/`Expires` (`devEnvAppPrefixRoutes`), so it is attached to every request to the shared host, `orbit.local.clearroute.io`, for the rest of the browser session — including requests the user intends for the real Orbit app, not any dev environment. The only place it is ever cleared is the dev-environment-only "Return to Orbit" action (`/api/dev-environment/exit`); closing the tab, bookmarking the host, or simply navigating back to it later leaves the cookie intact. Istio's route-merge sorting (confirmed by the 2026-07-13 404 correction above: exact/prefix matches are hoisted ahead of broader ones regardless of source `VirtualService`) places any route carrying a match condition — including a header-only match — ahead of `orbit-frontend`'s completely unconditional catch-all route. That makes the misrouting deterministic, not merely theoretical: once the cookie exists, it wins over the main app's own route for any path, on every request, until the user takes the explicit exit action.

This is distinct from, and more serious than, the already-accepted "URL bar loses the prefix after navigation" limitation: that one is a cosmetic/deep-linking annoyance inside a dev environment; this one silently redirects a user who believes they are looking at the main Orbit app into someone else's — or their own stale — dev environment, with no visual indication anything is wrong.

**Decision:** stop using an unscoped, path-independent cookie as the general routing mechanism for unprefixed requests. Instead, make the dev-environment frontend itself prefix-aware at runtime, so it emits correctly-prefixed navigation and redirect URLs in the first place, rather than relying on the gateway to guess the right environment from a global cookie after the fact. Concretely:

- The gateway already strips `/{env-id}` and sets `X-Forwarded-Prefix` on the way in (`devEnvAppPrefixRoutes`) — currently unused by the app. The frontend's root layout reads this header server-side on the initial request and threads the prefix through to client code (via an inline runtime value, not a build-time Next.js `basePath`, which decision 4's shared-image constraint still rules out).
- The specific redirect/navigation call sites already identified as emitting unprefixed absolute URLs — `frontend/src/lib/oidc-client.ts` (`redirect_uri` from `window.location.origin`), `frontend/src/app/auth/callback/page.tsx` (`router.replace(next)` defaulting to `/`), `frontend/src/app/(auth)/login/page.tsx`/`email-sign-in-form.tsx` (`next` defaulting to `/`), and `dashboard-header.tsx`'s `returnToOrbit()` — are updated to construct URLs from the known runtime prefix instead of assuming root.
- Once the app's own emitted URLs are correctly prefixed, the general-purpose, any-path `devEnvAppCookieRoute` fallback is deleted outright — not narrowed, removed — closing the hijack vector structurally rather than patching its scope. Only a narrowly `uri`-scoped fallback for `/_next/*` static assets (never a page a user navigates to directly, so never competitive with `orbit-frontend`'s catch-all in practice) is retained if Next.js's asset URLs can't be made prefix-aware the same way.
- Immediate stopgap, independent of the above and safe to land first: cap the routing cookie's lifetime (short `Max-Age`, refreshed only by dev-env traffic) instead of a session-only, unbounded-`Path=/` cookie, so a stale cookie self-expires quickly even before the app-level fix ships.

**Consequences:** this also resolves the accepted URL-bar limitation as a side effect — once the app emits its own correctly-prefixed URLs instead of unprefixed ones the gateway has to catch after the fact, the browser URL stays on `/{env-id}` through navigation and login, and the "one browser profile per environment" limitation (line 924) goes away with it. Cost: this is real frontend work (threading a runtime prefix through routing/auth/link construction), not a gateway-only config change, and needs verification that every remaining unprefixed emission point (not just the four call sites already found) is caught before the fallback route is actually deleted — a premature removal would reintroduce 404s for anything still unprefixed, with no fallback left to catch it.

**Not yet implemented** — this amendment records the decision; implementation is a separate follow-up.

## Amendment Implementation — Stopgap and Login-Path Prefix Landed; Full Cookie-Fallback Removal Still Open (2026-07-13)

The stopgap and the login round-trip's prefix-restoration are implemented; the larger decision (delete the general `devEnvAppCookieRoute` fallback once the app is fully prefix-aware) is not — that still needs every unprefixed emission point found and fixed, not just the login path, and live k3d verification neither piece below has had yet.

**Stopgap landed:** `devEnvAppPrefixRoutes`'s `Set-Cookie` now carries `Max-Age=900` (`devEnvRouteCookieMaxAgeSeconds`) instead of a session-only cookie. Every prefixed request re-sets it, so an actively-used environment's cookie never actually expires underfoot — only an abandoned one does, bounding the hijack window to 15 minutes of inactivity instead of the rest of the browser session.

**Login-path prefix restoration landed**, narrower than the amendment's full sketch: rather than making the whole app prefix-aware (every link, every fetch), only the unauthenticated-redirect round trip through `/login` is fixed, because that round trip is enough to resolve the originally-reported symptom (the browser URL not showing `/{env-id}` after entering an environment and logging in) without touching the OIDC `redirect_uri` registration or the cookie-fallback route's scope at all:

- New `frontend/src/lib/routing/devenv-prefix.ts` (`getDevEnvPrefix`) reads the already-set-but-previously-unused `X-Forwarded-Prefix` request header.
- `frontend/src/proxy.ts`'s two `/login` redirects (no session; session destroyed after a failed refresh) now build the `Location` as `{prefix}/login` and set `next={prefix}{pathname}`, instead of always redirecting to the unprefixed `/login`.
- `frontend/src/app/(auth)/login/page.tsx` now reads the same header directly (`headers()`, since it runs as a Server Component reached both via proxy.ts's redirect and by a direct visit with no `?next=` at all) and defaults `next` to `{prefix}/` instead of `/`, and its already-authenticated fast-path redirect does the same.
- Nothing downstream of `/login` needed a change: `EmailSignInForm` already threads whatever `next` it's given into the OIDC `state` unmodified, and `auth/callback/page.tsx` already does `router.replace(state.next)` — so a correctly-prefixed `next` set at the `/login` step survives the entire IdP round trip and lands the browser back on `/{env-id}/...` with no further plumbing. This relies on `/{env-id}/*` already being an explicit, deterministic gateway route (`devEnvAppPrefixRoutes`'s prefix match, any subpath) — not the cookie fallback — so `router.replace()`'s background RSC fetch for a prefixed path resolves correctly today, independent of this amendment's larger cookie-removal goal.

**Deliberately not changed:** `oidc-client.ts`'s `redirect_uri` (stays host-scoped, unprefixed — changing it would require re-registering every environment's Dex client with a prefixed callback URL, out of scope for this slice) and `dashboard-header.tsx`'s `returnToOrbit()` (its unprefixed `'/'` target is the correct, intentional destination — it deliberately exits the dev environment back to the real Orbit app, not a bug this amendment needs to fix). The amendment's original text listed both among the call sites needing a fix; on inspection neither did.

**Still open, and the harder remainder of this amendment:** the general-purpose `devEnvAppCookieRoute` fallback is untouched and still matches every path once its cookie is present — ordinary in-app navigation (clicking any sidebar link), most BFF `/api/*` fetches, and the OIDC callback itself all still rely on it, because their `href`/`fetch` targets are root-relative absolute paths with no prefix, throughout the app, not just on the login round trip. Narrowing or deleting that route now, without fixing every one of those call sites first, would break the dev environment outright (404s with no fallback left to catch them) — confirmed by re-reading the fallback's actual usage surface while implementing the piece above, not by trying it. Deleting it is unchanged from "not yet implemented": it needs the same treatment as `/login` — a runtime-prefix-aware base for every internal `AppLink`/`router.push`/`fetch` call — applied app-wide, which is substantially more surface than this slice covers.

## Correction (2026-07-13): Dev Environments Could Provision Further Dev Environments — Nav Tab and Creation Now Blocked at the Frontend Layer

Auditing the *Dev Environments* nav item and the "New environment" action found that nothing anywhere in the stack stopped a dev-environment-nested Orbit install from provisioning another dev environment inside itself. This is a gap against this ADR's own isolation intent (decision drivers: "Cluster-scoped resources are the crux," "blast radius of a broken environment must be one namespace on the host") that had gone unnoticed because `devEnvironmentId` — the session field added earlier for the "Return to Orbit" affordance (`dashboard-header.tsx`) — was never consumed anywhere else.

**Root cause, confirmed:** `useSession().devEnvironmentId` (sourced from `config.devEnvironmentId` / `ORBIT_DEV_ENVIRONMENT_ID`, set only on an in-vcluster frontend per `frontend/src/server/config.ts`) already told the app "this install is itself a dev environment," but the *Dev Environments* nav entry (`nav-entries.ts`) had only a `requiredScope` filter, the "New environment" button (`dev-environments-page.tsx`) had no gate at all, and `POST /api/dev-environments` (the BFF route) forwarded straight to `createDevEnvironment(...)` with no check. On the backend side the gap is total: `internal/devenvironments` (hosted in `cmd/identity`) has no `DevEnvironmentID`/`IsDevEnvironment` field in its `Config` at all, and `CreateEnvironment` (`service.go`) checks only the owner's active-environment quota — `ORBIT_DEV_ENVIRONMENT_ID` is wired exclusively into the **frontend** container's ConfigMap (`charts/orbit/templates/frontend/configmap.yaml`), never into `identity`'s own. So a dev environment's own UI could, and would, provision a nested vcluster exactly as a host install does.

**Fix, frontend/BFF layer only:**
- `NavEntry` (`nav-entries.ts`) gained a `hideInDevEnv?: boolean` flag, set on the Dev Environments entry; `dashboard-sidebar.tsx`'s existing scope filter now also drops any `hideInDevEnv` entry when `useSession().devEnvironmentId` is set — same filter pass, one added clause, no new pattern.
- `POST /api/dev-environments` (`frontend/src/app/api/dev-environments/route.ts`) now short-circuits with `403 forbidden` when `config.devEnvironmentId` is set, before it ever calls `createDevEnvironment` — the request never reaches the backend.
- `DevEnvironmentsPage` (`dev-environments-page.tsx`) hides the "New environment" button (header and empty-state action) and swaps the description copy to explain why, when `devEnvironmentId` is set, so the page never surfaces a create action that would just 403.

**Remaining gap, explicitly not closed:** this fix only covers the path through the BFF. A caller that reaches the backend's `POST /v1/dev-environments` directly from inside a dev environment — bypassing the BFF entirely — is not blocked; `internal/devenvironments` still has no signal to check. Closing that properly needs the same handoff this ADR already uses elsewhere (the operator's `OrbitPlatformSpec.DevEnvironmentID` field, set by `applyInVClusterOrbitPlatform` and consumed by `platform_controller.go`): thread an equivalent `DevEnvironmentID` into the `identity` binary's own config for in-vcluster installs, and check it in `CreateEnvironment` alongside the existing quota check. Tracked as a follow-up, not yet implemented.

**Verification status:** `pnpm lint` and `pnpm tsc --noEmit` clean. Not yet live-verified against a running dev environment on k3d — whoever picks up the backend follow-up above should verify both pieces together.
