Identity • Policy • Credentials

🤔 The Problem

Autonomous agents are powerful but dangerous:

  • Uncontrolled access: Agent runs as your identity → can access everything you can
  • No accountability: What did this agent do? → Unanswerable without traces
  • Security risks: Agent given access to deployment system → can push malicious code
  • Multi-tenant nightmare: One agent's bug could compromise all tenants
  • Credential exposure: Agent stores API keys → keys get stolen, leaked, logged
On your laptop: ✓ OK — you control the agent moment-to-moment
In production at scale: ✗ Broken — agent has too much power, no oversight

✨ The kora Solution

Policy enforcement at every boundary. Before an agent can take ANY action, kora intercepts it, checks a policy, and decides: allow or deny.

Three questions answered for every operation:

❓ Who?

Machine-verifiable identity via SPIFFE certificate

❓ What?

Policy check via OPA before execution

❓ How?

Credentials injected, never exposed to agent

❓ Question 1: Who Is This Agent?

Answer: SPIFFE Identity

Every agent gets a machine-verifiable identity at deploy time.

1. Pod is scheduled → Kubernetes assigns ServiceAccount
2. SPIRE Agent detects pod → Verifies pod credentials
3. Certificate issued → X.509 cert signed by Root CA
Subject: spiffe://kora.example.com/ns/prod/sa/agent-xyz
4. Certificate mounted → At /var/run/secrets/spiffe/cert.pem
5. Certificate used → Envoy uses it to prove identity to policy engine
Why SPIFFE? Certificate is bound to pod, rotated continuously, unforgeable. Not an API key that can be stolen.

❓ Question 2: What Can It Access?

Answer: OPA Policy Decision

Before every action, evaluate a policy. By default: DENY. Explicitly ALLOW only what you define.

// Rego policy (stored, versioned, auditable) allow { input.principal.id == "agent-xyz" input.action == "call_api" input.resource == "https://api.github.com/*" input.time < expires_at }

Policy Decision Points:

  • ✓ Can this agent call this API?
  • ✓ Can this agent read this file?
  • ✓ Can this agent execute this command?
  • ✓ Has the permission expired?

❓ Question 3: How Does It Connect?

Answer: Credentials Injected, Never Exposed

Agent never sees credentials. Credentials are injected at the network layer, just-in-time.

Agent code: db.connect("host=db.example.com") (no password!)
Envoy intercepts → Calls Identity Service
Identity Service exchanges identity for credentials → Gets temporary password
Credentials injected: db.connect("host=db.example.com user=agent_xyz password=temp_pwd")
Connection established → Agent never knew password existed
Result: If agent is compromised, attacker has no credentials to steal.

🔄 Complete Request Flow

An agent calls an external API. Here's what happens:

1️⃣ Agent code: GET https://api.github.com/data
2️⃣ Envoy intercepts → Extracts SPIFFE identity
3️⃣ Policy check: "Can agent-xyz call api.github.com?"
→ Policy Gateway evaluates OPA → Decision: ALLOW ✓
4️⃣ Credential exchange: "Get credentials for api.github.com"
→ Identity Service returns temporary GitHub token
5️⃣ Injection: Authorization: Bearer <token>
6️⃣ Request sent → api.github.com validates token → 200 OK
7️⃣ Response to agent → Agent receives data, unaware of any intervention
8️⃣ Audit logged: Principal, action, resource, decision, timestamp

🔗 Webhook → Agent Execution

1. GitHub sends webhook: "PR opened"
2. Triggers receives, stores in durable queue (Postgres)
3. Triggers looks up trigger rule: "PR opened → run code-review-agent"
4. Kora Agents receives execution request, creates Run
5. Session Manager allocates resources, sets up environment
6. Agent pod starts, agent code executes
7. Agent calls external APIs (GitHub, etc.)
8. Envoy intercepts → Policy check → Credential injection
9. Agent completes, result stored
10. Triggers marks delivery complete (exactly-once guarantee)

🏢 Multi-Tenant Isolation

Each tenant's agent runs in its own namespace with its own SPIFFE identity.

🔒 Namespace Isolation

Tenant-A pod in tenant-a namespace
Tenant-B pod in tenant-b namespace

🆔 Identity Per Tenant

SPIFFE cert includes tenant context
spiffe://kora/ns/tenant-a/sa/...

🚫 Cross-Tenant Blocked

Tenant-A agent cannot call Tenant-B Session Manager
Policy enforces separation

Result: One tenant's compromised agent cannot access another tenant's data or credentials.

📦 Multi-Binary Deployment

kora is NOT a monolith. Each service is an independent binary.

✅ Independent Scaling

Scale Policy Gateway without touching Identity Service

✅ Independent Deployment

Deploy Skills Service update without redeploying everything

✅ Failure Isolation

Triggers crash doesn't take down the Identity Service

Why? Clear boundaries, independent teams, faster iteration, better reliability.

🔐 Security First

  • Identity-Driven: All actions tied to verified, unforgeable identity
  • Policy-First: Policies enforced BEFORE execution, not after
  • Credential Brokering: Agent never handles raw credentials
  • Least Privilege: By default DENY, explicitly ALLOW only needed
  • Audit Trail: Every action logged: who, what, when, decision, result
  • Multi-Tenant Safe: Tenants isolated by namespace, identity, policy
  • Standards-Based: SPIFFE, OPA, Istio — no proprietary crypto

🧩 Key Abstractions

Principal

Agent, User, or Service
Has identity & permissions

Grant

Permission: Principal → Action
Scoped to resource, time, quota

Role

Named collection of grants
e.g., "data-analyst"

Policy: Rego rule that evaluates Grants & Roles → Allow/Deny decision

🎯 Development Philosophy

  • Security First: Every component assumes potential attackers
  • Identity-Driven: All decisions tied to verified identity
  • Policy as Code: Policies version-controlled, testable, auditable
  • Clear Boundaries: Each service has clear responsibility
  • No Hidden Magic: If something is done for you, understand it
  • Observability Built-in: Every component emits logs, metrics, traces
  • Repository Pattern: Data access abstracted behind interfaces
  • Standards-Based: Use open standards (SPIFFE, OPA, OpenTelemetry)
